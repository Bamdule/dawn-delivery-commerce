# 03. 결제 복구

주문, 재고, 결제, 가짜 결제 대행사를 실제 프로세스로 띄우고, 대행사 장애를 섞은 주문 300건을 흘립니다.
도중에 서비스를 SIGKILL 로 죽였다가 다시 띄운 뒤, 세 서비스와 대행사의 상태가 모두 맞는지 봅니다.
두 번 돌렸습니다. 첫 실행은 주문 서비스만, 둘째 실행은 결제, 주문, 재고 서비스를 차례로 죽였습니다.
두 번 모두 돈이나 예약이 어긋난 주문 0건, 재고 합 어긋남 0입니다.

## 준비

- **환경:** Apple M3 8코어 노트북. MySQL 8.4 와 Kafka 4.0 컨테이너 하나씩, 서비스 네 개는 실행 jar 로 띄운 별도 JVM
- **상품:** 20개, 재고 1,000개씩, 예약 유지 1분. 실험 시간을 줄이려고 운영(일반 10분)보다 짧게 둡니다
- **배치 주기:** 결제 조회와 환불 2초, 예약 만료 5초, 주문 정리 5초, 주문 환불 3초. 판단 기준(1분 넘은 시도, 요청 없음 60초)은 운영값 그대로입니다
- **고객:** 초당 10건씩 300명. 응답을 못 받으면 같은 주문서 ID 로 1초마다 다시 보내고, 카드가 거절되면 다른 카드로 한 번 더 결제합니다
- **실행:** `./gradlew :system-experiment:experiment` (`PaymentRecoveryExperiment`)

대행사의 승인 동작은 아래를 고정한 시드로 섞어 줄 세웠습니다. 줄을 다 쓰면 정상 승인입니다.

| 동작 | 건수 | 무엇을 흉내 내나 |
|---|---|---|
| 승인 | 210 | 정상 |
| 거절 | 30 | 잔액 부족 |
| 승인 후 5초 지연 | 20 | 승인됐지만 응답 유실 (결제 서비스 타임아웃 3초) |
| 처리 전 500 | 15 | 대행사 오류. 같은 키로 다시 보내면 처리 |
| 승인 후 500 | 15 | 처리한 뒤 오류 |
| 20초 뒤 늦은 승인 | 20 | 대행사가 늦게 받은 요청을 나중에 처리 |
| 받지 못함 | 15 | 요청이 대행사에 닿지 않음 |

## 절차

1. **첫 실행:** 주문을 흘리기 시작하고 12초에 주문 서비스를 SIGKILL 로 죽입니다. 6초 뒤 같은 DB 로 다시 띄웁니다
   **둘째 실행:** 6초에 결제, 14초에 주문, 22초에 재고 서비스를 차례로 죽이고 각각 6초 뒤 다시 띄웁니다. 실행 jar 는 복사본으로 띄워, 실험 중 빌드가 jar 를 덮어써도 영향이 없게 합니다
2. 부하가 끝나면 멈춘 상태가 하나도 남지 않을 때까지 5초마다 셉니다. PENDING 주문, 진행 중 환불, REQUESTED 결제, HELD 와 PAYING 예약, PENDING 아웃박스입니다
3. 대행사의 정산 기록과 세 서비스의 DB 를 대조합니다

## 예상

- **돈:** 주문마다 대행사에서 빠져나간 돈(승인 합 - 완료된 환불 합)이 PAID 면 주문 금액, 아니면 0 입니다
- **재고:** PAID 주문의 예약은 CONFIRMED 이고, 그 밖의 주문은 풀려 있습니다. 상품마다 처음 재고 = 남은 재고 + 확정 수량입니다
- **수렴:** 결과를 모르는 상태는 결제 조회 배치가, 끊긴 결제 시도는 주문 정리 배치가, 남은 예약은 만료 배치가 끝냅니다

## 실제

| 항목 | 첫 실행 (주문만 중단) | 둘째 실행 (결제, 주문, 재고 차례로 중단) |
|---|---|---|
| 부하와 수렴 | 부하 32초, 그 뒤 62초 만에 멈춘 상태 0 | 부하 35초, 그 뒤 581초 만에 멈춘 상태 0 |
| 고객의 다시 보내기 | 501번 | 520번 |
| 첫 응답 | 결제 완료 201, 결제 확인 중 68, 카드 거절 24, 결제 진행 중 6, 실패 1 | 결제 완료 40, 결제 확인 중 108, 카드 거절 7, 실패 143, 그 밖 2 |
| 최종 주문 | PAID 279, FAILED 21 | PAID 57, FAILED 243 |
| 대행사 | 승인 279건, 승인이 둘 이상인 주문 0건 | 승인 57건, 승인이 둘 이상인 주문 0건 |
| 대조 | 어긋난 주문 0건, 재고 합 어긋남 0 | 어긋난 주문 0건, 재고 합 어긋남 0 |

- **결제 확인 중 68건:** 대행사 타임아웃과 오류를 결제 서비스가 "모름"으로 돌려준 주문입니다. 조회 배치와 결제 이벤트로 모두 PAID 나 FAILED 가 됐습니다
- **결제 진행 중 6건:** 강제 종료가 결제 시도 중간을 끊은 주문입니다. 재기동 뒤 같은 주문서로 다시 요청했을 때 새 시도를 열지 않았고, 정리 배치가 회차를 봉인해 끝냈습니다
- **실패 1건:** 재고 예약이 500ms 안에 답하지 않아 주문을 바로 닫았습니다. 혹시 잡힌 예약은 만료로 풀려 재고 합이 맞았습니다
- **FAILED 21건:** 대행사가 끝내 받지 못한 주문과 두 번 거절된 주문은 다시 결제하지 않아, 예약이 만료된 뒤 정리 배치가 닫았습니다

둘째 실행은 실패가 많지만 모두 돈이 빠져나가지 않은 실패입니다. 서비스 로그로 원인을 나눴습니다.

- **재고 예약 실패 143건:** 대부분 1초 안에 몰렸습니다. 주문 서비스가 재기동에 3~4초 걸려, 다시 뜬 순간이 재고 서비스를 죽인 시각과 겹쳤습니다. 재시도를 기다리던 고객 약 80명이 한꺼번에 들어와 바로 실패로 닫혔습니다. 예약은 500ms 에 한 번만 다시 시도하는 설계 그대로입니다
- **결제 확인 중 108건:** 대부분 결제 서비스가 죽어 있던 동안의 주문입니다. 회차가 열리지 않은 채 끝나, 정리 배치가 1분 뒤 그 회차를 봉인하고 시도를 끝냈습니다. 고객이 다시 결제하지 않아 예약 만료 뒤 FAILED 가 됐습니다
- **수렴 581초:** 예약은 잡혔는데 만료 시각을 주문에 저장하기 전에 주문 서비스가 죽은 주문이 하나 있었습니다. 만료 시각을 모르는 주문은 설계대로 "주문 시각 + 최대 유지 시간 10분"이 지나야 닫힙니다

첫 시도에서 둘째 실행은 쓸 수 없는 결과를 냈습니다. 실험 도중 제가 같은 저장소에서 빌드를 돌려, 실행 중인 서비스의 jar 가 덮어써졌습니다.
가짜 대행사가 아직 읽지 않은 클래스를 찾지 못해 요청 스레드가 죽었고, 대조 단계가 응답을 기다리며 멈췄습니다. 지금은 jar 복사본으로 띄우고 HTTP 호출에 시간 제한을 둡니다

## 시험되지 않은 것

- **장애 중 고객의 재결제:** 실험의 고객은 카드 거절일 때만 다시 결제합니다. 결제 서비스 장애로 "결제 확인 중"을 받은 고객이 예약 유지 시간 안에 다시 결제하는 경로는 기존 통합 테스트가 맡습니다

- **쓰이지 않은 승인의 환불:** 0건이었습니다. 늦은 승인(20초)이 "요청 없음" 판정(마지막 전송 60초 뒤)보다 먼저 와서, 실패로 닫힌 회차가 승인되는 일이 없었습니다. 설계대로 막힌 것이고, 이 안전망은 정산 대사 통합 테스트가 맡습니다
- **운영 시간 그대로의 예약 유지(10분):** 실험 시간을 줄이려고 1분으로 줄였습니다
