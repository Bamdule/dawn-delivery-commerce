# dawn-delivery-commerce

[![build](https://github.com/Bamdule/dawn-delivery-commerce/actions/workflows/build.yml/badge.svg)](https://github.com/Bamdule/dawn-delivery-commerce/actions/workflows/build.yml)

가상의 새벽배송 커머스로 주문, 재고, 결제, 출고의 정합성을 설계하고, 그 설계가 실제로 동작하는지 테스트와 실험으로 증명한 개인 프로젝트입니다.

> 가상 시나리오입니다. 실제 운영 서비스나 실무 성과가 아닙니다.

## 2분 요약

- **무엇을 설계했나:** 특가에 초당 500건이 몰려도 재고를 실제보다 많이 팔지 않고, 결제 응답이 사라져도 돈이 새지 않고, 23:00 마감 뒤 30만 주문을 01:00 까지 센터에 나누는 시스템입니다. 설계 문서 일곱 개에 문제를 숫자로 세우고 고른 것과 포기한 것을 함께 남겼습니다
- **무엇으로 증명했나:** 설계의 완료 조건을 테스트 212개로 옮겼고, 푸시마다 CI 가 실제 MySQL 과 Kafka 로 돌립니다. 서비스 네 개를 실제 프로세스로 띄우고 결제, 주문, 재고 서비스를 차례로 강제 종료해도 돈과 재고가 어긋난 주문이 0건이었습니다
- **무엇을 찾아 고쳤나:** 설계의 숫자 가정을 실제로 쟀습니다. 예약 트랜잭션이 몰리는 행의 잠금을 필요 이상 쥐던 것, 릴레이의 기록 방식, 할당이 한 센터로 쏠리던 것을 찾아 고쳤고, 고친 뒤 다시 재서 확인했습니다

## 테스트와 실험으로 확인한 것

| 주장 | 증거 |
|---|---|
| 재고 100개에 300건이 동시에 와도 정확히 100건만 팔린다 | 재고 동시성 테스트. 상품 순서가 반대인 주문 1,000쌍을 섞어도 교착 0 |
| 특가 상품은 슬롯 8개가 있어야 초당 500건을 받는다 | [실험 01](docs/experiments/01-재고-동시성.md). 슬롯 없이 상품 3개 주문은 초당 약 400건에서 막혀 대기가 6초까지 쌓이고, 슬롯 8개는 p99 37ms |
| 결제 응답이 사라져도 승인은 한 번이고, 결과를 모르는 결제는 끝까지 수렴한다 | 결제와 주문 통합 테스트, [실험 03](docs/experiments/03-결제-복구.md). 대행사 장애 6종과 서비스 강제 종료를 섞어도 어긋난 주문 0건 |
| 커밋과 이벤트 발행이 어긋나지 않는다 | 아웃박스 테스트. 릴레이 두 대가 동시에 돌아도 이벤트마다 한 번, 같은 키의 순서 유지. [실험 02](docs/experiments/02-릴레이-처리량.md)에서 릴레이 한 대가 초당 약 1만 건 |
| 30만 주문의 출고 지시가 01:00 목표 안에 끝난다 | [실험 04](docs/experiments/04-출고-배치.md). 고르게 나뉘면 약 10분, 한 센터에 절반이 몰려도 약 13분 |
| 마감 경계에서 주문이 빠지거나 하루 일찍 나가지 않는다 | 출고 배치 테스트. 이벤트가 처리 실패 토픽으로 빠진 주문도 오르고, 23:04 결제 주문은 다음 회차로 간다 |
| 운영자가 멈춘 상태를 놓치지 않는다 | 서비스마다 Prometheus 지표와 경보 규칙 27개. 시각 기준 경보는 promtool 테스트 |

## 구조

```
[클라이언트] --주문서 ID--> [주문] --동기--> [재고]  예약, 결제 시작 표시
                              |    --동기--> [결제] --> [결제 대행사]
                              |
                  주문 확정 + 아웃박스 (한 트랜잭션)
                              |
   order.events -----> [재고] 예약 확정    [풀필먼트] 출고 대상 등록
   payment.events ---> [주문] 늦게 확정된 결제 반영, 환불 결과
   fulfillment.events -> [주문] 못 채운 품목의 취소와 환불, [재고] 입고와 실사 반영

   마감 후 [풀필먼트 배치]: 대상 확정 -> 할당 -> 판정 발행 -> 센터별 출고 지시 -> 결과 검증
```

사용자가 기다리는 것은 재고 예약과 결제 결과까지이고, 그 뒤의 일은 이벤트로 흘려보냅니다.
서비스마다 DB 를 따로 두고 서비스 사이를 한 트랜잭션으로 묶지 않습니다.
대신 결과가 늦게 확정되는 상태마다 그 상태를 마무리할 주인과 기한, 경보를 하나씩 정했습니다.

## 핵심 설계 결정

| 문제 | 선택 | 포기한 것 | 설계 문서 |
|---|---|---|---|
| 동시 주문의 오버셀 | 조건부 UPDATE 한 문장으로 차감 | 명시적 락의 단순함 | [02](docs/design/02-재고-정합성.md) |
| 특가 상품 한 행에 몰림 | 상한을 넘는 상품만 슬롯 8개로 분산 | 정확한 실시간 잔량 | [02](docs/design/02-재고-정합성.md) |
| 결제와 예약 만료의 경합 | 예약을 HELD 와 PAYING 으로 나누고, PAYING 은 결제 회차를 봉인한 뒤에만 풂 | 만료 시각만 보는 단순한 배치 | [02](docs/design/02-재고-정합성.md) |
| 커밋과 발행의 불일치 | 아웃박스, 선점 후 전송하는 릴레이, 처리 실패 토픽 | 즉시 발행 | [03](docs/design/03-이벤트-전달-보장.md) |
| 결제 응답 유실 | 주문번호와 결제 회차의 멱등키, 결제 이벤트와 주문 정리 배치 | 사용자 앞에서 끝까지 확정 | [04](docs/design/04-멱등성과-실패-복구.md) |
| 주문 요청 중복 | 주문서 ID 유니크 | 클라이언트가 ID 를 들고 다니는 수고 | [01](docs/design/01-전체-설계.md) |
| 마감 경계의 늦은 이벤트 | 배치 첫 스텝에서 주문 서비스 목록과 대조하고 입력을 표로 고정 | 이벤트만 믿는 단순함 | [05](docs/design/05-풀필먼트-배치.md) |
| 실사 부족과 취소 복원 | 반영 못 한 부족분을 들고 있다가 복원이 먼저 갚음, 하루 한 번 재고 대사 | 0 에서 멈추고 잊는 단순함 | [02](docs/design/02-재고-정합성.md) |

## 실행

Java 21과 Docker가 필요합니다.

```bash
./gradlew build                    # 테스트가 Testcontainers 로 MySQL 과 Kafka 를 직접 띄운다
docker compose up -d --wait        # 서비스를 직접 띄울 때. MySQL 13306, Kafka 19092
java -jar order-service/build/libs/order-service-0.0.1-SNAPSHOT.jar
```

각 서비스는 기동할 때 Flyway 로 자기 DB 의 테이블을 만듭니다. 상태는 `/actuator/health`, 운영 지표는 `/actuator/prometheus` 로 봅니다.
지표와 경보 규칙을 함께 보려면 `docker compose --profile monitoring up -d` 로 Prometheus(19090)를 띄웁니다.
실험은 몇 분씩 걸려 기본 빌드에서 빼고 `./gradlew experiment` 로 따로 돌립니다.

## 기술

Java 21, Spring Boot 4.1, Spring Batch 6, Spring Kafka, MySQL 8.4, Kafka 4.0(KRaft), Flyway, Testcontainers, Spring REST Docs, Micrometer와 Prometheus, GitHub Actions
