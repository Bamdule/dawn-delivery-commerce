# 02. 재고 정합성

## 요약

**무엇을 설명하나:** 재고 100개에 동시 주문 300건이 들어올 때 실제보다 많이 팔지 않는 방법입니다.
차감 방식, 특가 상품 분산, 예약과 만료, 판매 가능 재고와 실물 재고의 분리를 차례로 정합니다.

**재고 정합성은 무엇에 쓰나:** 오버셀이 나면 고객에게 취소를 통보해야 하고, 새벽배송에서는 그날 배송이 불가능해집니다.

**세 줄 요약**
1. 조회하고 계산해서 쓰면 300건이 모두 100을 읽어 갱신이 유실되므로, 조건부 UPDATE 한 문장으로 차감합니다.
2. 한 행의 상한(초당 200건)을 넘는 특가 상품만 재고를 슬롯 8개로 쪼갭니다.
3. 예약은 결제 시작을 PAYING 과 회차, 기한으로 표시하고, 만료 배치는 결제 기한이 지나기 전에는 PAYING 을 풀지 않습니다.

---

## 문제를 숫자로 세우기

> 재고 100개에 300건이 동시에 100을 읽고 99를 쓰면 주문 300건이 모두 성공합니다. 이 갱신 유실이 오버셀을 만듭니다.

재고가 100개인 상품에 동시에 300건의 주문 요청이 들어옵니다. 코드가 이렇게 되어 있다고 가정합니다.

```java
Stock stock = stockRepository.findById(productId);   // 100 을 읽음
if (stock.getQuantity() < orderQty) throw new OutOfStock();
stock.setQuantity(stock.getQuantity() - orderQty);   // 99 로 계산
stockRepository.save(stock);                          // 99 를 씀
```

300개 요청이 거의 같은 순간에 100을 읽고, 각자 1을 빼 99를 씁니다.
재고는 99가 되고 주문은 300건이 성공합니다. 200건은 팔 수 없는 물건입니다.
이게 갱신 유실입니다. 두 요청이 같은 값을 읽고 각자 덮어쓰면 한쪽 갱신이 사라집니다.

## 선택지와 각각이 깨지는 지점

> 비관적 락, 원자적 조건부 갱신, 낙관적 락, Redis 선점을 봅니다. 조건부 갱신을 고르지만 이것도 같은 행에 직렬화됩니다.

### 방법 1. 비관적 락

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Stock> findByProductIdForUpdate(Long productId);
```

조회 시점에 행을 잠그므로 300건이 한 줄로 서고 재고는 정확해집니다.

**어디서 깨지는가.** 한 건 처리가 5ms 라면 300번째 요청은 1.5초를 기다리고, 그동안 커넥션도 잡고 있습니다.

### 방법 2. 원자적 조건부 갱신

```sql
UPDATE stock
   SET quantity = quantity - :qty,
       updated_at = NOW(3)
 WHERE product_id = :productId
   AND quantity >= :qty
```

읽지 않고 바로 씁니다. 재고가 부족하면 아무 행도 갱신되지 않고, 영향받은 행 수가 0이면 품절로 판정합니다.
DB가 갱신하는 순간 행을 잠그고 커밋까지 유지하므로, 차감 문장을 트랜잭션 맨 끝에 두고 곧바로 커밋합니다.

**이것을 기본으로 고릅니다.** 비관적 락보다 락 구간이 짧고 낙관적 락보다 단순합니다.

**어디서 깨지는가.** 여전히 같은 행에 직렬화됩니다. 한 문장과 커밋에 5ms 가 걸리면 한 행의 상한은 초당 200건입니다.
특가 상품은 초당 500건이 몰리므로(01 규모 가정) 이 방법만으로는 줄이 길어집니다.

### 방법 3. 낙관적 락

버전 컬럼을 두고 충돌하면 예외를 던져 재시도합니다.

**어디서 깨지는가.** 충돌이 잦은 곳에서는 가장 나쁩니다. 300건이 경쟁하면 한 건만 성공하고 299건이 재시도합니다.
그 재시도가 다시 부하가 됩니다. 낙관적 락은 충돌이 드문 곳의 도구입니다.

### 방법 4. Redis 선점 후 DB 정산

Redis 에서 먼저 차감하고 DB 는 나중에 맞춥니다. 매우 빠릅니다.

**어디서 깨지는가.** Redis 차감 성공 후 DB 반영 전에 죽으면, 팔린 것으로 세어졌지만 주문이 없습니다.
쓰려면 정산과 보정 절차를 함께 만들어야 하고, 그 복잡성이 얻는 성능보다 크다고 판단했습니다.

### 상품이 여러 개인 주문

주문 하나에 상품이 평균 3개라, 예약 트랜잭션 하나가 여러 재고 행을 차감합니다. 두 가지를 정합니다.

- **잠금 순서:** 상품번호 순으로 차감합니다. {A, B} 와 {B, A} 를 담은 두 주문이 서로를 기다리는 교착이 생기지 않습니다
- **특가 행은 마지막에:** 슬롯 상품은 일반 상품을 다 차감한 뒤 마지막에 차감합니다. 특가 행을 잡고 있는 시간이 커밋까지 한 문장으로 줄어듭니다

위의 상한(초당 200건)은 한 문장 기준입니다. 여러 행을 잡는 실제 상한은 실험(작업 목록 8번)으로 확인합니다.

### 품절 캐시

재고 서비스는 판매 가능 재고가 0이 된 상품 목록을 API로 내놓습니다. 주문 서비스는 1초마다 받아 메모리에 둡니다.
주문을 저장하기 전에 이 목록을 봐서, 특가 품절 뒤의 시도가 주문 DB에 쓰지 않게 합니다(01번 "특가 시도 거르기").

## 특가 상품: 재고 슬롯 분산

> 상한을 넘는 상품만 재고를 슬롯 8개로 쪼갭니다. 슬롯별 차감 내역을 남겨 해제할 때 재고가 새지 않게 합니다.

### 몇 개로 쪼개나

특가 상품 초당 500건 ÷ 한 행 상한 200건 = 슬롯 3개가 최소입니다. 무작위 선택은 고르게 퍼지지 않아서 8개로 둡니다.
예상 초당 주문이 상한의 절반(100건)을 넘는 상품만 켭니다.

### 슬롯 모드

상품마다 `slot_mode` 를 둡니다.

| 모드 | 차감 | 해제 |
|---|---|---|
| NONE | `stock.quantity` 에서 | `stock.quantity` 로 |
| SPREAD | 무작위 슬롯에서, 모자라면 여러 슬롯에서 나눠 뺌 | 슬롯 내역대로 원래 슬롯에. 내역이 없으면 슬롯 0 에 |
| MERGED | 슬롯 0 에서만 | 모두 슬롯 0 에 |

```java
int slot = ThreadLocalRandom.current().nextInt(SLOT_COUNT);
int affected = slotMapper.decrease(productId, slot, qty);
if (affected == 0) {
    // 고른 슬롯이 비었을 뿐 전체가 품절은 아니다
    allocations = slotMapper.decreaseAcrossSlots(productId, qty);
}
```

어느 슬롯에서 몇 개를 뺐는지는 예약별 슬롯 내역(`reservation_slot`)에 남깁니다.

### 모드를 바꾸는 순간

- **켤 때 (NONE → SPREAD):** 한 트랜잭션에서 `stock` 행을 잠그고 수량을 슬롯 8개에 나눠 넣습니다
  - 같은 트랜잭션에서 `stock.quantity` 를 0 으로, 모드를 SPREAD 로 바꿉니다
  - 켜기 직전에 `stock` 차감을 기다리던 요청은 0행을 받습니다. 0행이면 모드를 다시 읽고, SPREAD 면 슬롯 경로로 한 번 더 시도합니다. 품절로 오판하지 않습니다
  - 켜기 전에 만든 예약은 슬롯 내역이 없습니다. 이런 예약을 풀면 슬롯 0 에 되돌립니다. `stock.quantity` 로 되돌리면 그 재고는 SPREAD 에서 쓰지 않아 팔리지 않습니다
- **합칠 때 (SPREAD → MERGED):** 잔량 합이 20 아래로 떨어지면 합칩니다
  - 슬롯 8개에 고르게 흩어진 잔량이 슬롯마다 2~3개, 즉 평균 주문 수량보다 작아지는 지점입니다. 이 아래에서는 빈 슬롯을 고르는 헛손질이 잦습니다
  - 그 상품의 슬롯 행 8개를 슬롯 번호 순으로 `FOR UPDATE` 로 잠근 뒤, 잔량을 슬롯 0 으로 옮기고 모드를 MERGED 로 바꿉니다
  - 잠그지 않고 합을 읽으면 읽은 직후 다른 주문이 뺀 수량을 덮어써 오버셀이 납니다. 번호 순으로 잠그는 것은 교착을 막기 위해서입니다
  - MERGED 뒤의 해제는 원래 슬롯이 아니라 슬롯 0 에 되돌립니다. 다른 슬롯에 되돌리면 그 재고는 팔리지 않습니다

### 포기하는 것

- **정확한 실시간 잔량:** 잔량이 슬롯의 합이라 상세 화면에는 "품절 임박" 같은 표시를 씁니다
- **단순한 해제:** 모드와 슬롯 내역에 따라 되돌릴 자리가 달라집니다

## 예약 후 확정

> 결제가 끝날 때까지 재고를 예약으로 잡아 둡니다. 결제 시작을 회차와 기한으로 표시해, 만료 배치와 결제가 엇갈려도 결제한 주문의 재고를 풀지 않습니다.

### 왜 즉시 차감이 아니라 예약인가

즉시 차감은 단순하지만, 결제가 실패해 되돌리다 실패하면 그 재고는 영영 돌아오지 않습니다.
재고 숫자만 줄었을 뿐 누가 왜 잡고 있는지 기록이 없어서, 나중에 찾아 돌려놓을 방법이 없습니다.
예약은 행마다 만료 시각이 있어서, 되돌리기를 놓쳐도 만료 배치가 찾아서 풉니다.

**유지 시간은 일반 10분, 특가 3분입니다.** 결제를 포기한 사용자의 예약은 만료까지 재고를 묶습니다.
특가는 재고가 적고 대기 수요가 많아 묶인 3분도 판매 손실입니다. 그래서 상품별 설정으로 짧게 둡니다.

### 예약 상태

| 상태 | 뜻 | 들어오는 길 |
|---|---|---|
| HELD | 재고를 잡았고 결제가 진행 중이 아님 | 예약 생성, 같은 회차의 결제 거절 뒤 되돌림 |
| PAYING | 결제 회차 r 의 승인 요청을 보냈거나 보내는 중. 회차와 결제 기한을 기록 | 주문 서비스가 승인 요청 직전에 표시 |
| CONFIRMED | 결제 완료로 확정 | order.events 의 PAID, 또는 만료 배치 |
| RELEASED | 만료로 판매 가능 재고에 되돌림 | 만료 배치 |
| RESTORED | 출고 불가가 아닌 취소로 되돌림 | order.events 의 CANCELLED (사유가 고객 취소나 관리자 취소) |

예약은 주문번호와 상품마다 한 행입니다. 카드 거절 후 다시 결제해도 예약을 새로 만들지 않고 같은 행을 씁니다.

### 결제 시작, 되돌림, 만료

```sql
-- 결제 시작 표시: 주문 서비스가 승인 요청 직전에 부른다
UPDATE stock_reservation
   SET status = 'PAYING', payment_round = :round, payment_deadline = NOW(3) + INTERVAL 5 SECOND
 WHERE order_no = :orderNo AND status = 'HELD' AND expires_at > NOW(3)

-- 거절 되돌림: 그 회차일 때만
UPDATE stock_reservation
   SET status = 'HELD'
 WHERE order_no = :orderNo AND status = 'PAYING' AND payment_round = :round

-- 만료: 결제가 시작되지 않은 예약
UPDATE stock_reservation
   SET status = 'RELEASED'
 WHERE reservation_id = :id AND status = 'HELD' AND expires_at <= NOW(3)
```

- **결제 시작과 만료:** 둘 다 HELD 를 조건으로 걸어, 같은 순간에 와도 하나만 성공합니다
- **결제 시작이 0행이면:** 상태를 함께 돌려줍니다. 주문 서비스는 RELEASED 일 때만 주문을 실패로 닫습니다(01번 "결제 시작 표시가 0행이면")
- **되돌림에 회차 조건:** 거절된 회차 1의 되돌림이 늦게 도착했을 때, 그사이 회차 2가 잡은 PAYING 을 HELD 로 바꾸지 않습니다
- **바뀐 행 수 확인:** 같은 주문의 예약 행은 만료 시각이 같아 함께 바뀝니다. 바뀐 행 수가 상품 수와 다르면 결제하지 않습니다

### 결제 기한

PAYING 표시와 결제 서비스의 회차 생성 사이에는 틈이 있습니다. 만료 배치가 그 틈에 결제 서비스에 물으면 "회차 없음"을 듣습니다.

| 시각 | 기한이 없을 때 |
|---|---|
| 22:59:59.990 | 결제 시작 표시 성공 (만료 23:00:00) |
| 23:00:00.020 | 만료 배치가 묻고 "회차 없음"을 들어 예약을 풂. 재고가 다시 팔림 |
| 23:00:00.060 | 늦게 도착한 승인 요청으로 회차가 열리고 승인됨 |

그래서 PAYING 에 결제 기한(표시 시각 + 5초)을 기록하고, 결제 요청에도 실어 보냅니다.

- **결제 서비스:** 기한이 지난 요청으로는 회차를 열지 않습니다
- **만료 배치:** PAYING 은 결제 기한에 서버 시계 차이 여유(5초)를 더한 시각이 지난 뒤에만 결제 상태를 묻습니다

그 시각 뒤에는 새 회차가 열릴 수 없으므로 "회차 없음"과 "FAILED"를 믿을 수 있습니다.

### 만료 배치

1분마다 돕니다. HELD 는 위 문장으로 바로 풉니다. PAYING 은 결제 기한이 지난 것만 결제 서비스에 그 회차의 상태를 묻습니다.

PAYING 이 만료 시각을 넘기는 경우는 둘입니다. 결제 결과를 아직 모르거나, 결제는 끝났는데 확정 이벤트가 밀린 경우입니다.
마감 직전에는 뒤의 경우가 실제로 생깁니다.

| 회차 r 의 결제 상태 | 만료 배치가 하는 일 |
|---|---|
| APPROVED | 풀지 않고 CONFIRMED 로 확정한다. 밀린 확정 이벤트를 대신 처리하는 셈이다 |
| FAILED, 또는 회차 없음 | `status = 'PAYING' AND payment_round = r` 조건으로 RELEASED, 재고를 되돌린다 |
| REQUESTED | 건드리지 않는다. 결제 서비스 조회 배치가 확정하면 다음 주기에 처리한다 |
| UNKNOWN | 풀지 않고 경보를 낸다. 사람이 결제를 확정하면 그 결과를 따른다 |

### 확정과 복원 소비자

| 이벤트 | 갱신 | 0행일 때 상태를 다시 읽어서 |
|---|---|---|
| PAID | PAYING → CONFIRMED | CONFIRMED 는 중복이라 넘김. RESTORED 는 먼저 온 취소라 넘김. RELEASED 나 HELD 는 경보 |
| CANCELLED (고객, 관리자) | HELD, PAYING, CONFIRMED → RESTORED, 재고 되돌림 | RESTORED 는 중복이라 넘김. RELEASED 는 이미 되돌려져 넘김 |
| CANCELLED (출고 불가) | 바꾸지 않음 | 실물이 없어서 생긴 취소라 되돌리면 없는 재고를 다시 팖 |

복원 소비자가 HELD 와 PAYING 도 받는 것은 순서가 바뀐 이벤트 때문입니다.
PAID 처리가 처리 실패 토픽으로 빠진 사이 고객 취소가 먼저 오면, 예약은 아직 PAYING 입니다. CONFIRMED 만 받으면 재고가 영영 돌아오지 않습니다.

## 판매 가능 재고와 실물 재고

> 판매는 전국 합산으로 하지만 출고는 특정 센터에서 나가므로 두 재고를 나눕니다. 실물 재고는 풀필먼트가 가집니다.

| 종류 | 무엇인가 | 주인 | 누가 바꾸는가 |
|---|---|---|---|
| **판매 가능 재고** | 지금 팔 수 있는 수량 | 재고 서비스 | 예약(차감), 만료와 취소(복원), 입고와 실사 이벤트 |
| **센터별 실물 재고** | 각 물류센터에 실제로 있는 수량 | 풀필먼트 | 입고, 출고 지시, 실사 조정 |

서울 센터에 10개, 부산 센터에 10개가 있으면 판매 가능 재고는 20입니다.
그래도 서울 고객의 주문 15건은 서울 센터만으로는 못 채웁니다. 어느 센터에서 낼지는 05번의 할당이 정합니다.

두 재고는 이벤트로 맞춥니다. 입고와 실사 차이가 생기면 풀필먼트가 실물 재고를 바꾸고 이벤트를 냅니다.
재고 서비스는 그 이벤트를 받아 판매 가능 재고를 더하거나 뺍니다. 값을 더하는 소비라 인박스로 중복을 막습니다.

**실사로 줄일 때는 0 에서 멈춥니다.** 판매 가능 재고가 이미 0 인데 실사가 -2 를 보내는 경우가 있습니다.
이미 다 팔린 뒤 실물이 모자란 것이라, 그 부족은 출고 할당에서 못 채운 주문으로 드러납니다.
그래서 판매 가능 재고는 0 아래로 내리지 않고, 요청한 조정과 실제 반영한 조정을 `stock_adjustment_log` 에 남깁니다.
이벤트를 실패시키지 않으므로 처리 실패 토픽에 쌓였다가 나중에 두 번 반영되는 일도 없습니다.

## 정리: 이 시스템의 선택

| 결정 | 선택 | 포기한 것 |
|---|---|---|
| 동시 차감 | **원자적 조건부 갱신**, 상품번호 순으로 잠그고 특가 행은 마지막 | 명시적 락의 단순함 |
| 특가 상품 | **상한을 넘는 상품만 슬롯 8개**, 모드별 해제 규칙 | 정확한 실시간 잔량, 단순한 해제 |
| 품절 뒤 시도 | **1초 품절 캐시로 주문 저장 전에 거름** | 1초 동안의 오차 |
| 차감 시점 | **예약 후 확정**, 결제 시작을 회차와 기한으로 표시 | 즉시 차감의 단순함, 만료 배치 |
| 만료 | **HELD 만 바로 풀고 PAYING 은 기한 뒤 결제 확인** | 만료 시각만 보는 단순한 배치 |
| 재고 모델 | **판매 가능 재고는 재고 서비스, 실물 재고는 풀필먼트** | 한 곳에서 보는 편의. 두 값을 이벤트로 맞춤 |
