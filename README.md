# dawn-delivery-commerce

가상의 새벽배송 커머스로 주문, 재고, 결제, 출고의 정합성 설계를 연습하고 구현하는 개인 프로젝트입니다.

> 가상 시나리오입니다. 실제 운영 서비스나 실무 성과가 아닙니다.
> 설계 판단과 그 대가를 문서로 남기고, 그 판단이 실제로 동작하는지 테스트로 확인하는 것이 목적입니다.

## 왜 만들었나

주문과 재고, 결제, 출고를 다루는 곳이면 어디서든 같은 문제를 만납니다.
동시 주문에 재고를 실제보다 많이 파는 문제, DB는 커밋됐는데 이벤트가 안 나간 문제가 대표적입니다.
결제는 됐는데 응답을 못 받은 문제도 있습니다.
이 저장소는 그 문제를 숫자로 세우고, 선택지가 어디서 깨지는지 보고, 고른 것과 포기한 것을 함께 남깁니다.

## 설계 조건

- 주문 마감 시각이 밤 11시이고, 마감 직전에 주문이 몰립니다
- 인기 상품에 주문이 쏠립니다. 재고 100개에 동시 요청이 수백 건 들어옵니다
- 마감 후 정해진 시간 안에 수십만 건의 출고 지시를 물류센터로 내려보내야 합니다
- 재고를 실제보다 많이 팔면 고객에게 취소를 알려야 해서 비용이 큽니다
- 결제는 외부 대행사를 거치고, 응답이 늦거나 유실될 수 있습니다

## 구조

```
[클라이언트] --주문서 ID--> [주문] --동기--> [재고]  예약, 결제 시작 표시
                              |    --동기--> [결제] --> [가짜 결제 대행사]
                              |
                  주문 확정 + 아웃박스 (한 트랜잭션)
                              |
   order.events -----> [재고] 예약 확정    [풀필먼트] 출고 대상 등록
   payment.events ---> [주문] 늦게 확정된 결제 반영, 환불 결과
   fulfillment.events -> [주문] 못 채운 품목의 취소와 환불, [재고] 입고와 실사 반영

   마감 후 [풀필먼트 배치]: 대상 확정 -> 할당 -> 판정 발행 -> 센터별 출고 지시 -> 결과 검증
```

사용자가 기다리는 것은 재고 예약과 결제 결과까지입니다. 그 뒤의 일은 이벤트로 흘려보냅니다.
서비스마다 DB를 따로 두고, 서비스 사이를 한 트랜잭션으로 묶지 않습니다.
대신 결과가 늦게 확정되는 상태마다 그 상태를 마무리할 주인과 기한, 경보를 하나씩 정했습니다.

## 핵심 설계 결정

| 문제 | 선택 | 포기한 것 | 설계 문서 |
|---|---|---|---|
| 동시 주문의 오버셀 | 조건부 UPDATE 한 문장으로 차감 | 명시적 락의 단순함 | [02](docs/design/02-재고-정합성.md) |
| 특가 상품 한 행에 몰림 | 한 행 상한을 넘는 상품만 슬롯 8개로 분산 | 정확한 실시간 잔량 | [02](docs/design/02-재고-정합성.md) |
| 결제와 예약 만료의 경합 | 예약을 HELD 와 PAYING 으로 나누고, PAYING 은 결제 회차를 봉인한 뒤에만 풂 | 만료 시각만 보는 단순한 배치 | [02](docs/design/02-재고-정합성.md) |
| 커밋과 발행의 불일치 | 아웃박스, 선점 후 전송하는 릴레이, 처리 실패 토픽 | 즉시 발행 | [03](docs/design/03-이벤트-전달-보장.md) |
| 결제 응답 유실 | 주문번호와 결제 회차의 멱등키, 결제 이벤트와 주문 정리 배치 | 사용자 앞에서 끝까지 확정 | [04](docs/design/04-멱등성과-실패-복구.md) |
| 주문 요청 중복 | 주문서 ID 유니크 | 클라이언트가 ID 를 들고 다니는 수고 | [01](docs/design/01-전체-설계.md) |
| 마감 경계의 늦은 이벤트 | 배치 첫 스텝에서 주문 서비스 목록과 대조 | 이벤트만 믿는 단순함 | [05](docs/design/05-풀필먼트-배치.md) |
| 마감 후 대량 출고 | 전체를 보고 한 번에 할당, 센터별로 출고 지시와 재고 차감 | 주문 시점의 즉시 확정 | [05](docs/design/05-풀필먼트-배치.md) |
| 실사 부족과 취소 복원 | 반영 못 한 부족분을 들고 있다가 복원이 먼저 갚음, 하루 한 번 재고 대사 | 0 에서 멈추고 잊는 단순함 | [02](docs/design/02-재고-정합성.md) |
| 출고 예외 | 품목을 다섯 수량으로 세고, 예외 수량만 이월하거나 취소 | 품목 하나에 상태 하나 | [05](docs/design/05-풀필먼트-배치.md) |

규모 가정은 피크 초당 200건, 특가 초당 500건, 하루 30만 주문입니다.
이 가정에서 계산한 설계 값은 [01](docs/design/01-전체-설계.md)에 있습니다.
전체 흐름과 서비스 경계는 [01 전체 설계](docs/design/01-전체-설계.md)에 있습니다.
설계 문서는 01번부터 순서대로 읽습니다. 각 문서가 앞 문서에서 남긴 문제를 이어받습니다.
"왜 더 단순한 방법을 쓰지 않았나" 같은 질문과 답은 [06 설계 판단 질문](docs/design/06-설계-판단-질문.md)에 모았습니다.

## 모듈

| 모듈 | 하는 일 | 포트 |
|---|---|---|
| `common-event` | 서비스 사이 이벤트 계약 | 없음 |
| `order-service` | 주문 상태와 환불의 주인. 정리 배치, 환불 배치 | 8081 |
| `inventory-service` | 판매 가능 재고, 슬롯, 예약, 만료 배치 | 8082 |
| `payment-service` | 결제 회차와 멱등, 미결 조회 배치, 환불, 정산 대사 | 8083 |
| `fake-pg` | 지연, 타임아웃, 응답 유실을 재현하는 가짜 결제 대행사 | 8090 |
| `fulfillment-batch` | 센터 실물 재고, 출고 대상, 할당, 출고 지시 배치 | 8084 |

상품, 회원, 알림 서비스는 이 설계의 쟁점이 아니라서 만들지 않습니다.

## 실행

Java 21과 Docker가 필요합니다.

```bash
docker compose up -d --wait        # MySQL 13306, Kafka 19092
./gradlew build
java -jar order-service/build/libs/order-service-0.0.1-SNAPSHOT.jar
```

각 서비스는 기동할 때 Flyway로 자기 DB의 테이블을 만듭니다. 상태는 `/actuator/health` 로 확인합니다.

## 진행 상태

구현 순서와 완료 조건은 [작업 목록](docs/TASKS.md)에 있습니다. 각 작업은 완료 조건을 통과하는 테스트가 있어야 끝납니다.

| 작업 | 상태 |
|---|---|
| 0. 메시징 기반 (아웃박스, 처리 실패 토픽) | 완료. 보존 정리 일부와 격리 관리 API 남음 |
| 1~3. 재고 차감, 예약, 슬롯 분산 | 완료. 재고 대사 남음 |
| 4. 결제 (회차, 봉인, 미결 조회, 환불, 정산 대사) | 완료 |
| 5. 주문 (동기 흐름, 정리 배치, 취소와 환불) | 완료 |
| 6. 풀필먼트 출고 배치 | 다음 |
| 7~8. 운영 지표, 실험 기록 | 대기 |

## 기술

Java 21, Spring Boot 4.1, Spring Batch, Spring Kafka, MySQL 8.4, Kafka 4.0(KRaft), Flyway, Testcontainers
