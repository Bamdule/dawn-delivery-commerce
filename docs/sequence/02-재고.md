## 1. 예약 확정과 복원

```mermaid
sequenceDiagram
    autonumber
    participant 카프카 as order.events
    participant 재고
    participant DB as 재고 DB

    카프카->>재고: PAID (주문번호)
    재고->>DB: PAYING 을 CONFIRMED 로
    alt 0행
        재고->>DB: 상태 다시 읽기
        alt CONFIRMED 또는 RESTORED
            Note right of 재고: 중복이거나 먼저 온 취소. 넘김
        else RELEASED 또는 HELD
            Note right of 재고: 결제한 주문에 재고가 없음. 즉시 경보
        end
    end

    카프카->>재고: CANCELLED (취소 품목과 수량)
    재고->>DB: 인박스 기록 + stock 행 잠금 + 모드에 맞는 자리로 되돌림 + 예약 취소 수량 증가 (한 트랜잭션)
    Note right of DB: 되돌리는 수량은 부족분을 먼저 갚고 남은 것만 판매 가능 재고에 더함
    opt 취소 수량이 예약 수량에 이름
        재고->>DB: RESTORED
    end
```

취소 사유(고객, 출고 불가, 관리자)와 관계없이 같은 규칙입니다. 실사로 반영하지 못한 부족분이 먼저 갚아지므로 없는 재고를 되살리지 않습니다.
예약이 아직 PAYING 이어도 복원합니다. PAID 처리가 처리 실패 토픽으로 빠진 사이 취소가 먼저 오는 경우입니다.

## 2. 결제 시작과 만료가 겹칠 때

두 갱신이 모두 `status = 'HELD'` 를 조건으로 걸어서, 같은 순간에 와도 하나만 성공합니다.

```mermaid
sequenceDiagram
    autonumber
    participant 주문
    participant 재고 as 재고 DB
    participant 만료 as 만료 배치

    Note over 재고: 예약 HELD, 만료 23:00:00.000
    par 결제 시작
        주문->>재고: HELD 를 PAYING 으로 (만료 전일 때만), 회차
    and 만료 처리
        만료->>재고: HELD 를 RELEASED 로 (만료 뒤일 때만)
    end
    alt 결제 시작이 먼저 행을 잡음
        재고-->>주문: 1행. 결제 진행
        재고-->>만료: 0행. PAYING 은 회차 봉인으로 다룸
    else 만료가 먼저 행을 잡음
        재고-->>만료: 1행. 재고 되돌림
        재고-->>주문: 0행, 현재 상태 RELEASED. 결제를 부르지 않고 주문 FAILED
    end
```

## 3. 예약 만료 배치

HELD 는 결제가 시작되지 않았다는 뜻이라 바로 풉니다. PAYING 은 그 회차를 봉인한 뒤에만 풉니다.

```mermaid
sequenceDiagram
    autonumber
    participant 만료 as 만료 배치
    participant 재고 as 재고 DB
    participant 결제

    loop 1분마다
        만료->>재고: 만료된 HELD 를 RELEASED 로 + 재고 되돌림 (예약마다 한 트랜잭션)
        만료->>재고: 만료된 PAYING 조회
        만료->>결제: 그 예약의 회차 r 봉인 요청
        alt APPROVED (봉인 실패)
            만료->>재고: PAYING 을 CONFIRMED 로 (밀린 확정 이벤트를 대신 처리)
        else 봉인됨, 또는 이미 FAILED, EXPIRED
            만료->>재고: PAYING 이고 회차 r 일 때만 RELEASED + 재고 되돌림
        else REQUESTED
            Note right of 만료: 건드리지 않음. 결제 조회 배치가 확정하면 다음 주기에 처리
        else UNKNOWN
            Note right of 만료: 풀지 않고 경보
        end
    end
```

봉인은 `(주문번호, 회차)` 유니크 자리에 EXPIRED 행을 넣는 것이라, 늦게 온 승인 요청은 그 회차를 열지 못합니다.
시간 가정 없이 먼저 커밋한 쪽만 이깁니다. 만료 5분이 지나도 남은 HELD, PAYING 은 경보를 냅니다.

## 4. 특가 상품 슬롯

한 행의 상한(초당 200건)을 넘는 상품만 재고를 슬롯 8개로 나눕니다. 모드에 따라 해제할 자리가 다릅니다.

```mermaid
sequenceDiagram
    autonumber
    participant 재고
    participant DB as 재고 DB

    Note over 재고,DB: 켜기 (NONE 에서 SPREAD)
    재고->>DB: stock 행 잠금, 100 을 슬롯 8개에 나눔, quantity 0, 모드 SPREAD (한 트랜잭션)
    Note right of DB: 켜기 직전 stock 차감을 기다리던 요청은 0행을 받고 모드를 다시 읽어 슬롯 경로로 한 번 더

    Note over 재고,DB: 예약 (5개)
    재고->>DB: 무작위 슬롯 3 에서 5개 조건부 차감
    alt 0행 (슬롯 3 잔량 2개)
        재고->>DB: 슬롯 3 에서 2개, 슬롯 7 에서 3개
    end
    재고->>DB: 예약 HELD + 슬롯 내역

    Note over 재고,DB: 합치기 (잔량 합이 20 아래)
    재고->>DB: stock 행 잠금, 슬롯 0 부터 7 까지 번호 순서로 FOR UPDATE
    재고->>DB: 잔량을 모두 슬롯 0 으로, 모드 MERGED

    Note over 재고,DB: 되돌림 (해제, 복원)
    재고->>DB: stock 행 잠금 후 모드 읽기 (모드 전환과 겹치지 않게)
    alt 모드 SPREAD 이고 슬롯 내역 있음
        재고->>DB: 내역대로 원래 슬롯에
    else 모드 SPREAD 이고 내역 없음 (켜기 전 예약)
        재고->>DB: 슬롯 0 에
    else 모드 MERGED
        재고->>DB: 모두 슬롯 0 에
    end
```

- **번호 순서로 잠그는 이유:** 두 합치기가 엇갈린 순서로 잠그면 교착이 납니다
- **되돌림도 stock 행을 잠그는 이유:** SPREAD 를 읽고 슬롯 3에 되돌리는 사이 합치기가 MERGED 로 바꾸면, 슬롯 3의 재고는 팔리지 않습니다
- **MERGED 뒤에 슬롯 0 으로 되돌리는 이유:** 합친 뒤에는 슬롯 0 에서만 팔아서, 다른 슬롯에 되돌린 재고는 팔리지 않습니다

## 5. 입고와 실사

실물 재고는 풀필먼트가 바꾸고, 판매 가능 재고는 이벤트를 받은 재고 서비스가 바꿉니다.

```mermaid
sequenceDiagram
    autonumber
    actor 센터 as 센터 담당자
    participant 풀필먼트
    participant 카프카 as Kafka
    participant 재고

    센터->>풀필먼트: 입고 30개 또는 실사 결과 (전산 10, 실제 8)
    풀필먼트->>풀필먼트: 센터 실물 재고 + 조정 이력 + 아웃박스 STOCK_CHANGED (한 트랜잭션)
    풀필먼트->>카프카: fulfillment.events STOCK_CHANGED (키 = 상품번호)
    카프카->>재고: 소비
    재고->>재고: 인박스 기록 + 판매 가능 재고 증감 (한 트랜잭션)
    opt 인박스에 이미 있음
        Note right of 재고: 중복. 아무 일도 하지 않음
    end
    opt 줄일 양이 판매 가능 재고보다 큼 (이미 다 팔린 뒤의 실사)
        재고->>재고: 0 에서 멈추고 남은 만큼을 부족분에 더함
        Note right of 재고: 뒤의 취소 복원과 입고가 부족분을 먼저 갚음
    end
```
