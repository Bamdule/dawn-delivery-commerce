# 작업 목록

설계 문서(`docs/design`)를 코드로 옮기는 순서입니다. 위에서부터 차례로 진행합니다.
각 작업은 완료 조건을 테스트로 증명해야 끝납니다. 끝나면 체크하고 커밋 해시를 적습니다.

## 0. 테스트 기반

- [ ] **통합 테스트 기반:** 서비스마다 Testcontainers로 MySQL 8.4를 띄우는 테스트 설정을 만든다. Kafka가 필요한 서비스는 Kafka 컨테이너도 띄운다
  - 완료 조건: 각 서비스의 `@SpringBootTest` 가 Flyway 마이그레이션을 적용하고 통과한다

## 1. 재고 차감 (설계 02, 선택지와 각각이 깨지는 지점)

- [ ] **갱신 유실 재현:** 조회 후 계산해서 저장하는 방식을 테스트 코드 안에만 만든다
  - 완료 조건: 재고 100, 동시 300건에서 성공 건수가 100을 넘는 것을 테스트가 보여 준다
- [ ] **조건부 차감:** `UPDATE ... WHERE quantity >= :qty` 한 문장으로 차감하고, 영향받은 행이 0이면 품절로 판정한다
  - 완료 조건: 재고 100, 동시 300건에서 정확히 100건 성공, 200건 품절, 남은 재고 0

## 2. 예약 후 확정 (설계 02, 즉시 차감이냐 예약이냐)

- [ ] **예약 API:** 판매 가능 재고를 차감하고 `HELD` 예약을 만드는 일을 한 트랜잭션으로 한다. 만료 시각은 설정값으로 둔다
- [ ] **해제 API:** 결제 실패 시 주문 서비스가 부른다. `HELD` 일 때만 풀고 재고를 되돌린다. 두 번 불러도 한 번만 되돌린다
- [ ] **확정 소비자:** `order.events` 의 `PAID` 를 받아 `HELD` 를 `CONFIRMED` 로 바꾼다
  - 0행이면 상태를 다시 읽는다. `CONFIRMED` 면 중복으로 넘기고, `RELEASED` 면 경보 로그를 남긴다
- [ ] **만료 배치:** 만료 시각이 지난 `HELD` 예약을 풀기 전에 주문 서비스에 결제 상태를 묻는다
  - 결제 없음이나 `FAILED` 는 풀고, `REQUESTED` 는 건너뛰고, `APPROVED` 는 확정한다
  - 완료 조건: 결제 승인 뒤 확정 이벤트가 늦게 오는 경우를 테스트로 만들고, 재고가 다시 팔리지 않음을 보인다

## 3. 슬롯 분산 (설계 02, 인기 상품 문제)

- [ ] **슬롯 차감:** `slot_enabled` 상품은 무작위 슬롯에서 빼고, 비었으면 다른 슬롯에서 뺀다
- [ ] **나눠 빼기와 합치기:** 주문 수량이 한 슬롯보다 크면 여러 슬롯에서 나눠 뺀다. 잔량이 임계값 아래면 슬롯을 하나로 합친다
  - 완료 조건: 슬롯 10개, 재고 100에서 동시 300건이 정확히 100건 성공한다. 남은 3개가 흩어져 있어도 3건이 모두 팔린다

## 4. 결제 (설계 04)

- [ ] **가짜 결제 대행사:** 승인 API와 조회 API를 만든다. 요청마다 지연, 타임아웃, 응답 유실(승인은 하고 응답만 안 줌)을 설정으로 고를 수 있게 한다. 멱등키 지원 여부도 설정으로 둔다
- [ ] **멱등키와 회차:** 키는 `order-{주문번호}-payment-{결제회차}` 다. 재시도는 같은 회차, 다시 결제하기는 다음 회차를 쓴다
  - 완료 조건: 응답 유실 후 재시도해도 대행사 승인은 한 번이다
- [ ] **미결 상태와 조회 배치:** 타임아웃은 `REQUESTED` 로 남긴다. 배치가 대행사에 결과를 묻고, 한도를 넘기면 `UNKNOWN` 으로 둔다
- [ ] **재시도 구분:** 잔액 부족 같은 영구 실패는 재시도하지 않는다. 5xx 같은 일시적 실패는 멱등키를 지원할 때만 지수 백오프와 지터로 재시도한다
- [ ] **회로 차단기:** 대행사 실패율이 임계값을 넘으면 호출을 멈추고 즉시 실패시킨다
- [ ] **환불:** 키는 `refund-{주문번호}-{환불시도번호}` 다
  - 완료 조건: 같은 환불 요청을 두 번 보내도 환불은 한 번이다

## 5. 주문 흐름 (설계 01, 04)

- [ ] **주문 생성:** 주문을 `PENDING` 으로 먼저 저장한다. 재고 예약과 결제는 트랜잭션 밖에서 부른다
- [ ] **주문 확정:** 결제 승인 뒤 짧은 트랜잭션으로 주문을 `PAID` 로 바꾸고 아웃박스에 `PAID` 이벤트를 쓴다
- [ ] **실패 처리:** 결제가 실패하면 예약을 풀고 주문을 `FAILED` 로 둔다. 결제가 `REQUESTED` 면 주문은 `PENDING` 으로 두고 조회 결과를 기다린다
- [ ] **결제 상태 조회 API:** 재고 서비스의 만료 배치가 쓴다
  - 완료 조건: 결제 대행사가 3초 지연할 때 DB 커넥션이 그동안 잡혀 있지 않음을 커넥션 풀 지표로 보인다

## 6. 아웃박스 릴레이 (설계 03)

- [ ] **폴링 릴레이:** 500ms마다 `PENDING` 을 읽어 발행하고 `SENT` 로 바꾼다. 여러 대가 돌아도 `FOR UPDATE SKIP LOCKED` 로 나눠 집는다
- [ ] **순서 지키기:** 같은 파티션 키에 앞선 `PENDING` 이 남아 있으면 뒤의 것을 보내지 않는다
- [ ] **정리 배치:** 보존 기간이 지난 `SENT` 를 청크로 지운다. 일반 스케줄 컴포넌트로 만든다
  - 완료 조건: 발행 직후 `SENT` 로 바꾸기 전에 릴레이를 죽이면 같은 이벤트가 다시 나가고, 받는 쪽 결과는 한 번만 반영된다

## 7. 풀필먼트 (설계 05)

- [ ] **출고 대상 등록:** `PAID` 이벤트를 받아 `shipment_target` 에 등록한다. 주문번호 기본 키라 두 번 와도 하나만 남는다
- [ ] **할당 스텝:** 마감 시각을 잡 파라미터로 받는다. 상품별, 권역별 수요 합계와 센터 재고를 모아 한 번에 배분하고 `allocation_result` 에 덮어쓴다
  - 한 센터에서 전량 출고할 수 있는지를 가장 먼저 본다
- [ ] **출고 지시 스텝:** 할당 결과를 센터별로 파티셔닝해 청크 500으로 출고 지시를 만든다. 스킵한 건은 리스너로 기록하고 임계값을 넘으면 실패시킨다
- [ ] **부족 처리:** 채울 수 없는 주문은 판정과 이유를 `unfillable_decision` 에 남기고 결제 서비스에 환불을 요청한다
  - 완료 조건: 출고 지시 스텝 중간에 실패시킨 뒤 재시작하면 남은 것만 처리되고, 출고 지시가 중복되지 않는다

## 8. 실험 기록

설계에서 예상한 것과 실제 측정을 `docs/experiments/` 에 남깁니다. 준비, 절차, 예상, 실제 순서로 씁니다.

- [ ] **동시성:** 조건부 차감, 슬롯 분산, 비관적 락을 같은 부하에서 처리량과 지연으로 비교
- [ ] **전달 보장:** 릴레이 중단과 재시작, 중복 소비와 멱등 처리 재현
- [ ] **결제 복구:** 응답 유실과 `REQUESTED` 조회, 부분 환불 멱등키 확인
- [ ] **배치:** 마감 시각 파라미터와 출고 지시 유니크 제약으로 재시작 결과 비교
