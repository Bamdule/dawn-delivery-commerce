# 05. 풀필먼트와 배치

## 요약

**무엇을 설명하나:** 밤 11시 마감 뒤 새벽 배송 전까지 수십만 건의 출고 지시를 만드는 방법을 다룹니다. 배치를 고르는 기준, Spring Batch의 청크와 재시작, 센터 할당, 재고 보정을 봅니다.

**풀필먼트 배치는 무엇에 쓰나:** 새벽배송은 마감과 배송 사이 몇 시간 안에 센터 할당부터 배차 묶기까지 끝내야 합니다. 한 건씩 처리하면 시간이 모자라고, 실패하면 어디까지 했는지 알아야 합니다.

**세 줄 요약**
1. 전체를 봐야 결정이 좋아지는 센터 할당은 이벤트가 아니라 마감 후 배치로 합니다.
2. Spring Batch는 수백 건 청크로 커밋하고, 어디까지 했는지 기록해 실패 지점부터 재시작합니다.
3. 센터 할당은 전체를 보고 한 번에 하고, 할당 뒤 스텝만 센터별로 나눠 락 경쟁을 피하고, 마감 시각을 파라미터로 받아 재실행 결과를 같게 합니다.

## 문제를 정확히 세우기

> 마감과 배송 사이 몇 시간 안에 여섯 가지 일을 끝내야 합니다. 대량 처리와 중간 실패 복구라는 두 요구가 Spring Batch를 쓰는 이유입니다.

새벽배송은 **시간 창이 좁습니다.** 밤 11시에 주문이 마감되고, 새벽에 배송이 나가야 하므로
**그 사이 몇 시간 안에 다음 일이 전부 끝나야 합니다.**

1. 마감 시점까지 결제가 끝난 주문을 출고 대상으로 묶기 (재고 예약 확정은 결제 이벤트에서 이미 끝남)
2. 주문마다 어느 센터에서 낼지 결정 (센터 할당)
3. 센터별 출고 지시 생성
4. 피킹 리스트 생성 (창고 내 동선 순서로 정렬)
5. 배차 대상 묶기
6. 채울 수 없는 주문 처리 (부분 출고, 취소, 환불)

**주문이 수십만 건이면 한 건씩 처리해서는 시간이 모자랍니다.** 그리고 **중간에 실패하면
어디까지 했는지 알아야** 처음부터 다시 하지 않을 수 있습니다.

**이 두 요구가 Spring Batch 를 쓰는 이유입니다.** 대량 처리를 청크로 나누고,
어디까지 했는지 기록해 재시작할 수 있게 하는 것이 이 프레임워크의 존재 이유입니다.

## 왜 이벤트가 아니라 배치인가

> 전체를 봐야 결정이 좋아지거나 정해진 시각에 몰아서 할 일은 배치입니다. 사건마다 즉시 반응할 일은 이벤트입니다.

03번에서 이벤트로 흘려보내기로 했는데 여기서는 배치를 씁니다. **기준이 필요합니다.**

| 성격 | 이벤트 | 배치 |
|---|---|---|
| 언제 일어나는가 | 사건이 생길 때마다 | 정해진 시각에 한꺼번에 |
| 처리 단위 | 한 건 | 수만에서 수십만 건 |
| 실패 처리 | 재시도와 처리 실패 큐 | 어디까지 했는지 기록하고 재시작 |
| 맞는 예 | 주문 확인 알림, 적립금 | 센터 할당, 출고 지시, 정산 |

**센터 할당을 이벤트로 하면 안 되는 이유가 있습니다.** 할당은 **전체를 봐야 최적이 됩니다.**
주문이 들어올 때마다 가장 가까운 센터를 골라 주면, 나중에 들어온 주문이 그 센터의 재고를
못 받아 먼 센터에서 나가거나 취소됩니다. **마감 후 전체를 한 번에 보고 배분하는 것이
훨씬 좋은 결과를 냅니다.**

**반대로 알림을 배치로 하면 안 됩니다.** 주문 확인 알림이 마감 후에 한꺼번에 가면
사용자는 결제하고 몇 시간 동안 아무 소식을 못 받습니다.

**그래서 기준은 이렇습니다. 전체를 봐야 결정이 좋아지는 것과 정해진 시각에 몰아서 해야
하는 것은 배치, 사건마다 즉시 반응해야 하는 것은 이벤트.**

## Spring Batch 로 무엇을 얻는가

> 청크 단위 커밋, 실패 지점부터의 재시작, 재시도와 스킵의 구분, 파티셔닝을 얻습니다.

### 청크 기반 처리

```java
@Bean
public Job dawnShipmentJob(JobRepository jobRepository) {
    return new JobBuilder("dawnShipmentJob", jobRepository)
        .start(allocationStep())            // 1. 전체 수요와 센터 재고를 모아 한 번에 배분 (Tasklet)
        .next(partitionedShipmentStep())    // 2. 센터별로 나눠 출고 지시와 피킹 생성 (청크)
        .build();
}

@Bean
public Step shipmentStep(JobRepository jobRepository, PlatformTransactionManager tm) {
    return new StepBuilder("shipmentStep", jobRepository)
        .<Allocation, ShipmentOrder>chunk(500, tm)
        .reader(allocationReader())          // 할당 결과를 500건씩 읽는다
        .processor(shipmentOrderBuilder())   // 출고 지시를 만든다
        .writer(shipmentOrderWriter())       // 출고 지시를 저장한다
        .faultTolerant()
        .retryLimit(3).retry(DeadlockLoserDataAccessException.class)
        .skipLimit(100).skip(InvalidShipmentException.class)
        .listener(skipListener())            // 스킵된 건을 따로 기록
        .build();
}
```

**할당과 출고 지시를 다른 스텝으로 나눈 이유가 있습니다.** 청크 스텝은 한 건씩 처리합니다.
할당을 청크로 하면 앞 주문이 가까운 센터 재고를 먼저 가져가, 주문마다 고르는 방식과 같아집니다.
그래서 할당 스텝은 마감 대상의 상품별, 권역별 수요 합계와 센터별 재고를 먼저 모두 모읍니다.
주문 단위가 아니라 합계라 메모리에 올릴 만한 크기입니다.
배분을 한 번에 계산해 할당 결과 표에 저장하고, 청크는 그 결과를 출고 지시로 만드는 뒤 스텝에서 씁니다.

**청크가 500이면 500건을 읽어 처리하고 한 트랜잭션으로 커밋합니다.** 이게 왜 중요한가.

**한 건씩 커밋하면 트랜잭션 오버헤드가 건수만큼 생깁니다.** 20만 건이면 20만 번입니다.
**반대로 전부를 한 트랜잭션으로 묶으면** 트랜잭션이 몇 시간 열려 있고, 실패하면 전부
되돌아가며, 언두 로그가 폭발합니다.

**청크는 그 사이의 타협입니다.** 500건 단위로 커밋하니 실패해도 그 청크만 되돌아갑니다.

**청크 크기를 정하는 기준**은 한 청크가 커밋되는 데 걸리는 시간입니다. 너무 크면 락을
오래 잡고 실패 시 되돌릴 양이 많아지며, 너무 작으면 오버헤드가 큽니다.
**수백 단위에서 시작해 측정하고 조정합니다.**

### 재시작

Spring Batch 는 `JobRepository` 에 **어느 스텝의 몇 번째 청크까지 성공했는지** 기록합니다.
그래서 3만 건째에서 죽으면 **다시 실행할 때 그 지점부터** 시작합니다.

**이게 없으면 처음부터 다시 해야 합니다.** 시간 창이 좁은 새벽배송에서 이건 치명적입니다.
할당 스텝은 청크가 아니라 한 번에 계산하므로 실패하면 계산을 처음부터 다시 합니다.
결과 표를 마감 회차 기준으로 덮어쓰므로 다시 해도 결과는 같습니다.

**단, 재시작이 되려면 리더가 어디까지 읽었는지 복원 가능해야 합니다.**
`JdbcPagingItemReader` 처럼 정렬 기준이 명확한 리더를 써야 하고,
**정렬 없이 읽으면 재시작 시 순서가 달라져 건너뛰거나 중복됩니다.**

### 스킵과 재시도의 구분

**04번에서 본 구분이 배치에도 그대로 적용됩니다.**

- **재시도(retry)** : 일시적 실패. 교착이나 락 대기 시간 초과는 다시 하면 됩니다
- **스킵(skip)** : 그 건이 잘못된 경우. 배송지가 없거나 데이터가 깨진 건입니다.
  **다시 해도 안 되므로 건너뛰고 따로 기록**합니다

**스킵을 조용히 넘기면 안 됩니다.** `SkipListener` 로 어느 건이 왜 스킵됐는지 남기고,
**스킵 건수가 임계값을 넘으면 실패시켜 사람이 보게** 합니다. 20만 건 중 10건 스킵은
정상 범위지만 5만 건 스킵은 데이터에 문제가 있다는 신호입니다.

### 파티셔닝

한 스레드로 20만 건을 돌리면 느립니다. 그런데 **센터 할당 스텝은 나눌 수 없습니다.** 할당 전 주문에는
아직 센터가 없고, 할당은 전체를 봐야 좋아지기 때문입니다(위 "왜 이벤트가 아니라 배치인가" 절).
그래서 할당은 한 스텝에서 한 번에 계산하고, **센터가 정해진 뒤의 출고 지시와 피킹 스텝을 센터별로 나눠 병렬로 돌립니다.**

```java
@Bean
public Step partitionedPickingStep() {
    return new StepBuilder("partitionedPicking", jobRepository)
        .partitioner("pickingStep", centerPartitioner())    // 할당이 끝난 주문을 센터별로 분할
        .step(pickingStep())
        .gridSize(8)
        .taskExecutor(taskExecutor())
        .build();
}
```

**센터를 파티션 기준으로 고른 이유가 중요합니다.** 할당이 끝난 주문을 센터별로 나누면 **각 파티션이
자기 센터의 실물 재고 행만 건드립니다.** 주문 아이디 범위로 나누면 여러 파티션이 같은 상품 재고를 동시에
갱신해 락 경쟁이 생깁니다.

**파티션 기준은 데이터가 겹치지 않게 잡는 것이 원칙입니다.** 02번의 슬롯 분산과 같은
발상입니다.

## 센터 할당 설계

> 한 센터 전량 출고를 최우선으로 두고, 채울 수 없으면 부분 출고나 취소와 환불로 넘깁니다. 환불에는 멱등키가 필요합니다.

### 무엇을 결정하는가

주문 하나에 상품이 세 개 있고, 각 상품이 어느 센터에 몇 개씩 있는지 다릅니다.
**어느 센터에서 낼지, 한 센터로 다 나갈 수 있는지, 안 되면 어떻게 할지**를 정해야 합니다.

### 우선순위

```
1. 한 센터에서 전량 출고 가능한가       -> 가장 좋다. 포장 한 번, 배송 한 번
2. 배송 권역 안의 센터인가              -> 새벽배송 시간 안에 도착 가능
3. 재고 회전이 필요한 센터인가          -> 유통기한이 짧은 상품
4. 나눠 보내야 하는가                   -> 포장과 배송이 두 번. 비용 증가
5. 채울 수 없는가                       -> 부분 출고 또는 취소
```

**1번을 최우선으로 두는 이유**는 비용입니다. 두 센터에서 나가면 상자가 두 개, 배송이
두 번입니다. **재고가 있다는 것과 한 번에 보낼 수 있다는 것은 다른 문제**입니다.

### 채울 수 없을 때

**여기가 설계에서 가장 조심할 부분입니다.** 이미 결제가 끝난 주문입니다.

```
채울 수 없음 판정
  |
  +-- 일부만 가능 -> 부분 출고 + 나머지 부분 환불
  |                   (고객에게 미리 알림. 동의 정책이 있으면 확인)
  |
  +-- 전량 불가   -> 주문 취소 + 전액 환불
                      (04번의 보상 트랜잭션)
```

**환불은 04번의 멱등키가 필요한 지점입니다.** 배치가 중간에 실패해 재시작하면
같은 주문에 환불 요청이 두 번 갈 수 있습니다. 부분 환불이 가능하므로 `refund-{주문번호}-{환불시도번호}`를 키로 씁니다. 같은 환불 시도만 같은 결과를 돌려받고, 다음 부분 환불은 별도 요청으로 처리됩니다.

**그리고 이 판정은 반드시 기록해야 합니다.** 왜 못 채웠는지(실사 차이, 입고 지연,
할당 실패)를 남기지 않으면 다음에 같은 일이 반복됩니다.

## 실사와 재고 보정

> 실사 값으로 센터 재고와 판매 가능 재고를 맞추고, 채울 수 없게 된 주문까지 정리합니다.

**전산 재고와 실물 재고는 어긋납니다.** 파손, 분실, 입고 오류로 생깁니다.

```
실사 결과 반영 배치
  |
  1. 센터별 실사 수량을 입력받는다
  2. 전산 수량과 비교해 차이를 기록한다 (조정 이력)
  3. 센터 실물 재고를 실사 값으로 맞춘다
  4. 판매 가능 재고를 다시 계산한다
  5. 이미 받은 주문 중 채울 수 없게 된 건을 찾아 위의 절차로 넘긴다
```

**5번을 빠뜨리면 안 됩니다.** 재고만 줄이고 주문을 그대로 두면 출고 단계에서 터집니다.
**보정은 재고 숫자를 고치는 일이 아니라 그 숫자에 딸린 주문까지 정리하는 일입니다.**

## 배치를 만들 때 반드시 함께 만들 것

> 배치를 만들 때 함께 챙길 여섯 가지입니다. 빈 실행 제거, 이력 정리, 정리 배치의 실행 방식, 중복 실행 방지, 예약 지연 대비, 마감 시각 파라미터가 들어갑니다.

**첫째, 할 일이 없으면 실행하지 않게 합니다.** 알림 배치가 보낼 것이 없어도 주기마다
돌면 실행 이력만 남깁니다. 대기 건을 먼저 확인하고 없으면 즉시 끝냅니다.

**둘째, 실행 이력을 지우는 주체를 함께 만듭니다.** 보존 기간을 정하고 청크로 지웁니다.

**셋째, 그 정리 배치를 Spring Batch Job 으로 만들지 않습니다.** Job 으로 만들면
**자기가 청소할 테이블에 자기 실행 이력을 남깁니다.** 일반 스케줄 컴포넌트로 만듭니다.

**넷째, 중복 실행을 막습니다.** 배치가 예정보다 오래 걸리는데 다음 실행이 시작되면
같은 데이터를 두 번 처리합니다. 실행 중 플래그나 락으로 막습니다.

**다섯째, 예약 실행의 지연을 전제로 만듭니다.** 범용 스케줄러는 예정 시각보다 늦게
실행될 수 있습니다. 밀린 실행을 따라잡는 장치와 누락 알림을 두고, 시각 정확도가 필요한
배치는 그에 맞는 스케줄러에 올립니다.

**여섯째, 마감 시각 기준을 코드에 못 박습니다.** "마감 후 주문" 을 `NOW()` 로 잡으면
배치가 늦게 돌 때마다 대상이 달라집니다. **마감 시각을 파라미터로 받아 그 시각 기준으로
조회**해야 재실행해도 대상 집합이 같습니다. 출고 지시 쪽에는 주문당 유니크 제약이나 upsert가 있어야 같은 대상을 다시 처리해도 멱등합니다.

## 정리: 이 시스템의 선택

> 일곱 가지 결정과 포기한 것을 모았습니다. 부족 처리처럼 포기할 것 없이 반드시 필요한 결정도 있습니다.

| 결정 | 선택 | 포기한 것 |
|---|---|---|
| 할당 방식 | **마감 후 전체를 보고 일괄 배분** | 주문 시점의 즉시 확정 |
| 처리 단위 | **청크 수백 건 단위 커밋** | 전체 원자성 |
| 실패 처리 | **일시적은 재시도, 잘못된 건은 스킵 후 기록** | 전부 성공 아니면 전부 실패 |
| 병렬화 | **센터별 파티셔닝** | 단일 스레드의 단순함 |
| 재시작 | **JobRepository 로 지점 복원** | 정렬 없는 자유로운 조회 |
| 배치 기준 시각 | **마감 시각을 파라미터로 받음** | `NOW()` 의 편의 |
| 부족 처리 | **부분 출고 또는 취소와 환불** | 없음. 반드시 필요합니다 |
