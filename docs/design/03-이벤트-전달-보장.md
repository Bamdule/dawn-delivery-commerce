# 03. 이벤트 전달 보장

## 요약

**무엇을 설명하나:** 주문은 커밋됐는데 이벤트가 나가지 않거나, 이벤트는 나갔는데 커밋이 롤백되는 문제를 다룹니다.
발행 쪽은 아웃박스, 받는 쪽은 조건부 갱신과 인박스, 순서는 파티션 키, 처리하지 못한 메시지는 처리 실패 토픽으로 풉니다.

**세 줄 요약**
1. DB 커밋과 Kafka 발행은 원자적이지 않으므로, 이벤트를 같은 트랜잭션의 아웃박스 테이블에 씁니다.
2. 릴레이는 행을 선점하고 커밋한 뒤 보내서, 락을 쥔 채 외부를 기다리지 않습니다. 대가로 최소 한 번 전달이 됩니다.
3. 받는 쪽은 상태 전이를 조건부로 하고, 값을 더하는 소비에만 인박스를 둡니다. 실패한 메시지는 버리지 않고 처리 실패 토픽에 남깁니다.

---

## 문제를 정확히 세우기

> 커밋 후 발행 실패와 발행 후 커밋 롤백, 두 방향의 사고가 있습니다. 2단계 커밋 대신 원자성을 포기하고 빠뜨리지 않는 것을 보장합니다.

```java
@Transactional
public void confirmOrder(String orderNo) {
    Order order = orderRepository.findByOrderNo(orderNo);
    order.markPaid();                                         // (1) DB 변경
    kafkaTemplate.send("order.events", orderNo, event);       // (2) Kafka 발행
}
```

**커밋은 됐는데 발행이 안 되는 경우.** `send` 는 메시지를 버퍼에 넣고 바로 돌아오는 비동기 호출입니다.
브로커 전송이 나중에 실패해도 메서드는 정상으로 끝나고 (1)이 커밋됩니다.
주문은 결제 완료인데 적립금도 출고 대상 등록도 일어나지 않습니다.

**발행은 됐는데 커밋이 안 되는 경우.** (2)는 메서드 안에서 실행되므로 커밋보다 먼저입니다.
메시지가 나간 뒤 커밋 단계에서 실패하면 (1)만 롤백되고, 없는 주문에 출고 대상이 생깁니다.

근본 원인은 DB 트랜잭션과 메시지 발행이 원자적이지 않다는 것입니다.

### 2단계 커밋을 쓰지 않는 이유

- **한 곳이 느려지면 전부 묶입니다.** 준비 단계에서 모든 참여자가 응답할 때까지 자원을 잡고 있습니다
- **조정자가 죽으면 애매한 상태로 남습니다.** 참여자들은 커밋할지 롤백할지 모른 채 자원을 잡고 기다립니다
- **Kafka 는 2단계 커밋 참여자로 설계된 시스템이 아닙니다**

그래서 원자성을 포기하고 최종적 일관성을 받아들입니다. 대신 빠뜨리지 않는 것과 두 번 하지 않는 것을 따로 보장합니다.

## 아웃박스 패턴

> 이벤트를 상태 변경과 같은 트랜잭션에서 아웃박스 테이블에 쓰고, 릴레이가 읽어 발행합니다.

### 쓰는 쪽

```java
@Transactional
public boolean confirmPaid(String orderNo, int paymentRound) {
    int changed = orderRepository.markPaidIfPending(orderNo, paymentRound); // WHERE status = 'PENDING'
    if (changed == 0) {
        return false;                       // 이미 다른 경로(동기 응답, 이벤트, 정리 배치)가 확정함
    }
    outboxRepository.save(OutboxEvent.of(
        EventIds.of("order", orderNo, "PAID"),  // 같은 사실에는 늘 같은 아이디
        Topics.ORDER_EVENTS, orderNo, payload(orderNo)));
    return true;
}
```

주문 상태와 이벤트 기록이 한 트랜잭션에 있으므로 함께 성공하거나 함께 실패합니다.
문제가 사라진 것이 아니라, 원자성이 필요한 두 대상을 같은 DB 안으로 옮긴 것입니다.

두 가지를 함께 지킵니다.

- **전이가 일어났을 때만 씁니다.** 결제 확정은 동기 응답, payment.events, 정리 배치 세 경로에서 올 수 있습니다. 조건부 갱신이 1행일 때만 아웃박스를 써서 PAID 이벤트는 한 번만 생깁니다
- **이벤트 아이디는 사실에서 만듭니다.** `주문, 주문번호, PAID` 로 만든 이름 기반 UUID 입니다. 무작위 UUID 면 같은 사실이 두 번 기록됐을 때 받는 쪽이 중복을 못 거릅니다

### 테이블

```sql
CREATE TABLE outbox_event (
    seq             BIGINT       NOT NULL AUTO_INCREMENT,  -- 같은 키 안의 발행 순서
    event_id        CHAR(36)     NOT NULL,
    topic           VARCHAR(100) NOT NULL,
    partition_key   VARCHAR(100) NOT NULL,
    payload         JSON         NOT NULL,
    status          VARCHAR(20)  NOT NULL,                 -- PENDING / SENT
    attempt_count   INT          NOT NULL DEFAULT 0,
    next_attempt_at DATETIME(3)  NOT NULL,
    created_at      DATETIME(3)  NOT NULL,
    sent_at         DATETIME(3)  NULL,
    PRIMARY KEY (seq),
    UNIQUE KEY uk_outbox_event_id (event_id),
    KEY idx_outbox_status_next (status, next_attempt_at),
    KEY idx_outbox_key_status (partition_key, status, seq)
);
```

상태는 PENDING 과 SENT 둘뿐입니다. 포기하고 버리는 FAILED 상태를 두지 않습니다.
버리면 그 이벤트가 사라지고, 같은 키의 뒤 이벤트가 앞질러 나가 순서가 깨지기 때문입니다.

### 릴레이

**락을 쥔 채 Kafka 를 기다리지 않습니다.** 01번 규칙 1(트랜잭션 안에서 외부 호출 금지)을 릴레이에도 적용합니다.
한 바퀴를 세 단계로 나눕니다.

```sql
-- 1. 선점: 짧은 트랜잭션. 다른 릴레이가 잡은 행은 건너뛴다
SELECT seq FROM outbox_event o
 WHERE o.status = 'PENDING' AND o.next_attempt_at <= NOW(3)
   AND NOT EXISTS (SELECT 1 FROM outbox_event p
                    WHERE p.partition_key = o.partition_key
                      AND p.status = 'PENDING' AND p.seq < o.seq)
 ORDER BY o.seq
 LIMIT 500
 FOR UPDATE SKIP LOCKED;

UPDATE outbox_event SET next_attempt_at = NOW(3) + INTERVAL 30 SECOND WHERE seq IN (:claimed);
COMMIT;
```

2. **전송:** 선점한 행을 모두 비동기로 보내고, 응답을 한꺼번에 기다립니다
3. **기록:** 짧은 트랜잭션으로 성공한 행은 SENT, 실패한 행은 다음 시도 시각을 정합니다

- **선점의 뜻:** 다음 시도 시각을 30초 뒤로 미뤄, 다른 릴레이가 같은 행을 집지 않게 합니다. 릴레이가 2단계에서 죽으면 30초 뒤 다시 집힙니다
- **순서:** 같은 키에 앞선 PENDING 이 남아 있으면 뒤의 것을 집지 않습니다. 앞선 것이 실패해 다시 시도를 기다려도 마찬가지입니다
- **실패 간격:** 1초부터 두 배씩 늘려 최대 60초, 무작위 지터를 더합니다. 10번 넘게 실패하면 경보를 내고 계속 시도합니다
- **프로듀서 설정:** `acks=all` 과 멱등 프로듀서를 켭니다. 브로커 재전송으로 파티션 안의 순서가 바뀌지 않습니다
- **전송 제한 시간은 선점보다 짧게:** `delivery.timeout.ms` 20초, `max.block.ms` 5초로 둡니다. 둘을 더해도 선점 30초 안이라, 선점이 끝나기 전에 전송 결과가 정해집니다
- **기록은 내 선점일 때만:** 3단계의 갱신은 `next_attempt_at = 내가 선점하며 쓴 값` 을 조건으로 겁니다. 선점이 끝나 다른 릴레이가 다시 집은 행을 늦게 덮어쓰지 않습니다

**키 단위 순서의 조건.** `seq` 순서가 커밋 순서와 같아야 "앞선 PENDING" 판단이 맞습니다.
앞 번호가 아직 커밋되지 않아 보이지 않으면, 뒤 번호가 먼저 집혀 나갈 수 있습니다.
그래서 같은 키의 이벤트를 쓰는 트랜잭션은 같은 행을 잠그게 합니다. 그러면 키 안에서는 한 번에 하나만 커밋됩니다.

| 서비스 | 이벤트 키 | 함께 잠그는 행 |
|---|---|---|
| 주문 | 주문번호 | 그 주문 행. 모든 주문 이벤트가 주문 상태를 바꾸므로 이미 잠김 |
| 결제 | 주문번호 | 그 주문의 회차 1 행. 회차, 환불 이벤트를 쓸 때 먼저 잠금 |
| 풀필먼트 | 주문번호 (UNFILLABLE), 상품번호 (STOCK_CHANGED) | 판정 행, 또는 그 상품의 첫 센터 실물 재고 행 |

STOCK_CHANGED 는 받는 쪽의 부족분 규칙(02번) 덕분에 순서가 바뀌어도 결과가 같습니다. 그래도 같은 규칙으로 맞춰 둡니다.

**처리량.** 선점 조회 약 10ms, 500건 비동기 전송 약 50ms, 기록 약 20ms 로 한 바퀴가 100ms 안팎입니다.
200ms 주기면 릴레이 한 대의 상한은 초당 2,500건입니다. 피크 이벤트는 서비스마다 초당 200건 정도라 10배 넘게 남습니다.

**최소 한 번 전달이 됩니다.** 2단계에서 보낸 뒤 3단계 기록 전에 죽으면 30초 뒤 같은 이벤트가 다시 나갑니다.
이건 버그가 아니라 이 구조의 성질이고, 받는 쪽에서 막습니다.

### 폴링이냐 CDC냐

| 방식 | 장점 | 단점 |
|---|---|---|
| **폴링** | 단순하고 의존성이 없음 | 지연이 폴링 주기만큼, 조회 부하 |
| **CDC** (트랜잭션 로그를 읽는 방식) | 지연이 짧고 조회 부하 없음 | 커넥터와 인프라를 따로 운영 |

폴링으로 시작합니다. 위 계산대로 피크의 10배를 감당하고, 운영할 것이 늘지 않습니다.
피크 이벤트가 초당 2,000건을 넘거나, 발행 지연 목표가 100ms 아래로 내려가면 CDC 로 옮깁니다.

### 보존과 정리

| 대상 | 보존 | 이유 |
|---|---|---|
| 아웃박스 SENT | 7일 | 장애 조사와 재발행 근거 |
| 처리 실패 토픽 | 14일 | 원인을 고쳐 다시 넣을 시간 |
| 인박스 | 30일 | 처리 실패 토픽에서 늦게 다시 들어온 중복까지 걸러야 함 |
| 끝난 예약 (CONFIRMED, RELEASED, RESTORED) | 30일 | 확정과 복원 소비자가 다시 읽을 수 있는 기간 |
| 출고 대상, 할당 결과, 출고 지시 | 90일 | 회차 조사와 반품 처리 근거 |
| Spring Batch 메타 테이블 | 90일 | 재시작 근거. 지우는 작업은 일반 스케줄 컴포넌트로 |

지우는 작업은 청크로 나눠 하고, 일반 스케줄 컴포넌트로 만듭니다. 큰 DELETE 한 번은 락과 복제 지연을 만듭니다.

## 받는 쪽의 멱등

> 상태를 바꾸는 소비는 조건부 갱신으로, 값을 더하는 소비는 인박스로 중복을 막습니다.

### 조건부 갱신으로 충분한 소비

| 소비 | 조건 | 두 번째 소비 |
|---|---|---|
| 재고: PAID 로 예약 확정 | `status = 'PAYING'` | 0행. 상태를 다시 읽어 판단 (02번 "확정 소비자") |
| 풀필먼트: PAID 로 출고 대상 등록 | 주문번호 기본 키, 없을 때만 삽입 | 아무 일 없음 |
| 주문: APPROVED 로 주문 확정 | `status = 'PENDING'` | 0행. 주문이 쓰지 않은 회차면 환불 요청 (04번) |
| 주문: REFUNDED 로 환불 완료 | `status IN ('ACCEPTED', 'FAILED')` | 0행. 누적액은 1행일 때만 더함 |

### 인박스가 필요한 소비

값을 더하는 일은 두 번 하면 결과가 달라집니다. 회원 적립금, 취소 수량의 복원, 입고와 실사로 판매 가능 재고를 바꾸는 일이 그렇습니다.

```java
@Transactional
public void handle(StockReceivedEvent event) {
    if (!inboxRepository.insertIfAbsent(event.eventId(), CONSUMER_NAME)) {
        return;                                   // 이미 처리한 이벤트
    }
    stockRepository.increase(event.productId(), event.quantity());
}
```

인박스 기록과 실제 처리는 같은 트랜잭션에 둡니다. 따로 두면 기록만 되고 처리가 빠지거나 그 반대가 됩니다.
키는 (컨슈머, 이벤트 아이디)입니다. 같은 이벤트를 여러 서비스가 각자 처리하기 때문입니다.

**알림 발송은 인박스로도 완전히 막히지 않습니다.** 알림은 외부로 나가서 DB 트랜잭션에 묶이지 않습니다.
그래서 이벤트 아이디를 발송 대행사의 중복 방지 키로 넘깁니다.

## 처리하지 못한 메시지

> 재시도해도 실패하는 메시지는 처리 실패 토픽에 남기고 경보를 냅니다. 로그만 남기고 넘어가면 그 주문은 조용히 사라집니다.

Spring Kafka 의 기본 오류 처리기는 재시도를 다 쓰면 로그만 남기고 다음 메시지로 넘어갑니다.
PAID 메시지의 형식이 깨져 풀필먼트가 처리하지 못하면, 그 주문은 출고 대상에 영영 오르지 않습니다.

- **재시도:** 1초, 2초, 4초 간격으로 세 번 다시 시도합니다
- **처리 실패 토픽:** 그래도 실패하면 `{토픽}.DLT` 로 같은 키와 함께 보냅니다. 1건이라도 쌓이면 경보입니다
- **다시 넣기:** 원인을 고친 뒤 관리 명령으로 원래 토픽에 다시 넣습니다. 받는 쪽이 멱등이라 다시 넣어도 안전합니다

한 메시지가 처리 실패 토픽으로 빠지면, 같은 키의 뒤 메시지(예: CANCELLED)가 먼저 처리됩니다.
그래서 받는 쪽은 순서가 바뀌어 와도 망가지지 않게 만듭니다.
풀필먼트는 출고 대상에 없는 주문의 CANCELLED 를 받으면 취소 표시 행을 남기고, 뒤늦은 PAID 가 그 행을 되살리지 않습니다.
마감 시각의 출고 대상 대조(05번)가 빠진 PAID 를 한 번 더 잡습니다.

## Kafka 파티션과 순서

> Kafka 는 파티션 안에서만 순서를 보장하므로 주문번호를 키로 씁니다. 파티션은 12개로 시작합니다.

```java
kafkaTemplate.send(Topics.ORDER_EVENTS, orderNo, payload); // 같은 주문은 같은 파티션
```

같은 주문의 PAID 와 CANCELLED 는 같은 파티션에 들어가 순서대로 처리됩니다.

**상품번호를 키로 쓰지 않습니다.** 특가 상품 이벤트가 한 파티션에 몰려, 02번에서 피한 핫키 문제가 Kafka 에서 다시 생깁니다.

**파티션 수는 12입니다.** 컨슈머 하나가 건당 10ms, 초당 100건을 처리한다고 보면 피크 초당 200건에 2개가 필요합니다.
파티션은 늘리면 키가 가는 파티션이 바뀌어 같은 키의 순서가 잠시 깨집니다. 그래서 처음부터 6배 여유를 둡니다.
너무 많으면 리밸런싱이 오래 걸리고 브로커 자원을 씁니다.

**오프셋은 처리가 끝난 뒤 커밋합니다.** Spring Kafka 의 기본 확인 방식이 그렇습니다.
리스너가 묶음 처리를 마친 뒤 컨테이너가 커밋합니다. 커밋 전에 죽으면 다시 소비하고, 중복은 위의 장치가 막습니다.
처리를 다른 스레드로 넘기면 처리 전에 커밋될 수 있어서, 리스너 스레드 안에서 처리를 끝냅니다.

**정확히 한 번을 전달로 보장하지 않고 처리로 보장합니다.**
