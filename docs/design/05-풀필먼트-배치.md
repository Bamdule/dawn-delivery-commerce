# 05. 풀필먼트와 배치

## 요약

**무엇을 설명하나:** 밤 11시 마감 뒤 01시까지 약 30만 주문의 출고 지시를 만드는 방법입니다.
마감 경계의 규칙, 출고 대상 대조, 할당 계산, 센터별 출고 지시, 못 채운 품목과 예외 처리를 다룹니다.

**세 줄 요약**
1. 마감 회차는 주문이 PAID 로 커밋된 시각으로 정하고, 배치 첫 스텝에서 주문 서비스 목록과 대조해 빠진 주문을 채웁니다.
2. 품목의 상태는 수량으로 셉니다. 대기, 출고, 못 채움, 예외, 취소 수량의 합이 늘 주문 수량과 같습니다.
3. 할당은 고정한 스냅샷으로 계산만 하고, 품목 수량을 옮기는 일은 판정 발행과 출고 지시 스텝에서만 합니다.

---

## 시간 창과 스텝

01번 규모 가정 기준으로 23:00 마감, 23:10 시작, 01:00 완료, 02:00 배차입니다.

| 스텝 | 하는 일 | 끝나면 회차 상태 | 예상 시간 |
|---|---|---|---|
| 1. 대상 확정 | 주문 서비스의 결제 완료 목록과 출고 대상을 대조 | TARGET_FIXED | 2분 |
| 2. 할당 | 재고 스냅샷을 고정하고, 품목마다 센터와 수량을 계산하고, 못 채운 수량을 판정 | ALLOCATED | 계산 1분, 저장 3분 |
| 3. 판정 발행 | 못 채운 수량을 품목에 반영하고 UNFILLABLE 이벤트를 씀 | UNFILLABLE_PUBLISHED | 1분 |
| 4. 출고 지시 | 센터별로 출고 지시를 만들고 실물 재고 차감 | SHIPMENT_CREATED | 고르면 5분, 한 센터에 절반이 몰리면 11분 |
| 5. 결과 검증 | 수량 합계와 예외 비율 확인 | VERIFIED 또는 VERIFY_FAILED | 1분 |

20분 안팎이면 끝나는 일을 1시간 50분 창에 둡니다. 중간에 실패해 몇 번 재시작해도 01시 안에 끝납니다.
피킹 리스트와 배차는 VERIFIED 회차만 넘겨받는 다음 단계라 이 설계에서는 다루지 않습니다.

**왜 이벤트가 아니라 배치인가.** 할당은 전체를 봐야 좋아집니다.
주문마다 그때그때 가까운 센터를 고르면, 나중 주문이 그 센터 재고를 못 받아 먼 센터에서 나가거나 취소됩니다.
반대로 주문 확인 알림은 사건마다 바로 가야 해서 이벤트입니다.

## 마감 경계의 규칙

> 어느 주문이 어느 마감 회차에 속하는지와 마감 뒤에 바뀔 수 있는 것을 먼저 고정합니다.

- **회차 기준 시각:** 주문 서비스가 주문을 PAID 로 커밋한 시각(`paid_at`)입니다. 모든 서비스가 주문 DB 의 한 시계를 보게 하려는 것입니다
- **회차:** `paid_at` 이 전 회차 마감 뒤이고 이번 마감 이하인 주문입니다
- **결제 확인이 늦어진 주문:** 22:59 에 결제했지만 확인이 23:03 에 끝나 그때 PAID 가 된 주문은 다음 회차입니다. 주문 서비스가 배송일 변경을 알립니다
- **고객 취소:** 주문이 속한 회차의 마감 전까지만 받습니다. 마감 뒤에는 출고 후 반품으로 처리합니다
- **마감 뒤의 변경:** 출고 예외를 사람이 처리하는 두 경로(이월, 관리자 취소)뿐입니다. 둘 다 풀필먼트가 받습니다(아래 "출고 예외")

### 품목의 수량 상태

한 품목이 여러 센터로 나뉘어 일부는 출고되고 일부는 예외가 될 수 있습니다. 그래서 품목에 상태 하나를 두지 않고 수량을 나눠 셉니다.

| 수량 | 뜻 | 늘어나는 때 |
|---|---|---|
| 대기 | 다음 할당을 기다림. 할당의 입력은 이 수량뿐 | 출고 대상 등록, 예외 이월 |
| 출고 | 출고 지시가 만들어짐 | 출고 지시 스텝 |
| 못 채움 | 못 채운 것으로 판정됨 | 판정 발행 스텝 |
| 예외 | 출고 지시를 만들지 못함. 사람이 처리 | 출고 지시 스텝 |
| 취소 | 취소됨 | 고객 취소, 관리자 취소 |

다섯 수량의 합은 늘 주문 수량과 같습니다. 모든 이동은 `대기 >= n` 같은 조건을 건 갱신이라 한 수량이 음수가 되지 않습니다.
예를 들어 상품 P 3개가 서울 2개, 김포 1개로 나뉘고 김포만 예외가 되면 출고 2, 예외 1 입니다. 이월하면 예외 1만 대기로 돌아갑니다.

## 1. 대상 확정

> 출고 대상은 PAID 이벤트로 미리 쌓아 두고, 마감에 주문 서비스 목록과 대조해 확정합니다. 이벤트가 밀리거나 처리 실패 토픽으로 빠진 주문도 여기서 잡힙니다.

출고 대상은 평소에는 order.events 의 PAID 를 받아 `shipment_target` 에 쌓습니다. 마감에 한꺼번에 읽지 않으려는 것입니다.
그런데 이벤트는 늦을 수 있습니다. 22:59:58 에 PAID 가 된 주문의 이벤트가 23:03 에 도착할 수 있습니다.
배치가 23:00 에 바로 시작하면 그 주문이 빠지고, 같은 마감 시각의 잡은 이미 완료라 다시 돌릴 수 없습니다.

그래서 첫 스텝에서 원천과 대조합니다.

1. 주문 서비스에 이번 회차의 PAID 주문번호 목록을 받습니다. 30만 건 × 20바이트로 약 6MB 라 페이지로 나눠 받습니다
2. `shipment_target` 과 비교해 없는 주문은 주문 서비스에서 상세(배송지 권역, 품목)를 받아 넣습니다
3. 목록 주문의 대기 수량과 앞 회차에서 이월된 대기 수량에 이번 회차를 기록합니다
4. 이번 회차 범위의 `paid_at` 인데 목록에 없는 대상(마감 전에 취소됨)은 취소로 표시합니다
5. 목록의 주문 수와 이번 회차에 오른 주문 수(이월만 있는 주문 제외)가 같으면 TARGET_FIXED 로 기록합니다
6. 다르면 1분 뒤 다시 대조하고, 세 번 다르면 스텝을 실패시키고 경보를 냅니다

대조 뒤에 늦게 도착한 PAID 이벤트는 이미 있는 행이라 아무 일도 하지 않습니다.

## 2. 할당

> 고정한 입력으로 계산만 합니다. 품목 수량은 건드리지 않으므로, 저장 중에 실패하면 결과를 지우고 다시 계산하면 됩니다.

### 입력을 고정합니다

할당 중에도 입고와 실사는 센터 실물 재고를 바꿉니다. 다시 계산할 때 입력이 바뀌면 결과도 바뀝니다.
그래서 할당을 시작할 때 센터 실물 재고를 `allocation_stock_snapshot` 에 회차별로 복사합니다. 이미 있으면 복사하지 않습니다.
할당 입력의 품목 수량 합도 이때 회차 행에 한 번만 적습니다. 결과 검증이 이 값을 씁니다.

### 할당은 품목 수량을 바꾸지 않습니다

할당 스텝은 할당 결과 표와 판정 표에만 씁니다. 품목의 대기 수량을 못 채움으로 옮기는 일은 3번 스텝이 합니다.
할당이 품목 수량까지 바꾸면, 재시작 때 판정만 지워지고 수량은 옮겨진 채 남아 그 품목이 입력에서 빠집니다.
그러면 판정이 다시 생기지 않아 환불도 재고 복원도 일어나지 않습니다.

### 입력

- 이번 회차에 배정된 대기 수량. 약 30만 주문 × 평균 3품목 = 90만 줄, 한 줄 100바이트로 약 90MB 입니다
- 센터 4곳의 재고 스냅샷. 상품 수천 개 × 4로 작습니다

### 계산

주문은 `paid_at`, 주문번호 순으로 처리합니다. 먼저 결제한 주문이 먼저이고, 같은 입력이면 결과가 늘 같습니다.

1. **1차:** 권역 안의 한 센터에서 전량 나갈 수 있는 주문만 배정합니다. 상자 하나, 배송 한 번이라 가장 싸기 때문입니다
2. **2차:** 남은 주문을 권역 안 여러 센터로 나눠 배정합니다. 한 품목의 수량이 센터 둘로 갈릴 수 있습니다
3. **3차:** 그래도 남으면 새벽 도착이 가능한 권역 밖 센터에서 채웁니다
4. **판정:** 배정하지 못한 수량을 품목마다 못 채움으로 판정합니다

주문마다 바로 고르는 방식과 다른 점은 1차입니다.
나눠 보내야 하는 주문이 한 센터에서 끝낼 수 있는 주문의 재고를 먼저 가져가지 않습니다.

### 저장과 재시작

- 할당 결과(주문, 상품, 센터, 수량)와 판정(주문, 상품, 수량)은 1,000행씩 나눠 커밋합니다
- 다 쓰면 회차를 ALLOCATED 로 기록합니다
- 재시작했을 때 ALLOCATED 가 아니면 그 회차의 결과와 판정을 청크로 지우고 같은 스냅샷으로 다시 계산합니다

## 3. 판정 발행

판정을 주문 단위로 묶어 읽고, 주문마다 한 트랜잭션에서 두 가지를 합니다.

- 품목의 대기 수량을 판정 수량만큼 못 채움으로 옮깁니다
- 풀필먼트 아웃박스에 UNFILLABLE 이벤트 하나를 씁니다. 그 주문의 못 채운 품목과 수량을 모두 싣습니다

이벤트 아이디는 (주문번호, 마감 시각)에서 만들고 아웃박스의 이벤트 아이디는 유니크입니다.
다시 돌아도 이미 쓴 주문은 유니크 위반으로 트랜잭션 전체가 되돌아가, 수량을 두 번 옮기지 않습니다.

## 4. 출고 지시

> 센터별로 나눠 병렬로 만들고, 출고 지시와 실물 재고 차감과 품목 수량 이동을 같은 트랜잭션에 둡니다.

```java
@Bean
public Job dawnShipmentJob(JobRepository jobRepository) {
    return new JobBuilder("dawnShipmentJob", jobRepository)
        .start(targetFixStep())              // 1. 대상 확정
        .next(allocationStep())              // 2. 할당 (Tasklet)
        .next(unfillablePublishStep())       // 3. 판정 발행
        .next(partitionedShipmentStep())     // 4. 센터별 출고 지시 (청크)
        .next(verificationStep())            // 5. 결과 검증
        .build();
}

@Bean
public Step shipmentStep(JobRepository jobRepository, PlatformTransactionManager transactionManager) {
    return new StepBuilder("shipmentStep", jobRepository)
        .<ShipmentDraft, ShipmentDraft>chunk(500, transactionManager)
        .reader(centerShipmentReader())        // 한 센터의 할당 결과를 주문 단위로 묶어 읽는다
        .writer(shipmentWriter())              // 출고 지시, 실물 재고 차감, 품목 수량 이동을 한 트랜잭션에
        .faultTolerant()
        .retryLimit(3).retry(DeadlockLoserDataAccessException.class)
        .skipLimit(1_000).skip(InvalidShipmentException.class)
        .listener(shipmentExceptionRecorder())  // 스킵한 (센터, 주문)을 출고 예외로 남긴다
        .build();
}
```

- **처리 단위:** (센터, 주문) 하나가 출고 지시 하나입니다. 리더가 할당 결과를 주문 단위로 묶어 읽습니다
- **한 트랜잭션:** 출고 지시와 품목 삽입, 그 센터의 실물 재고 조건부 차감, 품목의 대기 수량을 출고 수량으로 옮기는 일을 함께 합니다
- **예외:** 차감이 0행이거나 주소가 잘못되면 그 (센터, 주문)은 출고 예외입니다. 예외 기록과 대기 수량을 예외 수량으로 옮기는 일은 별도 트랜잭션에서 함께 합니다
- **재시작:** 출고 지시와 출고 예외는 모두 (마감 시각, 주문, 센터) 유니크입니다. 이미 있으면 삽입도 차감도 수량 이동도 하지 않습니다
- **정렬:** 리더는 주문번호 순으로 읽습니다. 정렬이 없으면 재시작 때 건너뛰거나 겹칩니다

### 왜 센터별로 나누나

센터 4곳이라 파티션 4개입니다. 각 파티션은 자기 센터의 `center_stock` 행만 차감합니다.
주문번호 범위로 나누면 여러 파티션이 같은 센터, 같은 상품 행을 동시에 차감해 락을 기다립니다.
한 품목이 두 센터로 나뉘면 두 파티션이 같은 품목 행의 수량을 옮깁니다. 서로 다른 수량을 조건부로 옮기는 짧은 갱신이라 정합은 지켜집니다.

처리량은 이렇게 셉니다. 출고 지시 약 32만 건을 청크 500으로 나누면 청크 640개이고, 청크 하나에 2초를 잡습니다.
고르게 나뉘면 파티션당 청크 160개로 약 5분, 한 센터에 절반이 몰리면 그 파티션이 청크 320개로 약 11분입니다.

### 청크 크기

청크 500은 커밋 한 번에 출고 지시 500건, 품목 약 1,500줄, 재고 갱신 약 1,500번입니다. 1~2초로 예상합니다.
너무 크면 락을 오래 잡고 실패할 때 되돌릴 양이 많고, 너무 작으면 커밋이 잦아집니다. 실험으로 조정합니다.

## 5. 결과 검증과 예외

> 못 채운 품목은 주문 서비스가 환불까지 책임지고, 데이터가 잘못된 품목은 사람이 처리합니다. 사람이 처리하는 입구는 풀필먼트 하나입니다.

### 못 채운 품목

UNFILLABLE 이벤트를 받은 주문 서비스는 그 품목 수량을 취소하고 품목 금액만큼 환불을 요청합니다.
모든 품목이 취소되면 주문은 CANCELLED, 아니면 PAID 로 남습니다. 주문 서비스가 내는 CANCELLED 로 재고 서비스가 판매 가능 재고를 되돌립니다.
환불 키는 `refund-{주문번호}-cutoff-{마감일시}` 입니다. 이벤트가 두 번 와도 환불 요청은 하나입니다(04번).

못 채운 품목도 판매 가능 재고로 되돌립니다. 실사 차이로 실물이 없어 생긴 것이라도, 그 차이는 실사 때 부족분으로 남아 있습니다.
되돌린 수량이 부족분을 먼저 갚으므로 없는 재고를 다시 팔지 않습니다(02번 "취소 복원과 부족분").

### 출고 예외

출고 예외는 (마감 시각, 주문, 센터) 하나이고, 그 출고 지시에 들어갈 품목과 수량을 기록합니다. 1건이라도 있으면 경보입니다.
결제가 끝난 주문이라 자동으로 환불하지 않고, 사람이 풀필먼트 관리 API로 예외 하나마다 둘 중 하나를 고릅니다.

| 처리 | 하는 일 |
|---|---|
| 이월 | 예외 상태를 OPEN 에서 DEFERRED 로. 같은 트랜잭션에서 예외 수량을 대기 수량으로 옮기고 다음 회차에 배정 |
| 관리자 취소 | 예외 상태를 OPEN 에서 CANCELLED 로. 같은 트랜잭션에서 예외 수량을 취소 수량으로 옮기고 아웃박스에 EXCEPTION_CANCELLED 를 씀 |

두 처리 모두 `status = 'OPEN'` 조건부 갱신이 1행일 때만 일어납니다. 한 예외를 두 사람이 이월하고 또 취소해도 한쪽만 이깁니다.
주문 서비스는 EXCEPTION_CANCELLED 를 받아 그 품목 수량을 취소하고 `refund-{주문번호}-admin-{예외 번호}` 로 환불합니다.
주문 서비스에 따로 관리자 취소 입구를 두지 않는 이유는, 이월 여부와 출고 여부를 아는 쪽이 풀필먼트이기 때문입니다.

주문 서비스가 품목 취소로 내는 CANCELLED 는 풀필먼트도 받습니다. 사유가 고객 취소일 때만 대기 수량을 취소 수량으로 옮깁니다.
출고 불가와 관리자 취소는 풀필먼트가 이미 수량을 옮긴 뒤라 넘깁니다.

**예외 임계값은 잡 전체로 셉니다.** 스킵 한도는 파티션 스텝마다 따로 세서, 센터 4곳이면 실제 한도가 4배가 됩니다.
그래서 스텝 한도는 넉넉히 두고, 5번 결과 검증 스텝에서 회차 전체의 예외 수량을 셉니다.

### 결과 검증

배치 중에 사람이 예외를 이월하거나 취소해도 바뀌지 않는 기록으로만, 수량으로 셉니다.

| 확인 | 기준 |
|---|---|
| 입력 = 결과 + 판정 | 회차 행에 적어 둔 할당 입력 수량 = 할당 결과 수량 합 + 판정 수량 합 |
| 결과 = 출고 + 예외 | 할당 결과 수량 합 = 출고 지시 품목 수량 합 + 출고 예외 품목 수량 합 |
| 예외 비율 | 출고 예외 수량이 할당 입력 수량의 0.1% 이하 |

통과하면 VERIFIED 로 기록하고 배차 단계가 이 회차를 가져갑니다.
넘으면 VERIFY_FAILED 로 기록하고 경보를 냅니다. 다시 돌려도 같은 판정이 나오므로 자동으로 재실행하지 않습니다.
사람이 원인을 고친 뒤 관리 API로 회차를 승인합니다. 승인 전에는 배차로 넘기지 않습니다.
이미 만든 출고 지시를 되돌리는 경로는 두지 않습니다. 배차 전에 고칠 일은 예외 처리로 하고, 이미 나간 출고 지시는 반품으로 다룹니다.

## 실사와 입고

> 실물 재고는 풀필먼트가 바꾸고, 판매 가능 재고는 이벤트를 받은 재고 서비스가 바꿉니다.

- **입고:** 센터 실물 재고를 늘리고, 조정 이력과 아웃박스 STOCK_CHANGED 를 한 트랜잭션에 씁니다. 재고 서비스가 판매 가능 재고를 늘립니다
- **실사 차이:** 센 수량을 그대로 덮어쓰지 않고 차이를 셉니다

```
차이 = 센 수량 - (전산 실물 재고 + 출고 지시는 됐지만 아직 피킹되지 않은 수량)
```

출고 지시는 전산 재고를 먼저 빼지만 선반의 물건은 피킹 때 빠집니다. 그 사이에 센 수량에는 지시된 물건이 섞여 있습니다.

| 시각 | 덮어쓰면 | 차이로 계산하면 |
|---|---|---|
| 23:35 | 출고 지시 4개, 전산 10 에서 6, 선반 10 | 같음 |
| 01:00 | 실사 10개를 세어 전산을 10으로. 판매 가능 재고도 +4 | 차이 = 10 - (6 + 4) = 0. 아무것도 바꾸지 않음 |
| 02:30 | 피킹 뒤 선반 6, 전산 10. 없는 4개를 다음 날 팖 | 선반 6, 전산 6 |

차이가 0이 아니면 실물 재고에 더하고, 같은 트랜잭션에 조정 이력과 아웃박스 STOCK_CHANGED 를 씁니다.
전산 실물 재고를 읽은 뒤 바뀌었을 수 있으므로, 읽은 갱신 시각을 조건으로 건 갱신이 0행이면 다시 셉니다.

- **이미 받은 주문:** 따로 찾지 않습니다. 다음 할당이 줄어든 재고로 계산하므로, 채울 수 없게 된 수량은 할당에서 판정됩니다
- **배치 중의 변경:** 할당은 스냅샷을 쓰고, 출고 지시는 실물 재고를 조건부로 차감합니다. 스냅샷 뒤에 줄어든 재고는 출고 예외로 드러납니다

## 배치를 만들 때 함께 만들 것

- **중복 실행 방지:** 같은 마감 시각 파라미터의 잡은 Spring Batch 가 한 번만 실행합니다. 스케줄러도 실행 중 표시로 겹치지 않게 합니다
- **마감 시각은 파라미터로:** `NOW()` 로 대상을 잡으면 늦게 돌 때마다 대상이 달라집니다. 재실행해도 같은 대상을 보려면 마감 시각을 받습니다
- **늦은 실행과 실패 감지:** 23:15 미시작, 00:30 ALLOCATED 아님, 00:50 SHIPMENT_CREATED 아님, 잡 실패는 즉시 경보를 냅니다
- **실행 이력 정리:** Spring Batch 메타 테이블은 90일 보존하고, 일반 스케줄 컴포넌트로 지웁니다. 정리 작업을 Spring Batch 잡으로 만들면 지울 테이블에 자기 이력을 남깁니다
- **주기 배치의 빈 실행:** 만료 배치나 정리 배치처럼 자주 도는 작업은 할 일이 없으면 바로 끝내고 이력을 남기지 않습니다
