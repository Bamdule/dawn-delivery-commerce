# 작업 목록

설계 문서(`docs/design`)를 코드로 옮기는 순서입니다. 위에서부터 차례로 진행합니다.
각 작업은 완료 조건을 테스트로 증명해야 끝납니다. 끝나면 체크하고 커밋 해시를 적습니다.

## 0. 기반

- [ ] **통합 테스트 기반:** 서비스마다 Testcontainers 로 MySQL 8.4 를 띄우는 테스트 설정을 만든다. Kafka 가 필요한 서비스는 Kafka 컨테이너도 띄운다
  - 완료 조건: 각 서비스의 `@SpringBootTest` 가 Flyway 마이그레이션을 적용하고 통과한다
- [ ] **아웃박스 공통 모듈:** 주문, 결제, 풀필먼트가 함께 쓰는 아웃박스 기록과 릴레이 (설계 03 "릴레이")
  - 선점, 전송, 기록의 세 단계. 같은 키에 앞선 PENDING 이 있으면 뒤의 것을 집지 않는다. 실패는 1초부터 두 배, 최대 60초, 지터
  - `delivery.timeout.ms` 20초, 선점 30초. 이벤트 아이디는 사실에서 만든 이름 기반 UUID
  - 완료 조건: 릴레이 두 대가 동시에 돌아도 이벤트마다 SENT 가 한 번이다. 전송 뒤 기록 전에 죽이면 30초 뒤 다시 나간다. 같은 키의 순서가 지켜진다
- [ ] **처리 실패 토픽:** 컨슈머 공통 오류 처리기. 1, 2, 4초로 세 번 재시도한 뒤 `{토픽}.DLT` 로 보낸다
  - 완료 조건: 형식이 깨진 메시지가 처리 실패 토픽에 같은 키로 남는다. 다시 넣기 명령으로 원래 토픽에 넣을 수 있다
- [ ] **보존 정리:** 설계 03 "보존과 정리" 표의 대상을 청크로 지우는 스케줄 컴포넌트

## 1. 재고 차감 (설계 02)

- [ ] **갱신 유실 재현:** 조회 후 계산해서 저장하는 방식을 테스트 코드 안에만 만든다
  - 완료 조건: 재고 100, 동시 300건에서 성공 건수가 100을 넘는 것을 테스트가 보여 준다
- [ ] **조건부 차감:** 한 문장으로 차감하고 0행이면 품절. 여러 상품은 상품번호 순, 슬롯 상품은 마지막
  - 완료 조건: 재고 100, 동시 300건에서 정확히 100건 성공. {A, B} 와 {B, A} 주문을 동시에 1,000번 섞어도 교착이 없다
- [ ] **품절 캐시 API:** 판매 가능 재고가 0인 상품 목록을 내놓는다

## 2. 예약 (설계 02 "예약 후 확정")

- [ ] **예약:** (주문번호, 상품)마다 한 행. 차감과 HELD 생성을 한 트랜잭션으로. 유지 시간은 상품의 `hold_minutes`
- [ ] **결제 시작 표시:** HELD 이고 만료 전일 때만 PAYING, 회차 기록. 0행이면 현재 상태와 회차를 돌려준다. 한 주문의 예약은 가장 짧은 유지 시간으로 만료 시각 하나
- [ ] **거절 되돌림:** `status = 'PAYING' AND payment_round = :round` 일 때만 HELD 로
- [ ] **확정 소비자:** PAID 로 PAYING 을 CONFIRMED. 0행이면 상태를 다시 읽어 설계 02 표대로
- [ ] **복원 소비자:** CANCELLED 의 품목 수량을 사유와 관계없이 되돌린다. 인박스, stock 행 잠금, 부족분 먼저 갚기. 취소 수량이 예약 수량에 이르면 RESTORED
- [ ] **부족분:** 실사 감소는 0 에서 멈추고 남은 만큼을 부족분에, 복원과 입고는 부족분부터 갚는다
  - 완료 조건: 실물 10, 판매 10건 상태에서 실사 -2, 취소 2건을 어떤 순서로 넣어도 판매 가능 재고 0, 부족분 0
- [ ] **재고 대사:** 하루 한 번 설계 02 의 식을 상품마다 확인. 두 번 연속 어긋나면 경보. 보정 관리 API
- [ ] **만료 배치:** 1분 주기. 만료된 HELD 는 바로 푼다. 만료된 PAYING 은 결제 서비스에 그 회차의 봉인을 요청하고 결과대로 처리한다. 만료 5분 지난 예약이 있으면 경보
  - 완료 조건 1: 결제 시작과 만료를 같은 순간에 100번 겹쳐도 결제가 시작된 예약이 풀리지 않는다
  - 완료 조건 2: PAYING 표시 뒤 결제 요청을 늦춰 봉인보다 늦게 도착시키면 회차가 열리지 않는다. 회차 커밋을 늦춰 봉인과 겹치게 해도 한쪽만 이긴다
  - 완료 조건 3: 결제 승인 뒤 확정 이벤트가 늦어도 재고가 다시 팔리지 않는다. UNKNOWN 결제의 예약은 풀리지 않는다
  - 완료 조건 4: PAID 를 처리 실패 토픽으로 보낸 뒤 고객 취소가 오면 재고가 돌아온다

## 3. 슬롯 분산 (설계 02 "특가 상품")

- [ ] **켜기:** stock 행을 잠그고 슬롯 8개에 나눠 넣고 quantity 0, 모드 SPREAD. 0행을 받은 차감은 모드를 다시 읽어 슬롯 경로로 한 번 더
- [ ] **슬롯 차감과 내역:** 무작위 슬롯에서 빼고, 모자라면 나눠 뺀다. 내역을 `reservation_slot` 에 남긴다
- [ ] **해제:** SPREAD 는 내역대로, 내역이 없으면 슬롯 0. MERGED 는 모두 슬롯 0
- [ ] **합치기:** 잔량 합이 20 아래면 슬롯 행을 번호 순으로 잠그고 슬롯 0 으로 모은 뒤 MERGED
  - 완료 조건: 슬롯 8개, 재고 100에서 동시 300건이 정확히 100건 성공한다. 켜기, 차감, 해제, 합치기를 동시에 섞어 돌려도 판매 가능 재고 합 + 잡힌 예약 합이 늘 처음 재고와 같다

## 4. 결제 (설계 04)

- [ ] **가짜 결제 대행사:** 승인, 멱등키 조회, 환불, 환불 조회, 정산 파일 API. 지연, 타임아웃, 응답 유실, 5xx, 늦은 처리(60초 뒤 승인), 실패로 닫은 회차의 늦은 승인을 설정으로 고른다
- [ ] **회차 열기와 봉인:** 같은 번호면 그 회차 상태를 돌려준다. 봉인된 번호는 열지 않는다. 가장 최근 회차가 FAILED 나 EXPIRED 일 때만 새 회차. 봉인 API 는 EXPIRED 행을 넣고, 이미 있으면 그 상태를 돌려준다
  - 완료 조건: 1회차가 REQUESTED 인 동안 2회차는 거절된다. 봉인된 회차는 열리지 않는다
- [ ] **동기 승인:** 대행사를 한 번만 부른다. 타임아웃, 연결 끊김, 5xx 는 REQUESTED. 결과와 아웃박스를 한 트랜잭션에
  - 완료 조건: 대행사가 5초 동안 응답하지 않아도 결제 서비스는 3초 남짓에 답한다
- [ ] **동시 호출 한도와 회로 차단기:** 동시 600 초과는 즉시 FAILED. 최근 100건 중 타임아웃, 5xx, 2초 넘는 느린 호출이 50% 이상이면 연다. 카드 거절은 세지 않는다
- [ ] **조회 배치:** REQUESTED 를 멱등키로 조회. "요청 없음"은 마지막 전송 60초 뒤에만 FAILED. 10분 넘으면 UNKNOWN. 멱등키 지원 시 5xx 건을 같은 키로 다시 보내며 마지막 전송 시각을 갱신
  - 완료 조건: 응답 유실 뒤에도 대행사 승인은 한 번이고 APPROVED 로 확정된다. 50초에 다시 보낸 요청이 처리 중이면 FAILED 로 닫지 않는다
- [ ] **결제 상태 조회 API:** 주문번호의 회차별 상태. 재고 만료 배치와 주문 정리 배치가 쓴다
- [ ] **환불 접수와 환불 배치:** 환불 키 유니크로 접수하고, REQUESTED 환불을 같은 키로 대행사에 보내고 조회. 결과는 REFUNDED, REFUND_FAILED 이벤트. 1시간 넘으면 UNKNOWN
- [ ] **정산 대사:** 하루 한 번 정산 파일과 비교. 대행사 승인인데 우리 FAILED 인 회차는 APPROVED 로 바로잡고 아웃박스 APPROVED, 경보
- [ ] **관리 API:** UNKNOWN 결제와 UNKNOWN, FAILED 환불을 사람이 확정한다. 일반 전이처럼 아웃박스를 거친다

## 5. 주문 (설계 01, 04)

- [ ] **주문 생성:** 품절 캐시로 먼저 거른다. 주문서 ID 유니크. 같은 주문서 ID 로 다시 오면 기존 주문의 현재 상태를 돌려준다
  - 완료 조건: 같은 주문서 ID 로 동시에 5번 요청해도 주문과 결제가 하나다
- [ ] **동기 흐름:** PENDING 저장, 예약, 결제 시작 표시, 결제 승인. 시간 예산(재고 500ms, 결제 5초)을 지킨다
  - 결제 시작 표시가 0행이면 예약 상태로 나눈다. RELEASED 만 FAILED, PAYING 은 그 회차 상태를 보고 판단
  - 완료 조건 1: "결제 확인 중"에 다시 결제를 눌러도 주문이 FAILED 가 되지 않는다
  - 완료 조건 2: 대행사가 3초 지연할 때 주문 DB 커넥션이 그동안 잡혀 있지 않음을 커넥션 풀 지표로 보인다
- [ ] **다시 결제 API:** `payment_round = 이전 값` 조건으로 회차를 올린 뒤 결제 시작
  - 완료 조건: 같은 주문에 다시 결제를 동시에 두 번 눌러도 회차는 하나만 열린다
- [ ] **결제 이벤트 소비자:** APPROVED 는 주문 상태로 나눈다(설계 04 표). PENDING 이면 PAID, `paid_round`, 아웃박스. 쓰지 않은 승인이면 `refund-{주문번호}-orphan-{회차}` 와 경보
  - 완료 조건: 실패로 닫은 회차가 늦게 승인되면 그 회차가 환불된다
- [ ] **정리 배치:** 2분 넘은 PENDING 을 결제 서비스에 묻고 설계 04 표대로. 15분 넘으면 경보
  - 완료 조건: 승인 응답을 받은 직후 PAID 커밋 전에 주문 서비스를 죽여도, 재기동 뒤 PAID 와 PAID 이벤트가 한 번씩 생긴다
- [ ] **회차별 PAID 목록 API와 주문 상세 API:** 출고 배치의 대상 확정이 쓴다
- [ ] **고객 취소:** 속한 회차의 마감 전까지만. CANCELLED(CUSTOMER), 아웃박스, 환불 요청을 한 트랜잭션에
- [ ] **관리자 취소 API:** 출고 예외 주문만. CANCELLED(ADMIN), 환불 키 `refund-{주문번호}-admin`
- [ ] **환불 접수 배치와 결과 반영:** REQUESTED 를 결제 서비스가 접수할 때까지 보내 ACCEPTED. REFUNDED 로 COMPLETED 와 누적액을 한 트랜잭션에(1행일 때만)
- [ ] **출고 불가 소비자:** UNFILLABLE 의 품목을 취소하고 품목 금액만큼 환불 요청. 모든 품목이 취소되면 CANCELLED. 환불 키는 마감 일시로

## 6. 풀필먼트 (설계 05)

- [ ] **출고 대상 소비자:** PAID 는 없을 때만 삽입. 모르는 주문의 CANCELLED 는 취소 표시 행을 남기고 뒤늦은 PAID 가 되살리지 않는다
- [ ] **대상 확정 스텝:** 주문 서비스 목록과 대조, 빠진 주문 삽입, 회차 기록, 이월 주문 포함, 취소 표시, TARGET_FIXED
  - 완료 조건: PAID 이벤트를 처리 실패 토픽으로 보낸 주문도 출고 대상에 오른다. 이월한 주문이 다음 회차에 오른다
- [ ] **할당 스텝:** 스냅샷을 고정하고 1차, 2차, 3차 순으로 배정. 결과와 판정을 1,000행씩 커밋, 끝나면 ALLOCATED
  - 완료 조건: 저장 중간에 죽이고, 그사이 입고를 넣고, 재시작해도 결과가 처음 계산과 같다
- [ ] **판정 발행 스텝:** 판정마다 아웃박스 UNFILLABLE. 이벤트 아이디는 (주문번호, 마감 시각)
- [ ] **출고 지시 스텝:** 센터별 파티션 4개, 청크 500. (센터, 주문) 단위로 묶어 읽고, 출고 지시, 품목, 실물 재고 차감을 한 트랜잭션에. 이미 있으면 건너뛴다
  - 완료 조건: 중간에 실패시킨 뒤 재시작하면 남은 것만 처리되고, 출고 지시와 재고 차감이 두 번 일어나지 않는다
- [ ] **결과 검증 스텝:** 예외 0.1% 와 건수 합계 확인. 넘으면 VERIFY_FAILED 와 경보
- [ ] **관리 API:** 출고 예외의 이월, 검증 실패 회차의 승인
- [ ] **입고와 실사:** 실물 재고, 조정 이력, 아웃박스 STOCK_CHANGED 를 한 트랜잭션에. 재고 서비스가 인박스로 받아 판매 가능 재고를 바꾸고, 0 에서 멈춘 조정은 기록만 한다

## 8. 실험 기록

설계에서 예상한 것과 실제 측정을 `docs/experiments/` 에 남깁니다. 준비, 절차, 예상, 실제 순서로 씁니다.

- [ ] **동시성:** 조건부 차감, 슬롯 8개, 비관적 락을 초당 500건에서 비교. 상품 3개 주문으로도 잰다. 한 행 상한 초당 200건 가정이 맞는지
- [ ] **릴레이 처리량:** 200ms 주기, 500건에서 실제 상한이 초당 2,500건 가까이 나오는지
- [ ] **결제 복구:** 응답 유실, 늦은 처리, 주문 서비스 중단을 섞어 돌린 뒤 결제와 주문과 예약 상태가 모두 맞는지
- [ ] **배치:** 30만 주문 데이터로 스텝별 시간을 재고, 한 센터 쏠림까지 예상과 비교
