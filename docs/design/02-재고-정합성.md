# 02. 재고 정합성

## 요약

**무엇을 설명하나:** 재고 100개에 동시 주문 300건이 들어올 때 실제보다 많이 팔지 않는 방법을 다룹니다. 차감 방식, 인기 상품 분산, 차감 시점, 재고 모델을 차례로 고릅니다.

**재고 정합성은 무엇에 쓰나:** 오버셀이 나면 고객에게 취소를 통보해야 하고, 새벽배송에서는 그날 배송이 불가능해집니다. 그래서 재고는 어긋나면 비용이 큰 값입니다.

**세 줄 요약**
1. 조회하고 계산해서 쓰면 300건이 모두 100을 읽어 갱신이 유실되므로, 조건부 UPDATE 한 문장으로 차감합니다.
2. 그래도 같은 행에 직렬화되므로, 주문이 쏠리는 상품에만 재고를 슬롯으로 쪼개 경쟁을 흩습니다.
3. 차감은 예약 후 확정으로 하고, 판매 가능 재고와 센터별 실물 재고를 나눠 관리합니다.

## 문제를 숫자로 세우기

> 재고 100개에 300건이 동시에 100을 읽고 99를 쓰면 주문 300건이 모두 성공합니다. 이 갱신 유실이 오버셀을 만듭니다.

재고가 100개인 상품에 **동시에 300건의 주문 요청**이 들어옵니다.
지금 코드가 이렇게 되어 있다고 가정합니다.

```java
Stock stock = stockRepository.findById(productId);   // 100 을 읽음
if (stock.getQuantity() < orderQty) throw new OutOfStock();
stock.setQuantity(stock.getQuantity() - orderQty);   // 99 로 계산
stockRepository.save(stock);                          // 99 를 씀
```

**300개 요청이 거의 같은 순간에 100을 읽습니다.** 각자 100에서 1을 빼 99를 씁니다.
결과적으로 재고는 99가 되고 **주문은 300건이 성공합니다.** 200건은 팔 수 없는 물건입니다.

이게 갱신 유실입니다. 두 요청이 같은 값을 읽고 각자 덮어쓰면 한쪽 갱신이 사라집니다.

**커머스에서는 이게 더 비쌉니다.** 조회수 같은 값은 조금 어긋나도 나중에 맞추면 되지만,
오버셀은 **고객에게 취소를 통보해야 하고 새벽배송에서는 그날 배송이 불가능해집니다.**

## 선택지와 각각이 깨지는 지점

> 비관적 락, 원자적 조건부 갱신, 낙관적 락, Redis 선점의 네 가지를 봅니다. 대부분은 조건부 갱신이 정답이지만 이것도 같은 행에 직렬화됩니다.

### 방법 1. 비관적 락

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Stock> findByProductIdForUpdate(Long productId);
```

조회 시점에 행을 잠그므로 300건이 한 줄로 서고 재고는 정확해집니다.

**어디서 깨지는가.** 인기 상품 하나에 초당 300건이 몰리면 **전부 그 행 하나를 기다립니다.**
한 건 처리가 5ms 라면 300번째 요청은 1.5초를 기다립니다. 그 동안 커넥션도 잡고 있습니다.
게다가 락을 잡은 트랜잭션 안에서 다른 일을 하면(로그 저장, 이력 삽입) 그만큼 대기가 길어집니다.

락 구간이 바깥 트랜잭션 길이에 끌려가지 않도록, 잠금 조회 뒤의 변경과 커밋을 짧은 트랜잭션으로 끝내야 합니다.

### 방법 2. 원자적 조건부 갱신

```sql
UPDATE stock
   SET quantity = quantity - :qty,
       updated_at = NOW()
 WHERE product_id = :productId
   AND quantity >= :qty
```

**읽지 않고 바로 씁니다.** 조건을 SQL 안에 넣어 재고가 부족하면 아무 행도 갱신되지 않습니다.
애플리케이션은 **영향받은 행 수가 0이면 품절**로 판정합니다.

```java
int affected = stockMapper.decrease(productId, qty);
if (affected == 0) throw new OutOfStock();
```

락을 명시적으로 잡지 않지만 데이터베이스가 갱신하는 순간 그 행을 잠그므로 정확합니다.
락은 커밋까지 유지되므로 차감 `UPDATE`를 트랜잭션 맨 끝에 두고 곧바로 커밋합니다.

**이게 대부분의 경우 정답입니다.** 비관적 락보다 빠르고 낙관적 락보다 단순합니다.

**어디서 깨지는가.** 여전히 **같은 행에 직렬화됩니다.** 락 구간이 짧아졌을 뿐 없어진 것은
아닙니다. 초당 수천 건이 한 행에 몰리면 이것도 병목이 됩니다.

### 방법 3. 낙관적 락

버전 컬럼을 두고 충돌하면 예외를 던져 재시도합니다.

**어디서 깨지는가.** **충돌이 잦은 곳에서는 최악입니다.** 300건이 경쟁하면 한 건만 성공하고
299건이 실패해 재시도하고, 그중 한 건만 또 성공합니다. **재시도가 부하를 다시 만듭니다.**
낙관적 락은 충돌이 드문 곳에 쓰는 도구입니다.

### 방법 4. Redis 선점 후 DB 정산

Redis 에서 `DECR` 로 먼저 차감하고 DB 는 나중에 맞춥니다. 매우 빠릅니다.

**어디서 깨지는가.** **Redis 와 DB 가 어긋날 수 있습니다.** Redis 차감 성공 후 DB 반영
전에 죽으면 팔린 것으로 카운트됐지만 주문이 없습니다. 반대 경우도 생깁니다.
`DECR`만 쓰면 재고가 0일 때도 -1로 내려갑니다. Lua 스크립트에서 현재 값을 확인하고, 수량이 충분할 때만 차감하도록 한 번에 실행해야 합니다.
그래서 이걸 쓰려면 **정산과 보정 절차를 반드시 함께 만들어야** 하고, 그 복잡성이
얻는 성능보다 큰지 따져야 합니다. 재고가 돈과 직결되는 곳에서는 신중해야 합니다.

## 인기 상품 문제: 재고 슬롯 분산

> 한 상품 재고를 여러 슬롯 행으로 쪼개 경쟁을 흩습니다. 대가가 있어서 주문이 쏠리는 상품에만 플래그로 켭니다.

방법 2를 골랐다고 해도 **초당 수천 건이 한 상품에 쏠리면** 그 행이 병목입니다.
새벽배송 마감 직전에 특정 상품에 주문이 몰리는 상황이 정확히 이것입니다.

**해법은 한 행을 여러 행으로 쪼개는 것입니다.**

```
stock_slot
+------------+---------+----------+
| product_id | slot_no | quantity |
+------------+---------+----------+
|      1001  |       0 |       10 |
|      1001  |       1 |       10 |
|      ...   |     ... |      ... |
|      1001  |       9 |       10 |
+------------+---------+----------+
```

재고 100을 10개 슬롯에 10씩 나눠 둡니다. 차감할 때 **슬롯 하나를 골라 그 행만 갱신**합니다.

```java
int slot = ThreadLocalRandom.current().nextInt(SLOT_COUNT);
int affected = slotMapper.decrease(productId, slot, qty);
if (affected == 0) {
    // 고른 슬롯이 비었을 뿐 전체가 품절은 아니다
    affected = slotMapper.decreaseFromAnySlot(productId, qty);
}
```

**경쟁이 10분의 1로 흩어집니다.** 슬롯 수를 늘리면 더 흩어집니다.

**대가가 있습니다.** 이 방식은 세 가지를 포기합니다.

**첫째, 전체 재고 조회가 합산이 됩니다.** `SELECT SUM(quantity)` 이 되어 정확한 잔량을
실시간으로 보여주기 어렵습니다. 그래서 보통 상세 화면에는 정확한 수치 대신
"품절 임박" 같은 표시를 씁니다.

**둘째, 마지막 몇 개에서 헛손질이 생깁니다.** 총 3개 남았는데 슬롯 10개에 흩어져 있으면
빈 슬롯을 고를 확률이 높습니다. 그래서 **잔량이 임계값 아래로 떨어지면 슬롯을 하나로
합치는 전환**이 필요합니다. 주문 수량이 슬롯 하나의 잔량보다 큰 경우도 같습니다.
전체 재고가 충분해도 한 슬롯에서 다 빼지 못해 실패하므로, 여러 슬롯에서 나눠 빼거나 합친 경로로 넘깁니다.

**셋째, 슬롯 재배분이라는 운영 작업이 생깁니다.** 입고할 때 어느 슬롯에 넣을지 정해야 합니다.

**그래서 슬롯 분산은 기본이 아니라 예외로 씁니다.** 전 상품에 적용하지 않고
**주문이 쏠리는 상품에만 켭니다.** 상품 속성에 플래그를 두고, 판매 예정 수량이 크거나
과거에 쏠렸던 상품만 슬롯을 나눕니다.

## 즉시 차감이냐 예약이냐

> 언제 차감할지는 별개의 결정입니다. 새벽배송은 죽은 재고의 손실이 커서 예약 후 확정과 만료 배치를 씁니다.

지금까지는 "차감" 이라고 뭉뚱그렸는데 **언제 차감할지가 별개의 결정**입니다.

### 즉시 차감

주문 요청이 오면 바로 재고를 깎습니다. 단순하고 오버셀이 확실히 막힙니다.

**문제는 결제 실패입니다.** 재고를 깎았는데 결제가 실패하면 되돌려야 합니다.
그런데 **되돌리는 데 실패하면 그 재고는 영영 돌아오지 않습니다.**
재고 숫자만 줄었을 뿐 누가 왜 잡고 있는지 기록이 없어서, 나중에 찾아 돌려놓을 방법이 없습니다.

### 예약 후 확정

```
stock_reservation
+----------------+------------+----------+---------------------+--------+
| reservation_id | product_id | quantity | expires_at          | status |
+----------------+------------+----------+---------------------+--------+
| r-2026-0001    |      1001  |        2 | 2026-09-10 23:05:00 | HELD   |
+----------------+------------+----------+---------------------+--------+
```

주문 시작 시 **판매 가능 재고에서 빼고 예약 행을 만듭니다.** 결제가 성공하면 예약을 확정으로
바꾸고, 실패하거나 **만료 시각이 지나면 예약을 풀어 판매 가능 재고로 되돌립니다.**

**만료 처리는 두 가지를 함께 씁니다.** 결제 실패 시 즉시 해제하는 경로와,
**놓친 것을 주워 담는 배치**입니다. 즉시 해제가 실패할 수 있으므로 배치가 반드시 필요합니다.
즉시 차감과 달리 예약 행에 만료 시각이 남아 있어서, 배치가 놓친 재고를 찾아낼 수 있습니다.

### 만료 배치는 결제 상태를 먼저 봅니다

결제가 끝난 뒤 예약 확정은 이벤트로 비동기 처리합니다(01번).
마감 직전처럼 이벤트가 밀리면, 결제한 주문의 예약이 만료 시각을 넘겨도 `HELD`로 남아 있습니다.
이걸 그대로 풀면 결제한 고객의 재고를 다른 고객에게 다시 팝니다.

| 시각 | 일어난 일 |
|---|---|
| 23:00 | 예약, 만료 23:05 |
| 23:01 | 결제 승인, 주문 `PAID` |
| 23:05 | 확정 이벤트가 밀려 아직 `HELD`. 만료 배치가 풀면 재고가 다시 팔림 |
| 23:07 | 확정 이벤트 도착. `HELD`가 아니라 0행 |

그래서 만료 배치는 예약을 풀기 전에 주문 서비스에 결제 상태를 묻습니다.

| 결제 상태 | 만료 배치가 하는 일 |
|---|---|
| 결제 없음, `FAILED` | 예약을 풀어 판매 가능 재고로 되돌린다 |
| `REQUESTED` | 풀지 않고 결제 결과를 먼저 조회한다. 조회 한도를 넘기면 사람이 확인한다 |
| `APPROVED` | 풀지 않고 예약을 확정한다. 밀린 확정 이벤트를 대신 처리하는 셈이다 |

확정하는 쪽도 짝을 맞춥니다. 확정 갱신이 0행이면 이미 확정된 중복인지, 풀린 예약인지 구분합니다.
풀린 예약이면 결제한 주문에 재고가 없다는 뜻이므로 경보를 냅니다(03번).

**어느 쪽을 고르는가.** 결제가 즉시 끝나는 구조라면 즉시 차감으로 충분합니다.
결제창에서 사용자가 머무는 시간이 있거나 외부 결제로 나갔다 오는 흐름이면 예약이 필요합니다.
그 사이 실패할 일이 많고, 실패할 때마다 되돌리기가 필요하기 때문입니다.
새벽배송은 마감 직전에 몰려 놓친 재고가 곧 그날 판매 손실이라 예약 쪽입니다.

## 판매 가능 재고와 실물 재고를 나누는 이유

> 판매는 전국 합산으로 하지만 출고는 특정 센터에서 나가므로 두 재고를 나눕니다. 실사 차이가 나면 판매 가능 재고도 줄여야 합니다.

여기까지는 "재고" 를 하나로 봤지만 풀필먼트가 붙으면 **두 개로 나뉩니다.**

| 종류 | 무엇인가 | 누가 바꾸는가 |
|---|---|---|
| **판매 가능 재고** | 지금 팔 수 있는 수량 | 주문(차감), 예약 해제(복원), 입고 반영 |
| **센터별 실물 재고** | 각 물류센터에 실제로 있는 수량 | 입고, 출고 확정, 실사 조정 |

**왜 나누는가.** 판매는 전국 합산으로 하지만 출고는 특정 센터에서 나갑니다.
서울 센터에 10개, 부산 센터에 10개가 있으면 판매 가능 재고는 20이지만,
**서울 고객의 주문 15건은 서울 센터만으로는 못 채웁니다.**

그래서 출고 단계에서 **어느 센터에서 낼지 결정하는 할당 로직**이 필요하고,
할당이 안 되면 부분 출고나 취소로 이어집니다. 이 부분은 05번에서 다룹니다.

**그리고 실사 차이가 있습니다.** 전산은 10개인데 실제로 세어 보니 9개인 경우입니다.
파손이나 분실, 입고 오류로 생깁니다. **실사 결과를 반영하면 판매 가능 재고도 줄여야 하고,
이미 받은 주문 중 일부는 채울 수 없게 됩니다.** 이 조정도 배치 영역입니다.

## 정리: 이 시스템의 선택

> 네 가지 결정과 각각 포기한 것을 표로 모았습니다. 무엇을 포기했는지 말할 수 있어야 이해한 것입니다.

| 결정 | 선택 | 포기한 것 |
|---|---|---|
| 동시 차감 | **원자적 조건부 갱신**을 기본으로 | 명시적 락의 단순함 |
| 인기 상품 | **슬롯 분산을 플래그로 켬** | 정확한 실시간 잔량 표시, 슬롯 운영 부담 |
| 차감 시점 | **예약 후 확정** | 즉시 차감의 단순함, 만료 배치가 추가로 필요 |
| 재고 모델 | **판매 가능 재고와 센터 실물 재고 분리** | 두 값을 맞추는 정산 절차가 필요 |

이 표의 핵심은 무엇을 골랐는지가 아니라 **무엇을 포기했는지**입니다. 선택의 대가까지
설명할 수 있어야 이해한 것입니다.
