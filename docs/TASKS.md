# 작업 목록

설계 문서(`docs/design`)를 코드로 옮기는 순서입니다. 위에서부터 차례로 진행합니다.
각 작업은 완료 조건을 테스트로 증명해야 끝납니다. 끝나면 체크하고 커밋 해시를 적습니다.

## 0. 기반

- [x] **통합 테스트 기반:** 서비스마다 Testcontainers 로 MySQL 8.4 를 띄우는 테스트 설정을 만든다. Kafka 가 필요한 서비스는 Kafka 컨테이너도 띄운다
  - 완료 조건: 각 서비스의 `@SpringBootTest` 가 Flyway 마이그레이션을 적용하고 통과한다
- [x] **아웃박스 공통 모듈:** 주문, 결제, 풀필먼트가 함께 쓰는 아웃박스 기록과 릴레이 (설계 03 "릴레이")
  - 선점, 전송, 기록의 세 단계. 같은 키에 앞선 PENDING 이 있으면 뒤의 것을 집지 않는다. 실패는 1초부터 두 배, 최대 60초, 지터
  - `delivery.timeout.ms` 20초, 선점 30초. 이벤트 아이디는 사실에서 만든 이름 기반 UUID
  - 완료 조건: 릴레이 두 대가 동시에 돌아도 이벤트마다 SENT 가 한 번이다. 전송 뒤 기록 전에 죽이면 30초 뒤 다시 나간다. 같은 키의 순서가 지켜진다
- [x] **처리 실패 토픽:** 컨슈머 공통 오류 처리기. 1, 2, 4초로 세 번 재시도한 뒤 `{토픽}-dlt` 로 보낸다
  - 완료 조건: 형식이 깨진 메시지가 처리 실패 토픽에 같은 키로 남는다. 다시 넣기 명령으로 원래 토픽에 넣을 수 있다
- [x] **보존 정리:** 설계 03 "보존과 정리" 표의 대상을 청크로 지우는 스케줄 컴포넌트. 서비스마다 보존 규칙을 등록하고, 처리 실패 토픽 14일은 Kafka 토픽 설정으로 둔다
- [x] **아웃박스 격리 관리 API:** 영구히 보낼 수 없는 이벤트를 사람이 고쳐 다시 보내거나 QUARANTINED 로 격리. 메시징 모듈에 두어 이벤트를 내는 서비스마다 같은 주소로 켜진다

## 1. 재고 차감 (설계 02)

- [x] **갱신 유실 재현:** 조회 후 계산해서 저장하는 방식을 테스트 코드 안에만 만든다
  - 완료 조건: 10건이 모두 100을 읽은 뒤 각자 99를 쓰면 10건이 성공해도 재고는 99다. 장벽(CyclicBarrier)으로 읽기를 맞춰 매번 같은 결과를 낸다
- [x] **조건부 차감:** 한 문장으로 차감하고 0행이면 품절. 여러 상품은 상품번호 순, 슬롯 상품은 마지막(슬롯은 3번 작업에서)
  - 완료 조건: 재고 100, 동시 300건에서 정확히 100건 성공. {A, B} 와 {B, A} 주문을 동시에 1,000번 섞어도 교착이 없다
- [x] **품절 목록 API:** 판매 가능 재고가 0인 상품 목록을 요청 때마다 계산해 내놓는다
- [x] **예약 상태 조회 API:** 주문번호의 예약 상태. 주문 정리 배치가 쓴다. 예약이 없으면 없다고 답한다 (예약, 결제 시작 표시, 되돌림 HTTP API 와 함께 5번 작업에서)

## 2. 예약 (설계 02 "예약 후 확정")

- [x] **예약:** (주문번호, 상품)마다 한 행. 차감과 HELD 생성을 한 트랜잭션으로. 유지 시간은 상품의 `hold_minutes`. 요청에 실린 배송 권역이 판매 제한 권역이면 품절로 답한다
- [x] **판매 제한 권역 관리 API:** 상품별 판매 제한 권역을 설정한다 (재고 서비스)
- [x] **결제 시작 표시:** HELD 이고 만료 전일 때만 PAYING, 회차 기록. 0행이면 현재 상태와 회차를 돌려준다. 한 주문의 예약은 가장 짧은 유지 시간으로 만료 시각 하나
- [x] **거절 되돌림:** `status = 'PAYING' AND payment_round = :round` 일 때만 HELD 로
- [x] **확정 소비자:** PAID 로 PAYING 을 CONFIRMED. 0행이면 상태를 다시 읽어 설계 02 표대로
- [x] **복원 소비자:** CANCELLED 의 품목 수량을 사유와 관계없이 되돌린다. 인박스, stock 행 잠금, 부족분 먼저 갚기. 취소 수량이 예약 수량에 이르면 RESTORED
- [x] **부족분:** 실사 감소는 0 에서 멈추고 남은 만큼을 부족분에. 만료 해제, 취소 복원, 입고는 모두 부족분부터 갚는다 (실사 감소의 STOCK_CHANGED 소비자와 슬롯 상품의 실사 감소는 6번 입고와 실사 작업에서 완료)
  - 완료 조건 2: 어떤 순서로 섞어 넣어도 부족분이 0보다 크면 판매 가능 재고는 0 이다. HELD 10건을 만료시켜도 실사 부족분 2 를 먼저 갚는다
  - 완료 조건: 실물 10, 판매 10건 상태에서 실사 -2, 취소 2건을 어떤 순서로 넣어도 판매 가능 재고 0, 부족분 0
- [x] **재고 대사:** 하루 한 번 설계 02 의 식을 상품마다 확인. 어긋난 상품만 10분 뒤 다시 재서 또 어긋나면 경보. 보정 관리 API (풀필먼트가 실물 합과 출고 전 확정 수량을 주는 API 와 함께)
- [x] **만료 배치:** 1분 주기. 만료된 HELD 는 바로 푼다. 만료된 PAYING 은 결제 서비스에 그 회차의 봉인을 요청하고 결과대로 처리한다. 푸는 수량은 부족분부터 갚는다. 배치가 5분 넘게 돌지 않거나 만료 5분 지난 HELD 가 있으면 경보 (완료 조건 2 는 결제 서비스 테스트 "봉인된 회차는 늦게 온 승인 요청이 열지 못한다"로 확인. 정지 경보 지표는 7번에서)
  - 완료 조건 1: 결제 시작과 만료를 같은 순간에 100번 겹쳐도 결제가 시작된 예약이 풀리지 않는다
  - 완료 조건 2: PAYING 표시 뒤 결제 요청을 늦춰 봉인보다 늦게 도착시키면 회차가 열리지 않는다. 회차 커밋을 늦춰 봉인과 겹치게 해도 한쪽만 이긴다
  - 완료 조건 3: 결제 승인 뒤 확정 이벤트가 늦어도 재고가 다시 팔리지 않는다. UNKNOWN 결제의 예약은 풀리지 않는다
  - 완료 조건 4: PAID 를 처리 실패 토픽으로 보낸 뒤 고객 취소가 오면 재고가 돌아온다

## 3. 슬롯 분산 (설계 02 "특가 상품")

- [x] **켜기:** stock 행을 잠그고 슬롯 8개에 나눠 넣고 quantity 0, 모드 SPREAD. 0행을 받은 차감은 모드를 다시 읽어 슬롯 경로로 한 번 더
- [x] **슬롯 차감과 내역:** 무작위 슬롯에서 빼고, 모자라면 나눠 뺀다. 내역을 `reservation_slot` 에 남긴다
- [x] **해제:** SPREAD 는 내역대로, 내역이 없으면 슬롯 0. MERGED 는 모두 슬롯 0. 어느 모드든 부족분부터 갚는다
- [x] **합치기:** 잔량 합이 20 아래면 슬롯 행을 번호 순으로 잠그고 슬롯 0 으로 모은 뒤 MERGED
  - 완료 조건: 슬롯 8개, 재고 100에서 동시 300건이 정확히 100건 성공한다. 켜기, 차감, 해제, 합치기를 동시에 섞어 돌려도 판매 가능 재고 합 + 잡힌 예약 합이 늘 처음 재고와 같다
- [x] **다시 펴기:** MERGED 상품을 `stock` 행과 슬롯 8개를 번호 순으로 잠그고 다시 나눠 SPREAD 로. 특가 판매 등록 전에 확인한다

## 4. 결제 (설계 04)

- [x] **가짜 결제 대행사:** 승인, 멱등키 조회, 환불, 환불 조회, 정산 파일 API. 지연, 타임아웃, 응답 유실, 5xx, 늦은 처리(60초 뒤 승인), 실패로 닫은 회차의 늦은 승인을 설정으로 고른다
- [x] **회차 열기와 봉인:** 같은 번호면 그 회차 상태를 돌려준다. 봉인된 번호는 열지 않는다. 가장 최근 회차가 FAILED 나 EXPIRED 일 때만 새 회차. 봉인 API 는 EXPIRED 행을 넣고, 이미 있으면 그 상태를 돌려준다
  - 완료 조건: 1회차가 REQUESTED 인 동안 2회차는 거절된다. 봉인된 회차는 열리지 않는다
- [x] **동기 승인:** 대행사를 한 번만 부른다. 타임아웃, 연결 끊김, 5xx 는 REQUESTED. 결과와 아웃박스를 한 트랜잭션에
  - 완료 조건: 대행사가 5초 동안 응답하지 않아도 결제 서비스는 3초 남짓에 답한다
- [x] **동시 호출 한도와 회로 차단기:** 동시 600 초과는 즉시 FAILED. 최근 100건 중 타임아웃, 5xx, 2초 넘는 느린 호출이 50% 이상이면 연다. 카드 거절은 세지 않는다
- [x] **조회 배치:** REQUESTED 를 멱등키로 조회. 한 주기에 오래된 순서로 최대 1,000건, 동시 호출 한도와 회로 차단기를 함께 거침. "요청 없음"은 마지막 전송 60초 뒤에만 FAILED. 10분 넘으면 UNKNOWN. 멱등키 지원 시 5xx 건을 같은 키로 다시 보내며 마지막 전송 시각을 갱신
  - 완료 조건: 응답 유실 뒤에도 대행사 승인은 한 번이고 APPROVED 로 확정된다. 50초에 다시 보낸 요청이 처리 중이면 FAILED 로 닫지 않는다
- [x] **결제 상태 조회 API:** 주문번호의 회차별 상태. 동기 흐름이 "PAYING, 앞 회차"를 만났을 때 앞 회차의 끝 상태를 확인하는 데 쓴다
- [x] **환불 상태 조회 API:** 환불 키로 상태를 돌려준다. 주문 환불 배치가 오래된 ACCEPTED 를 맞출 때 쓴다
- [x] **환불 접수와 환불 배치:** 같은 환불 키가 있으면 먼저 그 상태를 돌려주고, 없을 때만 회차별 환불 합 상한을 검사해 접수한다. REQUESTED 환불은 같은 키로 대행사에 보내고 조회. 결과는 REFUNDED, REFUND_FAILED 이벤트. 1시간 넘으면 UNKNOWN
  - 완료 조건: 45,000원 환불의 접수 응답을 유실시키고 다시 보내도 거절되지 않는다
- [x] **정산 대사:** 하루 한 번 정산 파일과 비교. 세 종류(대행사 승인과 우리 FAILED, 우리 APPROVED 와 대행사 없음, 환불 상태 다름)를 `settlement_mismatch` 에 남기고 경보
  - 첫째는 APPROVED 로 바로잡고 정산 정정 표시를 단 APPROVED 를 낸다. 주문 서비스는 이것을 늘 쓰이지 않은 승인으로 환불한다
  - 셋째는 환불을 대행사 결과로 바로잡는다. 완료가 실패로 바뀌면 COMPLETED → FAILED 와 REFUND_FAILED
- [x] **관리 API:** UNKNOWN 결제와 UNKNOWN, FAILED 환불을 사람이 확정한다. 일반 전이처럼 아웃박스를 거친다

## 5. 주문 (설계 01, 04)

- [x] **주문 생성:** 500ms 마다 받은 품절 목록으로 먼저 거른다. 주문서 ID 유니크. 같은 주문서 ID 로 다시 오면 기존 주문의 현재 상태를 돌려준다
  - 완료 조건: 같은 주문서 ID 로 동시에 5번 요청해도 주문과 결제가 하나다
- [x] **동기 흐름:** PENDING 저장, 예약, 결제 시도 시작, 결제 시작 표시, 결제 승인. 시간 예산(재고 500ms, 결제 5초)을 지킨다
  - 같은 주문서 ID 확인을 품절 목록보다 먼저 한다
  - 결제 시도는 `attempt = 'IDLE'` 조건으로 시작한다. 0행이면 "결제 진행 중". 시도를 끝내는 모든 갱신에는 `payment_round = r` 조건을 건다
  - 결제 시작 표시가 0행이면 설계 01 표대로. 예약이 만료됐을 때만 FAILED. "봉인됨" 응답도 예약 상태를 다시 읽어 판단
  - 완료 조건 1: "결제 확인 중"에 다시 결제를 눌러도 주문이 FAILED 가 되지 않는다
  - 완료 조건 2: 대행사가 3초 지연할 때 주문 DB 커넥션이 그동안 잡혀 있지 않음을 커넥션 풀 지표로 보인다
- [x] **다시 결제 API:** 동기 흐름의 결제 시도 시작부터 같다
  - 완료 조건: 같은 주문에 다시 결제를 동시에 열 번 눌러도 시도는 하나만 진행되고, 결제된 주문이 FAILED 로 닫히지 않는다
- [x] **결제 이벤트 소비자:** APPROVED 는 주문 상태와 회차로 나눈다(설계 04 표). PENDING 이고 진행 중인 회차면 PAID, 아니면 `refund-{주문번호}-orphan-{회차}` 와 경보
  - 완료 조건: 오래 멈췄던 요청이 깨어나 시도를 끝내려 해도, 그사이 시작된 다음 회차의 시도를 바꾸지 못한다
  - 완료 조건: 실패로 닫은 회차가 늦게 승인되면 그 회차가 환불된다
- [x] **정리 배치:** 1분 넘은 IN_PROGRESS 시도는 회차 봉인으로, 시도가 IDLE 인 PENDING 은 예약 상태로 설계 04 표대로. 15분 넘으면 경보
  - 완료 조건 1: 승인 응답을 받은 직후 PAID 커밋 전에 주문 서비스를 죽여도, 재기동 뒤 PAID 와 PAID 이벤트가 한 번씩 생긴다
  - 완료 조건 2: 주문 저장 직후, 예약 직후, 결제 시작 표시 직후에 각각 주문 서비스를 죽여도 주문이 PAID 나 FAILED 로 끝난다
  - 프로세스를 실제로 죽이는 대신, 각 지점에서 멈춘 DB 상태를 만들고 정리 배치를 돌려 확인했다. 실제 강제 종료 실험은 8번 실험 기록에서
- [x] **회차별 PAID 목록 API와 주문 상세 API:** 출고 배치의 대상 확정이 쓴다
- [x] **고객 취소:** 속한 회차의 마감 전까지만. CANCELLED(CUSTOMER), 아웃박스, 환불 요청을 한 트랜잭션에
- [x] **관리자 취소 소비자:** EXCEPTION_CANCELLED 의 품목 수량을 취소하고 환불을 요청한다
  - 환불 키는 `refund-{주문번호}-admin-{예외번호}`. 모든 품목이 취소되면 주문 CANCELLED
- [x] **환불 접수 거절:** 결제 서비스가 상한 초과로 거절하면 REJECTED, 경보. 사람이 관리 API 로 바로잡음
- [x] **정산 정정 환불 반영:** 정산 정정 표시가 달린 REFUND_FAILED 를 받으면 COMPLETED 를 FAILED 로 바꾼다
  - 같은 트랜잭션에서 누적액을 되돌리고 경보. 사람이 `refund-{주문번호}-reissue-{원래 요청 번호}` 로 다시 요청하는 관리 API
- [x] **환불 접수 배치와 결과 반영:** REQUESTED 를 결제 서비스가 접수할 때까지 보내 ACCEPTED. 접수 응답의 결제 쪽 상태도 반영. REFUNDED 는 REQUESTED, ACCEPTED, FAILED 에서 COMPLETED 로, 누적액을 한 트랜잭션에(1행일 때만). 1시간 넘은 ACCEPTED 는 환불 상태 조회로 맞춤
  - 완료 조건: 접수 응답을 유실시키고 그사이 환불을 완료시켜도 COMPLETED 와 누적액이 맞다
- [x] **출고 불가 소비자:** UNFILLABLE 의 품목을 취소하고 품목 금액만큼 환불 요청을 한 트랜잭션에. 환불 키 유니크로 중복을 막는다. 모든 품목이 취소되면 CANCELLED. 환불 키는 마감 일시로
- [x] **CANCELLED 이벤트:** 취소 품목과 수량을 싣고, 이벤트 아이디는 그 취소의 환불 키에서 만든다

## 6. 풀필먼트 (설계 05)

- [x] **출고 대상 소비자:** PAID 는 없을 때만 삽입(품목은 모두 대기 수량, 배정 회차는 비움. 배송지, 권역, paid_at 은 이벤트에서). CANCELLED 는 사유가 고객 취소일 때만 대기 수량을 취소 수량으로 옮긴다. 모르는 주문이면 취소 표시 행을 남기고 뒤늦은 PAID 가 되살리지 않는다
- [x] **대상 확정 스텝:** 주문 서비스 목록과 대조, 빠진 주문 삽입, 취소 표시와 대기 수량 취소. 배정 회차가 빈 대기 수량은 목록 주문만, 배정 회차가 지난 대기 수량(이월)은 모두 이번 회차로. 끝나면 할당 입력 표에 고정
  - 앞 회차 잡이 끝나지 않았으면 시작하지 않고 경보
  - 주문 수가 같으면 TARGET_FIXED. 세 번 다르면 `target_fix_diff` 에 차이를 남기고 실패와 경보
  - 완료 조건 1: PAID 이벤트를 처리 실패 토픽으로 보낸 주문도 출고 대상에 오른다
  - 완료 조건 2: 다음 회차의 할당이 입력을 읽은 뒤에 이월해도, 그 수량이 그다음 회차에 오른다
  - 완료 조건 3: 마감 뒤 23:04 에 결제해 23:10 전에 등록된 주문은 이번 회차에 오르지 않고 다음 회차에 오른다
  - 완료 조건 4: 마감 전에 취소됐는데 CANCELLED 가 늦은 주문은 출고되지 않는다
- [x] **할당 스텝:** 할당 입력 표와 처음 한 번만 고정한 스냅샷으로 1차, 2차, 3차 순으로 배정. 결과와 판정만 1,000행씩 커밋하고 품목 수량은 바꾸지 않는다. 끝나면 ALLOCATED
  - 완료 조건: 저장 중간에 죽이고, 그사이 입고와 이월을 넣고, 재시작해도 결과가 처음 계산과 같다
- [x] **판정 발행 스텝:** 판정을 주문 단위로 묶어, 주문마다 대기 수량을 못 채움 수량으로 옮기고 UNFILLABLE 하나를 쓰는 일을 한 트랜잭션에. 이벤트 아이디는 (주문번호, 마감 시각)
- [x] **출고 지시 스텝:** 센터별 파티션 4개, 주문 500건씩 한 트랜잭션. 청크 스킵 대신 쓰기 전에 잠그고 확인해 예외로 남긴다. (센터, 주문) 단위로 묶어 읽고, 출고 지시, 실물 재고 차감, 대기 수량을 출고 수량으로 옮기는 일을 한 트랜잭션에. 예외는 예외 기록과 예외 수량 이동을 한 트랜잭션에. 이미 있으면 건너뛴다
  - 완료 조건 1: 한 품목 3개가 서울 2, 김포 1로 나뉘고 김포만 예외면 출고 2, 예외 1 이 된다 (테스트는 서울 A 2, 서울 B 1)
  - 완료 조건: 중간에 실패시킨 뒤 재시작하면 남은 것만 처리되고, 출고 지시와 재고 차감이 두 번 일어나지 않는다
- [x] **결과 검증 스텝:** 입력 수량 = 결과 + 판정, 결과 = 출고 + 예외, 예외 0.1% 이하를 수량으로 확인. 넘으면 VERIFY_FAILED 와 경보
- [x] **관리 API:** 사람이 개입하는 풀필먼트 경로를 모두 만든다
  - 출고 예외의 이월과 관리자 취소. 둘 다 OPEN 조건부이고 취소는 EXCEPTION_CANCELLED 를 낸다
  - 배차 전 출고 지시 취소. 실물 재고를 되돌리고 출고 수량을 예외 수량으로 옮긴다
  - 검증 실패 회차의 승인, 대상 확정 차이 목록(`target_fix_diff`) 조회와 출고 대상 보정, 출고 대상 배송지 수정
  - 완료 조건: 한 예외에 이월과 취소를 동시에 보내도 한쪽만 일어난다
- [x] **입고와 실사:** 실사는 센 수량에서 (전산 실물 + 피킹 전 출고 지시 수량)을 뺀 차이로 반영. 실물 재고, 조정 이력, 아웃박스 STOCK_CHANGED 를 한 트랜잭션에. 재고 서비스가 인박스로 받아 슬롯 모드별 규칙과 부족분 규칙으로 판매 가능 재고를 바꾼다
  - 완료 조건: 출고 지시 뒤 피킹 전에 실사를 해도 판매 가능 재고가 늘지 않는다

## 7. 운영 지표
