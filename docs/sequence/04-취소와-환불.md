# 04. 취소와 환불

고객 취소, 환불 처리, 출고 불가 환불, 늦은 승인의 환불 흐름입니다. 환불을 만드는 쪽은 언제나 주문 서비스입니다. 설계 근거는 [04 멱등성과 실패 복구](../design/04-멱등성과-실패-복구.md)와 [05 풀필먼트와 배치](../design/05-풀필먼트-배치.md)에 있습니다.

| 흐름 | 언제 |
|---|---|
| [1. 고객 취소](#1-고객-취소) | 주문이 속한 회차의 마감 전에 고객이 취소할 때 |
| [2. 환불 처리](#2-환불-처리) | 환불 요청을 접수시키고 대행사와 확정할 때 |
| [3. 출고 불가 환불](#3-출고-불가-환불) | 할당에서 못 채운 품목으로 판정될 때 |
| [4. 늦은 승인의 환불](#4-늦은-승인의-환불) | 실패로 닫은 회차를 대행사가 늦게 승인했을 때 |

---

## 1. 고객 취소

```mermaid
sequenceDiagram
    autonumber
    actor 사용자
    participant 주문
    participant 카프카 as Kafka
    participant 재고
    participant 풀필먼트

    사용자->>주문: 취소 요청
    alt 속한 회차의 마감 전
        주문->>주문: 남은 품목 모두 취소, PAID 를 CANCELLED + 환불 요청 refund-{주문번호}-cancel + 아웃박스 (한 트랜잭션)
        주문-->>사용자: 취소 접수
        주문->>카프카: order.events CANCELLED
        카프카->>재고: 취소 품목 되돌림, 예약 RESTORED
        카프카->>풀필먼트: 출고 대상을 취소로 표시
    else 마감 뒤
        주문-->>사용자: 취소 불가. 출고 후 반품 안내
    end
```

마감 뒤 고객 취소를 받지 않기 때문에, 출고 배치가 대상을 확정한 뒤 대상이 바뀌는 길은 사람이 처리하는 출고 예외뿐입니다.

---

## 2. 환불 처리

경계는 "결제 서비스가 접수했는가" 입니다. 접수시키는 일은 주문 서비스가, 대행사와 확정하는 일은 결제 서비스가 맡습니다.

```mermaid
sequenceDiagram
    autonumber
    participant 주문배치 as 주문 환불 배치
    participant 주문 as 주문 DB
    participant 결제
    participant 결제배치 as 결제 환불 배치
    participant 대행사 as 결제 대행사

    loop 1분마다
        주문배치->>주문: REQUESTED 환불 요청
        주문배치->>결제: 환불 접수 (환불 키, 금액)
        결제->>결제: 환불 키 유니크로 한 건만 생성, 회차의 환불 합이 승인 금액을 넘으면 거절
        결제-->>주문배치: 접수됨 (결제 쪽 현재 상태)
        주문배치->>주문: ACCEPTED, 이미 COMPLETED 면 COMPLETED 와 누적액
        opt 1시간 넘은 ACCEPTED
            주문배치->>결제: 환불 키로 상태 조회 후 맞춤
        end
    end

    loop 1분마다
        결제배치->>대행사: 환불 또는 조회 (같은 환불 키)
        alt 완료
            결제배치->>결제: COMPLETED + 아웃박스 REFUNDED
        else 대행사 거절
            결제배치->>결제: FAILED + 아웃박스 REFUND_FAILED, 경보
        else 1시간 넘게 모름
            결제배치->>결제: UNKNOWN, 경보 (사람이 확정)
        end
    end

    결제->>주문: payment.events REFUNDED
    주문->>주문: REQUESTED, ACCEPTED, FAILED 를 COMPLETED 로, 1행일 때만 같은 트랜잭션에서 환불 누적액 더함
    Note right of 주문: REQUESTED 는 접수 응답이 유실된 경우, FAILED 는 사람이 대행사에서 처리하고 확정한 경우
```

"기존 환불 건수 + 1" 로 키를 만들면, 재시작 때 같은 환불에 새 번호가 붙어 두 번 환불됩니다. 키는 사유에서 만듭니다.

## 3. 출고 불가 환불

판정은 풀필먼트가 하고, 환불은 주문 서비스가 합니다.

```mermaid
sequenceDiagram
    autonumber
    participant 발행 as 출고 배치 판정 발행 스텝
    participant 카프카 as Kafka
    participant 주문
    participant 재고

    Note over 발행: 할당이 ALLOCATED 로 끝난 뒤에만 실행
    발행->>발행: 판정마다 아웃박스 UNFILLABLE (이벤트 아이디는 주문번호와 마감 시각)
    발행->>카프카: fulfillment.events UNFILLABLE (주문 B 품목 1개, 주문 C 품목 전부)
    카프카->>주문: 소비
    주문->>주문: B 는 그 품목만 취소, PAID 유지, 품목 금액 환불 요청 refund-B-cutoff-2026102823 + 아웃박스 CANCELLED (품목)
    주문->>주문: C 는 모든 품목 취소, CANCELLED + 전액 환불 요청 + 아웃박스 CANCELLED
    주문->>카프카: order.events CANCELLED (B 의 품목, C 의 품목)
    카프카->>재고: 소비
    Note right of 재고: 취소 품목을 되돌림. 실사 부족분이 있으면 먼저 갚아 없는 재고를 되살리지 않음
```

환불 요청이 생긴 뒤는 2번 흐름이 처리합니다. 이벤트가 두 번 와도 환불 키 유니크라 요청은 하나입니다.

## 4. 늦은 승인의 환불

새 회차는 앞 회차가 FAILED 나 EXPIRED 일 때만 열리므로 정상이라면 승인이 둘 생기지 않습니다.
그래도 "요청 없음"으로 FAILED 를 확정한 회차를 대행사가 아주 늦게 승인하면 생깁니다. 결제 서비스는 알리기만 하고, 환불은 주문 서비스가 합니다.

```mermaid
sequenceDiagram
    autonumber
    participant 대사 as 결제 정산 대사 (하루 한 번)
    participant 결제 as 결제 DB
    participant 대행사 as 결제 대행사
    participant 주문

    대사->>대행사: 전날 정산 파일
    대행사-->>대사: 주문 D 의 회차 1 승인, 회차 2 승인
    대사->>결제: 우리 상태와 비교 (회차 1 FAILED, 회차 2 APPROVED)
    대사->>결제: 회차 1 을 APPROVED 로 바로잡음 + 아웃박스 APPROVED + 어긋남 기록, 경보
    결제->>주문: payment.events APPROVED (회차 1)
    주문->>주문: 주문 D 는 PAID, paid_round 2. 회차 1 은 쓰지 않은 승인
    주문->>주문: 환불 요청 refund-D-orphan-1 + 경보
    Note right of 주문: 이후 2번 흐름으로 환불
```

FAILED 에서 APPROVED 로 가는 전이는 정산 대사만 할 수 있습니다. 대행사의 정산이 사실이기 때문입니다.
