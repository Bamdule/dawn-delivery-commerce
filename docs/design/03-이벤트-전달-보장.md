# 03. 이벤트 전달 보장

## 요약

**무엇을 설명하나:** 주문은 커밋됐는데 이벤트가 나가지 않거나, 이벤트는 나갔는데 커밋이 롤백되는 문제를 다룹니다. 발행 쪽은 아웃박스, 받는 쪽은 인박스, 순서는 Kafka 파티션 키로 풉니다.

**이벤트 전달 보장은 무엇에 쓰나:** 발행이 빠지면 결제 완료 주문에 적립금, 알림, 출고 지시가 일어나지 않습니다. 반대로 커밋이 빠지면 없는 주문에 적립금이 붙고 출고 지시가 만들어집니다.

**세 줄 요약**
1. DB 커밋과 Kafka 발행은 원자적이지 않으므로, 이벤트를 같은 트랜잭션의 아웃박스 테이블에 씁니다.
2. 그 대가로 최소 한 번 전달이 되므로, 값을 더하는 소비에는 인박스를 두고 나머지는 조건부 갱신으로 막습니다.
3. 순서가 중요한 주문번호를 파티션 키로 쓰고, 오프셋은 처리 후 수동으로 커밋합니다.

## 문제를 정확히 세우기

> 커밋 후 발행 실패와 발행 후 커밋 롤백, 두 방향의 사고가 있습니다. 2단계 커밋 대신 원자성을 포기하고 빠뜨리지 않는 것을 보장합니다.

01번에서 주문 확정 후 이벤트를 발행하기로 했습니다. 코드로 쓰면 이렇습니다.

```java
@Transactional
public void confirmOrder(Long orderId) {
    Order order = orderRepository.findById(orderId);
    order.markPaid();                              // (1) DB 변경
    kafkaTemplate.send("order.events", order.getOrderNo(), event); // (2) Kafka 발행
}
```

**이 코드에는 두 가지 방향의 사고가 숨어 있습니다.**

**커밋은 됐는데 발행이 안 되는 경우.** `send`는 메시지를 버퍼에 넣고 바로 돌아오는 비동기 호출입니다.
브로커 전송이 나중에 실패해도 메서드는 정상으로 끝나고 (1)이 커밋됩니다.
**주문은 결제 완료인데 적립금도, 알림도, 출고 지시도 일어나지 않습니다.**
고객은 결제됐다고 보는데 물건이 오지 않습니다.

**발행은 됐는데 커밋이 안 되는 경우.** (2)는 메서드 안에서 실행되므로 커밋보다 먼저입니다.
메시지가 나간 뒤 커밋 단계에서 실패하면 (1)만 롤백됩니다.
**없는 주문에 적립금이 붙고 출고 지시가 만들어집니다.**

**근본 원인은 DB 트랜잭션과 메시지 발행이 원자적이지 않다는 것입니다.** 둘은 다른
시스템이고, 한쪽만 성공하는 순간이 반드시 존재합니다.

### 2단계 커밋을 쓰지 않는 이유

이론적으로는 분산 트랜잭션인 2단계 커밋(2PC)으로 묶을 수 있습니다. 쓰지 않습니다.

**첫째, 한 곳이 느려지면 전부 묶입니다.** 준비 단계에서 모든 참여자가 응답할 때까지
자원을 잡고 있습니다. Kafka 가 느려지면 DB 트랜잭션도 같이 길어집니다.

**둘째, 조정자가 죽으면 애매한 상태로 남습니다.** 참여자들은 커밋해야 할지 롤백해야 할지
모른 채 자원을 잡고 기다립니다. 사람이 개입해야 풀립니다.

**셋째, Kafka 는 2단계 커밋 참여자로 설계된 시스템이 아닙니다.**

그래서 **원자성을 포기하고 최종적 일관성을 받아들이는 쪽**으로 갑니다. 대신
**빠뜨리지 않는 것**을 보장합니다.

## 아웃박스 패턴

> 이벤트를 주문 상태와 같은 트랜잭션에서 아웃박스 테이블에 쓰고, 릴레이가 읽어 발행합니다. 그 결과 최소 한 번 전달이 됩니다.

### 발상

**메시지 발행을 DB 쓰기로 바꿉니다.** Kafka 로 바로 보내지 않고, **같은 트랜잭션 안에서
아웃박스 테이블에 행을 하나 넣습니다.**

```java
@Transactional
public void confirmOrder(Long orderId) {
    Order order = orderRepository.findById(orderId);
    order.markPaid();
    outboxRepository.save(new OutboxEvent(
        UUID.randomUUID(),        // event_id
        "order.events",           // topic. payload의 type으로 이벤트 종류를 구분
        order.getOrderNo(),       // partition key
        toJson(event)             // payload
    ));
}
```

**주문 상태와 이벤트 기록이 한 트랜잭션에 있으므로 둘은 함께 성공하거나 함께 실패합니다.**
문제가 해결된 것이 아니라 **원자성이 필요한 두 대상을 같은 DB 안으로 옮긴 것**입니다.
이게 이 패턴의 핵심입니다.

### 테이블

```sql
CREATE TABLE outbox_event (
    event_id     CHAR(36)     NOT NULL,
    topic        VARCHAR(100) NOT NULL,
    partition_key VARCHAR(100) NOT NULL,
    payload      JSON         NOT NULL,
    status       VARCHAR(20)  NOT NULL,   -- PENDING / SENT / FAILED
    retry_count  INT          NOT NULL DEFAULT 0,
    created_at   DATETIME(3)  NOT NULL,
    sent_at      DATETIME(3)  NULL,
    PRIMARY KEY (event_id),
    KEY idx_status_created (status, created_at)
);
```

### 발행하는 쪽

별도 릴레이가 `PENDING` 을 읽어 Kafka 에 보내고 `SENT` 로 바꿉니다.

```java
@Scheduled(fixedDelay = 500)
public void publish() {
    List<OutboxEvent> batch = outboxRepository.findPending(100);
    for (OutboxEvent e : batch) {
        try {
            kafkaTemplate.send(e.getTopic(), e.getPartitionKey(), e.getPayload()).get();
            e.markSent();
        } catch (Exception ex) {
            e.increaseRetry();          // 지수 백오프로 다음 시도
        }
    }
}
```

**여기서 최소 한 번 전달이 확정됩니다.** 발행은 성공했는데 `SENT` 로 바꾸기 전에 죽으면
**같은 이벤트가 다시 발행됩니다.** 이건 버그가 아니라 이 패턴의 성질이고,
받는 쪽에서 해결합니다.

이 코드에는 빠진 것이 둘 있습니다. 릴레이가 여러 대면 같은 행을 동시에 집어 두 번 보냅니다.
그래서 `SELECT ... FOR UPDATE SKIP LOCKED`로 서로 다른 행을 나눠 집거나, 릴레이를 한 대만 돌립니다.
또 한 건이 실패해 재시도로 밀리면 같은 키의 다음 이벤트가 먼저 나갈 수 있습니다.
순서가 중요한 이벤트는 같은 파티션 키에 앞선 `PENDING`이 남아 있으면 뒤의 것을 보내지 않습니다.

### 폴링이냐 CDC냐

| 방식 | 어떻게 | 장점 | 단점 |
|---|---|---|---|
| **폴링** | 스케줄러가 테이블을 조회 | 단순하고 의존성이 없음 | 지연이 폴링 주기만큼, DB 부하 |
| **CDC** | Debezium 이 트랜잭션 로그를 읽음 | 지연이 짧고 DB 조회 부하 없음 | 인프라가 늘고 운영이 어려움 |

**시작은 폴링이 맞습니다.** 500ms 주기면 대부분의 알림과 적립에 충분하고,
운영할 것이 하나도 늘지 않습니다. **지연이 문제가 되거나 아웃박스 조회가 부하가 될 때
CDC 로 옮기면 됩니다.** 처음부터 CDC 를 넣으면 없던 운영 부담이 생깁니다.

### 정리 배치가 반드시 필요합니다

`SENT` 행이 계속 쌓이면 테이블이 커지고 `idx_status_created` 조회가 느려집니다.
**보존 기간을 정해 지우는 배치를 함께 만들어야 합니다.**

## 인박스 패턴: 받는 쪽의 멱등

> 처리한 이벤트 아이디를 컨슈머별로 기록하고, 이미 있으면 건너뜁니다. 처리 자체가 멱등하면 인박스 없이 조건부 갱신으로 충분합니다.

아웃박스 때문에 **같은 이벤트가 두 번 올 수 있습니다.** 적립금이 두 번 붙거나 재고가
두 번 확정되면 안 됩니다.

**해법은 처리한 이벤트 아이디를 기록하고, 이미 있으면 건너뛰는 것입니다.**

```sql
CREATE TABLE inbox_event (
    event_id    CHAR(36)    NOT NULL,
    consumer    VARCHAR(50) NOT NULL,   -- 어느 컨슈머가 처리했는지
    processed_at DATETIME(3) NOT NULL,
    PRIMARY KEY (consumer, event_id)
);
```

```java
@Transactional
public void handle(OrderPaidEvent event) {
    try {
        inboxRepository.insert(event.getEventId(), "point-service");
    } catch (DuplicateKeyException e) {
        return;                          // 이미 처리했다
    }
    pointService.earn(event.getMemberId(), event.getAmount());
}
```

**중요한 것은 인박스 기록과 실제 처리가 같은 트랜잭션에 있어야 한다는 점입니다.**
따로 두면 기록은 됐는데 처리가 안 되거나 반대가 됩니다. **같은 트랜잭션에 두면
기록과 처리가 함께 성공하거나 함께 실패**하고, 실패하면 다시 소비되어 재처리됩니다.

**컨슈머별로 키를 나눈 이유**는 같은 이벤트를 여러 서비스가 각자 처리하기 때문입니다.
적립금 서비스가 처리했다고 알림 서비스가 건너뛰면 안 됩니다.

**인박스도 정리 배치가 필요합니다.** 다만 보존 기간을 재발행 가능 기간보다 길게 잡아야
합니다. 너무 빨리 지우면 늦게 온 중복을 못 걸러냅니다.

### 도메인 조건으로 대신할 수 있으면 그게 낫습니다

모든 소비에 인박스를 붙일 필요는 없습니다. **처리 자체가 이미 멱등하면 표가 필요 없습니다.**

- 주문 상태를 `PAID` 로 바꾸는 일은 두 번 해도 결과가 같습니다
- 예약을 확정으로 바꾸는 일도 조건부 갱신으로 쓰면 두 번째는 0행이 됩니다

```sql
UPDATE stock_reservation
   SET status = 'CONFIRMED'
 WHERE reservation_id = :id AND status = 'HELD'
```

0행이 나오면 바로 중복으로 넘기지 않고 예약 상태를 다시 읽습니다.
`CONFIRMED`면 중복이라 넘기고, 만료로 풀린 상태면 결제한 주문에 재고가 없다는 뜻이라 경보를 냅니다.

**반면 값을 더하는 일은 멱등하지 않습니다.** 적립금 적립과 카운터 증가가 그렇습니다.
이런 것에만 인박스를 씁니다.

알림 발송은 인박스로도 완전히 막히지 않습니다. 알림은 외부로 나가서 DB 트랜잭션에 묶이지 않습니다.
보낸 뒤 커밋이 실패하면 다시 소비되어 한 번 더 갑니다.
그래서 이벤트 아이디를 발송 대행사의 중복 방지 키로 넘기거나, 드물게 두 번 가는 것을 받아들입니다.

## Kafka 파티션과 순서

> Kafka는 파티션 안에서만 순서를 보장하므로 주문번호를 키로 씁니다. 오프셋은 처리 후 수동으로 커밋합니다.

### 순서가 보장되는 범위

**Kafka 는 파티션 안에서만 순서를 보장합니다.** 토픽 전체의 순서는 보장하지 않습니다.

그래서 **순서가 중요한 단위를 파티션 키로 잡습니다.**

```java
kafkaTemplate.send("order.events", order.getOrderNo(), payload); // payload.type: PAID, CANCELLED
```

주문번호를 키로 쓰면 **같은 주문의 이벤트는 `order.events` 토픽의 같은 파티션에 들어가 순서대로 처리됩니다.**
`payload.type`이 `PAID`인 이벤트 다음에 `CANCELLED`가 오면 그 순서대로 봅니다. 서로 다른 토픽의 메시지 사이에는 순서 보장이 없습니다.

**상품번호를 키로 쓰면 안 되는 이유**가 여기서 나옵니다. 재고 이벤트를 상품번호로 키를
잡으면 인기 상품의 이벤트가 한 파티션에 몰립니다. **02번에서 본 핫키 문제가 Kafka 에서
재현됩니다.** 파티션 하나의 컨슈머 랙(처리 지연량)만 쌓입니다.

### 파티션 수를 정하는 기준

**파티션 수가 병렬 처리의 상한입니다.** 한 파티션에는 컨슈머 그룹 내에서 컨슈머 하나만
붙습니다. 파티션이 3개면 컨슈머를 10개 띄워도 7개는 놀고 있습니다.

**파티션은 늘릴 수만 있고 줄일 수 없습니다.** 늘리더라도 키가 가는 파티션이 바뀌어 같은 키의 순서가
잠시 깨집니다. 그래서 처음에 넉넉하게 잡습니다.
다만 **너무 많으면 순서 보장 단위가 쪼개지고 리밸런싱이 오래 걸립니다.**

### 오프셋 커밋 시점

| 방식 | 사고 유형 |
|---|---|
| 자동 커밋 | poll 루프 안에서 동기로 처리하면 다음 poll 때 직전 묶음을 커밋하므로 최소 한 번. 처리를 다른 스레드로 넘기면 처리 전에 커밋돼 잃을 수 있음 |
| 처리 후 수동 커밋 | 커밋 전에 죽으면 **다시 소비합니다** |

Spring Kafka의 기본 처리 방식은 리스너 처리가 끝난 뒤 오프셋을 커밋합니다. **후자를 고릅니다.** 잃는 것보다 중복이 낫고, 중복은 위의 인박스와 조건부 갱신으로
이미 막아 뒀기 때문입니다.

**이 선택이 앞의 모든 설계와 이어집니다.** 최소 한 번 전달을 받아들이고 소비 쪽을
멱등하게 만드는 것이 일관된 전략입니다. **정확히 한 번을 전달로 보장하려 하지 말고
처리로 보장합니다.**

## 정리: 이 시스템의 선택

> 일곱 가지 결정과 포기한 것을 모았습니다. 정확히 한 번은 전달이 아니라 처리로 보장한다는 전략으로 이어집니다.

| 결정 | 선택 | 포기한 것 |
|---|---|---|
| DB 와 발행의 원자성 | **아웃박스로 같은 DB 안으로 옮김** | 즉시 발행. 폴링 주기만큼 지연 |
| 발행 방식 | **폴링으로 시작** | CDC 의 짧은 지연 |
| 전달 보장 | **최소 한 번** | 정확히 한 번의 단순함 |
| 중복 처리 | **값을 더하는 소비에만 인박스**, 나머지는 조건부 갱신 | 일괄 적용의 단순함 |
| 순서 | **주문번호를 파티션 키로** | 토픽 전체 순서 |
| 오프셋 | **처리 후 수동 커밋** | 중복 소비 없는 상태 |
| 정리 | **아웃박스와 인박스 모두 보존 배치 필수** | 없음. 안 만들면 반드시 문제가 됩니다 |
