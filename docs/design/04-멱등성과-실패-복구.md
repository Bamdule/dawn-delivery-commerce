# 04. 멱등성과 실패 복구

## 요약

**무엇을 설명하나:** 결제 대행사 호출이 3초 뒤 타임아웃 났을 때, 이중 결제도 돈만 빠진 주문도 만들지 않는 방법입니다.
멱등키와 결제 회차, 미결 상태와 그 결과를 주문까지 끌고 가는 경로, 재시도 구분, 환불을 차례로 봅니다.

**세 줄 요약**
1. 외부 호출 결과는 성공, 실패, 모름 세 가지이고, 모름을 실패로 단정하는 것이 사고의 원인입니다.
2. 멱등키는 주문번호와 결제 회차로 만들고, 새 회차는 가장 최근 회차가 실패로 확정됐을 때만 엽니다.
3. 결제 서비스는 승인된 회차를 모두 이벤트로 알리고, 주문이 쓰지 않은 승인은 주문 서비스가 환불까지 책임집니다.

---

## 문제를 정확히 세우기

> 결제 호출이 타임아웃 나면 승인 여부를 알 수 없습니다. 재시도하면 이중 결제가, 실패로 처리하면 돈만 빠진 주문이 생깁니다.

주문 하나에 45,000원을 결제합니다. 대행사 호출이 3초 뒤 타임아웃 났습니다. 세 가지 경우가 모두 가능합니다.

1. 요청이 대행사에 닿지 않았다 (승인 안 됨)
2. 요청이 닿아 승인됐는데 응답이 유실됐다 (45,000원 빠짐)
3. 대행사가 아직 처리 중이다 (곧 승인됨)

새 요청으로 재시도하면 2번일 때 90,000원이 빠집니다. 실패로 처리하면 2번일 때 돈은 빠졌는데 주문이 없습니다.

---

## 멱등키와 결제 회차

> 같은 회차의 재시도는 같은 키로 보내 승인을 한 번으로 만듭니다. 새 회차는 가장 최근 회차가 실패로 확정됐을 때만 엽니다.

### 키

```
POST /payments
Idempotency-Key: order-20261028-000123-payment-1
{ "amount": 45000, "method": "CARD" }
```

대행사는 같은 키로 온 요청을 이미 처리했으면 새로 처리하지 않고 처음 결과를 돌려줍니다.
`UUID.randomUUID()` 로 키를 만들면 재시도할 때마다 키가 바뀌어 소용이 없습니다.

### 재시도와 다시 결제하기는 다릅니다

- **재시도:** 타임아웃 뒤 같은 요청을 다시 보내는 것입니다. 같은 회차, 같은 키를 씁니다
- **다시 결제하기:** 카드가 거절돼 사용자가 다른 카드로 결제하는 것입니다. 새 결제라 회차를 올립니다

### 새 회차를 여는 조건

회차를 아무 때나 열면 이중 결제가 다시 생깁니다.

| 시각 | 일어난 일 |
|---|---|
| 22:58:04 | 1회차가 타임아웃으로 REQUESTED |
| 22:58:20 | 사용자가 다른 카드로 2회차 승인 |
| 22:58:40 | 조회 배치가 1회차도 승인됐음을 확인. 두 번 결제 |

회차 번호는 주문 서비스가 정하고(01번), 결제 서비스는 그 주문의 회차 행을 잠근 뒤 검사합니다.

- 요청에 실린 결제 기한이 지났으면 열지 않습니다(02번 "결제 기한")
- 기존 회차보다 큰 번호이고, 가장 최근 회차가 FAILED 일 때만 엽니다. 회차가 없으면 엽니다
- 가장 최근 회차가 REQUESTED 나 UNKNOWN 이면 거절하고 "결제 확인 중" 으로 답합니다
- 가장 최근 회차가 APPROVED 면 거절하고 이미 결제됐다고 답합니다

### 대행사가 멱등키를 지원하지 않으면

`payment` 테이블의 `(order_no, payment_round)` 유니크 제약으로 막습니다.
같은 회차를 두 번 만들려 하면 삽입이 실패하고 이미 있는 결제를 돌려줍니다.
이 경우 같은 회차의 재시도는 대행사에 다시 보내지 않고, 조회로만 결과를 확인합니다.

## 동기 경로에서는 한 번만 부릅니다

> 사용자가 기다리는 동안 결제 서비스는 대행사를 한 번만 부릅니다. 모호한 결과는 모두 REQUESTED 로 남기고 뒤에서 확정합니다.

```java
public PaymentResult approve(ApproveCommand command) {
    Payment payment = paymentWriter.openRound(command);          // 짧은 트랜잭션. 기한과 회차 규칙 검사
    PgResult result = pgClient.approve(payment.toRequest());     // 트랜잭션 밖, 타임아웃 3초
    return paymentWriter.record(payment.getId(), result);        // 짧은 트랜잭션. 상태와 아웃박스
}
```

| 대행사 결과 | 결제 상태 | 주문에게 주는 답 |
|---|---|---|
| 승인 | APPROVED | 승인 |
| 잔액 부족, 유효하지 않은 카드 같은 거절 | FAILED | 거절 |
| 타임아웃, 연결 끊김, 5xx | REQUESTED | 모름 |
| 동시 호출 한도(600) 초과, 회로 차단기 열림 | FAILED (사유: 호출 안 함) | 거절. 잠시 뒤 다시 결제 안내 |

5xx 도 모름으로 둡니다. 대행사가 처리한 뒤 오류를 냈을 수 있기 때문입니다.
동기 경로 안에서 백오프 재시도를 하면 사용자가 30초 넘게 기다리고, 주문 서비스의 5초 타임아웃과 엇갈립니다.
주문 서비스가 포기한 뒤 결제 서비스가 승인을 기록하는 일이 그렇게 생깁니다.

## 미결 상태를 확정하고 주문까지 반영하기

> 결제 서비스가 REQUESTED 를 확정하고 이벤트로 알립니다. 주문 서비스는 이벤트를 받고, 놓친 것은 정리 배치로 직접 물어 확정합니다.

### 결제 서비스: 조회 배치

```java
@Scheduled(fixedDelay = 10_000)
public void resolveRequested() {
    for (Payment payment : paymentRepository.findRequestedDue()) {
        PgStatus status = pgClient.inquire(payment.getIdempotencyKey());   // 회차를 정확히 지목
        if (status.isApproved()) {
            paymentWriter.approve(payment, status);          // APPROVED + 아웃박스 APPROVED
        } else if (status.isNotFound() && payment.lastSentBefore(PG_MAX_PROCESSING)) {
            paymentWriter.fail(payment, "대행사에 요청 없음");  // FAILED + 아웃박스 FAILED
        } else if (payment.requestedBefore(Duration.ofMinutes(10))) {
            paymentWriter.markUnknown(payment);               // 사람이 확인, 경보
        }
    }
}
```

- **조회는 멱등키로 합니다.** 주문번호로 조회하면 2회차 승인을 1회차 결과로 잘못 읽을 수 있습니다
- **"요청 없음"은 마지막 전송에서 60초가 지난 뒤에만 믿습니다.** 처음 요청 시각으로 세면, 50초에 다시 보낸 요청이 처리 중인데 실패로 닫습니다(01 규모 가정의 최대 처리 시간)
- **멱등키를 지원하는 대행사면 5xx 건은 같은 키로 다시 보냅니다.** 1초부터 두 배씩, 지터를 더해 최대 다섯 번입니다. 보낼 때마다 마지막 전송 시각을 갱신합니다
- **결과는 모두 결제 아웃박스로 payment.events 에 냅니다**

### 주문 서비스: 이벤트와 정리 배치

payment.events 의 APPROVED 에는 회차 번호가 실립니다. 주문 서비스는 주문 상태에 따라 나눕니다.

| 주문 상태 | 하는 일 |
|---|---|
| PENDING | PAID 로 바꾸고 승인 회차를 `paid_round` 에 기록, 아웃박스 PAID (1행일 때만) |
| PAID 이고 `paid_round` 가 같은 회차 | 중복. 넘김 |
| PAID 이고 다른 회차, 또는 FAILED, CANCELLED | 주문이 쓰지 않은 승인. 환불 요청 `refund-{주문번호}-orphan-{회차}` 와 경보 |

마지막 줄은 설계대로면 생기지 않아야 합니다. 새 회차는 앞 회차가 FAILED 일 때만 열리기 때문입니다.
그래도 대행사가 FAILED 로 닫은 회차를 아주 늦게 승인하면 생깁니다. 그때도 돈이 새지 않게 하는 안전망입니다.

FAILED 이벤트를 받으면 주문은 PENDING 그대로 둡니다. 예약 유지 시간 안에 다음 회차를 받을 수 있습니다.

**정리 배치 (1분 주기):** 2분 넘은 PENDING 주문을 결제 서비스에 직접 묻습니다.
이벤트를 놓쳤거나, 승인 응답을 받고 PAID 를 커밋하기 전에 주문 서비스가 죽은 경우를 잡습니다.

| 결제 서비스의 답 | 정리 배치가 하는 일 |
|---|---|
| 승인된 회차 있음 | PAID 로 확정, 아웃박스 PAID |
| 가장 최근 회차 FAILED 또는 회차 없음, 주문 후 예약 유지 시간 + 2분 지남 | FAILED 로 닫음. 예약은 재고 만료 배치가 이미 풀었고, 결제 기한이 지나 새 회차도 열릴 수 없음 |
| REQUESTED 또는 UNKNOWN | 기다림. 15분 넘으면 경보 |

세 경로(동기 응답, 이벤트, 정리 배치)가 같은 주문을 확정하려 해도 조건부 갱신이라 한 번만 바뀝니다.

### 대행사 정산 대사

하루 한 번 대행사 정산 파일과 결제 테이블을 맞춰 봅니다.
대행사에는 승인인데 우리는 FAILED 인 회차를 찾으면, 그 회차를 APPROVED 로 바로잡고 아웃박스 APPROVED 를 씁니다.
FAILED 에서 APPROVED 로 가는 전이는 이 대사만 할 수 있습니다. 대행사의 정산이 사실이기 때문입니다.
이벤트를 받은 주문 서비스가 위 표의 마지막 줄대로 환불합니다. 결제 서비스가 스스로 환불을 시작하지 않으므로 환불의 주인은 하나입니다.

## 회로 차단기와 동시 호출 한도

**동시 호출 한도:** 대행사로 가는 동시 호출을 600으로 묶습니다(01번 "스레드와 커넥션"). 넘는 요청은 기다리지 않고 거절합니다.

**회로 차단기:** 최근 100건 중 50% 이상이 타임아웃, 5xx, 2초 넘는 느린 호출이면 회로를 엽니다.
카드 거절은 대행사가 정상으로 답한 것이라 세지 않습니다.
열린 동안은 대행사를 부르지 않고 바로 거절로 답하고, 30초 뒤 소수의 요청만 흘려 회복을 확인합니다.
호출하지 않았으니 결과가 확실한 실패라 REQUESTED 가 아니라 FAILED 입니다.

느린 호출을 세는 이유는 대행사가 2.5초씩 걸리며 겨우 답하는 상태를 잡기 위해서입니다.
타임아웃(3초)이 나지 않아 실패율로는 열리지 않는데, 그동안 커넥션 500개가 묶입니다.

## 보상: 되돌릴 수 없는 것을 되돌리는 법

> 외부에 반영된 것은 롤백되지 않습니다. 되돌리기 비싼 것을 뒤로 미루고, 그래도 되돌려야 하면 환불로 상쇄합니다.

### 순서를 바꿔 되돌리기 비싼 것을 나중에 합니다

```
주문 저장 (PENDING)     <- 되돌릴 수 있음
재고 예약 (HELD)        <- 되돌릴 수 있음 (만료)
결제 시작 (PAYING)      <- 되돌릴 수 있음 (HELD 로)
결제 승인               <- 되돌리기 비쌈 (환불)
주문 확정 (PAID)        <- 짧고 실패하기 어려운 작업
```

결제 승인 뒤에는 짧은 갱신만 남깁니다. 그것마저 실패하면 위의 정리 배치가 PAID 로 마무리합니다.

### 환불은 주문 서비스가 끝까지 책임집니다

환불이 생기는 경우는 넷입니다. 모두 주문 서비스가 환불 요청을 만듭니다.

| 경우 | 환불 키 | 금액 |
|---|---|---|
| 마감 전 고객 취소 | `refund-{주문번호}-cancel` | 남은 결제 금액 전부 |
| 출고 불가 (05번) | `refund-{주문번호}-cutoff-{마감일시}` | 못 채운 금액 |
| 관리자 취소 (출고 예외) | `refund-{주문번호}-admin` | 남은 결제 금액 전부 |
| 주문이 쓰지 않은 승인 | `refund-{주문번호}-orphan-{회차}` | 그 회차 금액 |

**환불 키는 다시 계산해도 같아야 합니다.** "기존 환불 건수 + 1" 처럼 세어서 만들면, 재시작 때 같은 환불에 새 번호가 붙어 두 번 환불됩니다.

일은 두 서비스가 나눠 맡습니다. 경계는 "결제 서비스가 접수했는가" 입니다.

| 단계 | 주인 | 하는 일 |
|---|---|---|
| 1. 요청 기록 | 주문 서비스 | 주문 상태 변경과 환불 요청 행(REQUESTED)을 한 트랜잭션에 씀 |
| 2. 접수 | 주문 서비스 환불 배치 | 결제 서비스가 접수할 때까지 같은 키로 보냄. 접수되면 ACCEPTED |
| 3. 대행사 확정 | 결제 서비스 환불 배치 | 같은 키로 대행사에 환불하고 조회. 결과는 payment.events 의 REFUNDED 나 REFUND_FAILED |
| 4. 반영 | 주문 서비스 | 환불 요청을 COMPLETED 나 FAILED 로 바꾸고, 1행일 때만 같은 트랜잭션에서 주문의 환불 누적액을 더함 |

- **결제 서비스의 `refund` 는 환불 키 유니크입니다.** 같은 키로 두 번 접수해도 한 건입니다
- **누적액은 완료 때 더합니다.** 요청 때 더하면 대행사가 거절한 환불도 환불된 것으로 보입니다. 상태 전이가 1행일 때만 더해서 이벤트가 두 번 와도 한 번 더합니다
- **대행사가 거절하면 FAILED, 1시간 넘게 모르면 UNKNOWN 입니다.** 둘 다 경보를 내고 사람이 관리 API로 확정합니다

### 단계가 늘어나면

지금 보상은 환불 하나라 상태 표와 배치로 충분합니다.
보상 단계가 늘고 분기가 생기면 그때 사가(Saga, 여러 단계의 진행과 보상을 기록하는 방식)를 도입합니다.

## 정리: 이 시스템의 선택

| 결정 | 선택 | 포기한 것 |
|---|---|---|
| 외부 호출 결과 | **성공, 실패, 모름 세 가지**, 5xx 도 모름 | 두 가지로 단순화하는 편의 |
