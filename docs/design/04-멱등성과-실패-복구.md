# 04. 멱등성과 실패 복구

## 요약

**무엇을 설명하나:** 결제 대행사 호출이 3초 뒤 타임아웃 났을 때, 이중 결제도 돈만 빠진 주문도 만들지 않는 방법을 다룹니다. 멱등키, 미결 상태, 재시도 구분, 보상 트랜잭션을 차례로 봅니다.

**멱등성과 실패 복구는 무엇에 쓰나:** 외부 시스템을 호출하는 모든 곳에 같은 문제가 있습니다. 결제만이 아니라 재고 확정, 알림 발송, 배송사 접수가 모두 같습니다.

**세 줄 요약**
1. 외부 호출 결과는 성공, 실패, 모름 세 가지이고, 모름을 실패로 단정하는 것이 사고의 원인입니다.
2. 주문번호 기반 멱등키로 재시도를 안전하게 하고, 결과를 모르면 미결로 남겨 조회 배치가 확인합니다.
3. 되돌리기 비싼 일은 뒤로 미루고, 그래도 되돌려야 하면 환불 같은 반대 작업으로 상쇄합니다.

## 문제를 정확히 세우기

> 결제 호출이 타임아웃 나면 승인 여부를 알 수 없습니다. 재시도하면 이중 결제가, 실패로 처리하면 돈만 빠진 주문이 생길 수 있습니다.

주문 API 가 결제 대행사를 호출합니다. **3초 뒤 타임아웃이 났습니다.**

**이때 승인이 됐는지 안 됐는지 알 수 없습니다.** 세 가지 경우가 모두 가능합니다.

1. 요청이 대행사에 닿지 않았다 (승인 안 됨)
2. 요청이 닿아 승인됐는데 응답이 유실됐다 (승인 됨, 돈 빠짐)
3. 대행사가 처리 중이다 (곧 승인 됨)

**여기서 재시도하면 2번인 경우 이중 결제가 됩니다.** 반대로 실패로 처리하면 2번인 경우
**돈은 빠졌는데 주문이 없습니다.** 어느 쪽도 안전하지 않습니다.

**이 문제는 외부 시스템을 호출하는 모든 곳에서 생깁니다.** 결제만이 아니라 재고 확정,
알림 발송, 배송사 접수가 모두 같습니다.

---

## 멱등키: 같은 요청을 두 번 보내도 한 번만 처리되게

> 요청에 주문번호 기반의 고유 키를 붙이면 재시도해도 승인은 한 번입니다. 대행사가 지원하지 않으면 유니크 제약으로 막습니다.

### 발상

**요청에 고유한 키를 붙여 보냅니다.** 대행사는 같은 키로 온 요청을 이미 처리했으면
**새로 처리하지 않고 처음 결과를 그대로 돌려줍니다.**

```
POST /payments
Idempotency-Key: order-20260910-000123-payment-1
{ "amount": 45000, "method": "CARD" }
```

이러면 타임아웃 후 **안심하고 재시도할 수 있습니다.** 이미 승인됐으면 승인 결과가 오고,
안 됐으면 그때 승인됩니다. **어느 경우든 결과는 승인 한 번입니다.**

### 키를 무엇으로 만드는가

**주문번호처럼 그 요청을 유일하게 식별하는 값**이어야 합니다.
`UUID.randomUUID()` 를 쓰면 안 됩니다. **재시도할 때 새 키가 생겨서 멱등성이 사라집니다.**

```java
// 재시도해도 같은 키. 결제 회차는 사용자가 결제를 새로 시작할 때만 올린다
String idempotencyKey = "order-" + order.getOrderNo() + "-payment-" + paymentRound;
```

**재시도와 다시 결제하기는 다릅니다.** 타임아웃 뒤 같은 요청을 다시 보내는 재시도는 같은 키를 씁니다.
카드가 거절돼 사용자가 다른 카드로 다시 결제하는 것은 새 결제라 키가 달라야 합니다.
그래서 키에 결제 회차를 넣습니다. 회차는 결제를 새로 시작할 때만 올리고, 재시도 때는 올리지 않습니다.

### 대행사가 멱등키를 지원하지 않으면

**우리 쪽에서 상태로 막습니다.**

```java
public PaymentResult pay(Order order) {
    Payment payment = paymentService.createIfAbsent(order.getOrderNo(), paymentRound); // 짧은 트랜잭션
    if (payment.isAlreadyCreated()) return payment.toResult();

    PgResponse response = pgClient.approve(payment.toRequest()); // 트랜잭션 밖 외부 호출
    return paymentService.recordResult(payment.getId(), response); // 짧은 트랜잭션
}
```

`createIfAbsent`와 `recordResult`는 각각 짧은 트랜잭션으로 실행합니다. 결제 대행사를 기다리는 동안 DB 커넥션을 잡지 않습니다.

`payment` 테이블에 `(order_no, payment_round)` 유니크 제약을 겁니다.
같은 회차의 두 번째 시도는 삽입이 실패해 이미 있는 결제를 찾아 반환합니다.

**그래도 3번 경우(대행사 처리 중)는 남습니다.** 우리는 시도 기록만 있고 결과를 모릅니다.
그래서 **결과를 확인하는 조회 API 가 필요하고, 그걸 주기적으로 물어보는 배치가 필요합니다.**
이게 다음 절입니다.

## 미결 상태를 남기고 나중에 확인하기

> 타임아웃은 실패로 단정하지 않고 `REQUESTED`로 남깁니다. 조회 배치가 결과를 묻고, 한도를 넘기면 `UNKNOWN`으로 사람에게 넘깁니다.

**타임아웃이 났을 때 성공도 실패도 아닌 상태로 남깁니다.**

```
결제 상태
  REQUESTED  -> 요청을 보냈고 결과를 모른다
  APPROVED   -> 승인 확인
  FAILED     -> 실패 확인
  UNKNOWN    -> 재시도 한도를 넘겨 사람이 봐야 한다
```

```java
try {
    PgResponse res = pgClient.approve(request);
    payment.approve(res);
} catch (TimeoutException e) {
    payment.markRequested();       // 실패로 단정하지 않는다
}
```

그리고 **조회 배치가 `REQUESTED` 를 주워 대행사에 결과를 물어봅니다.**

```java
@Scheduled(fixedDelay = 30_000)
public void reconcile() {
    for (Payment p : paymentRepository.findRequestedOlderThan(Duration.ofSeconds(30))) {
        PgStatus status = pgClient.inquire(p.getOrderNo());
        if (status.isApproved())      p.approve(status);
        else if (status.isNotFound()) p.fail("대행사에 요청이 없음");
        else if (p.exceededRetry())   p.markUnknown();   // 사람이 확인
    }
}
```

**여기가 가장 중요한 설계 판단입니다.** 외부 호출은 성공과 실패 두 가지가 아니라
**성공, 실패, 모름 세 가지**입니다. **모름을 실패로 단정하는 것이 사고의 원인**이 됩니다.

재시도가 소진된 건은 확인 필요 상태로 남기고, 사람이 승인 여부를 확인할 수 있게 합니다.

## 재시도: 무엇을 다시 시도하고 무엇을 하지 않는가

> 일시적 실패만 재시도하고 영구적 실패는 재시도하지 않습니다. 재시도에는 백오프와 지터, 한도를 두고, 계속 실패하면 회로 차단기로 멈춥니다.

**모든 실패를 재시도하면 안 됩니다.** 재시도해도 결과가 같은 실패가 있습니다.

| 실패 종류 | 예 | 재시도 |
|---|---|---|
| **일시적** | 커넥션 리셋, 5xx, 락 대기 초과 | 멱등키를 지원하는 대행사일 때만 한다 |
| **영구적** | 잔액 부족, 유효하지 않은 카드, 400, 검증 실패 | **하지 않는다** |
| **모름** | 결제 승인 타임아웃, 응답 없음 | **조회로 확인한다** |

```java
try {
    pgClient.approve(request);
} catch (PgBusinessException e) {
    payment.fail(e.getCode());        // 잔액 부족 같은 것. 재시도 무의미
    throw new NonRetryableException(e);
} catch (TimeoutException e) {
    payment.markRequested();           // 승인 여부를 모름. 조회로 확인
} catch (PgSystemException e) {
    throw new RetryableException(e);   // 멱등키를 지원하는 대행사일 때만 재시도
}
```

성공할 수 없는 비즈니스 예외까지 재시도하면 처리 실패 큐만 쌓입니다. 재시도 가능 여부를
예외 종류와 대행사의 멱등키 지원 여부로 구분합니다.

### 백오프와 한도

**즉시 재시도를 반복하면 상대를 더 밀어붙입니다.** 상대가 부하로 죽어 가는 중이면
재시도가 사망을 앞당깁니다.

```
1회: 1초 후
2회: 2초 후
3회: 4초 후
4회: 8초 후 (+ 무작위 지터)
이후: 포기하고 UNKNOWN 으로 남김
```

**지터를 넣는 이유**는 동시에 실패한 요청들이 같은 시각에 다시 몰리는 것을 막기 위해서입니다.
지터가 없으면 재시도가 파도처럼 몰려옵니다.

재시도는 내 서비스만의 처리량이 아니라 상대 시스템의 수용량까지 고려해 설계합니다.

### 회로 차단기

상대가 계속 실패하면 **아예 호출을 멈추는 것**이 낫습니다. 실패율이 임계값을 넘으면
회로를 열어 즉시 실패시키고, 일정 시간 후 소수의 요청만 흘려 회복을 확인합니다.

**왜 필요한가.** 상대가 죽었는데 계속 호출하면 **내 스레드와 커넥션이 타임아웃을 기다리며
묶입니다.** 결제 대행사 하나가 죽어서 주문 API 전체가 멈추는 상황이 이렇게 생깁니다.

## 보상 트랜잭션: 되돌릴 수 없는 것을 되돌리는 법

> 외부에 반영된 것은 롤백되지 않습니다. 되돌리기 비싼 것을 뒤로 미루고, 불가능하면 반대 작업으로 상쇄하며 그 진행을 표로 남깁니다.

### 문제

주문 흐름을 처음 떠올리기 쉬운 순서(예약, 결제, 저장)로 두었다고 하겠습니다. 이때 **재고 예약은 성공했고 결제도 성공했는데 주문 저장이 실패**했습니다.
결제는 이미 대행사에서 승인됐습니다. **롤백할 수 없습니다.**

**외부 시스템에 이미 반영된 것은 트랜잭션으로 되돌아가지 않습니다.**
DB 롤백은 우리 DB만 되돌립니다. 대행사에 남은 승인은 그대로입니다.

### 두 가지 해법

**해법 1. 순서를 바꿔 되돌리기 비싼 것을 나중에 합니다.**

되돌릴 수 있는 일을 먼저 하고, 되돌리기 비싼 일을 마지막에 둡니다.
그러면 앞에서 막혀도 싸게 되돌릴 수 있습니다.

주문 저장을 결제보다 먼저 하고 상태만 나중에 바꿉니다. 01번의 주문 흐름이 이 순서입니다.

```
주문 저장 (status = PENDING)   <- 되돌릴 수 있음
  |
재고 예약                       <- 되돌릴 수 있음 (예약 해제)
  |
결제 승인                       <- 되돌리기 비쌈 (환불)
  |
주문 상태 변경 (PAID)           <- 짧은 트랜잭션
```

**되돌리기 비싼 것을 최대한 뒤로 밀고, 그 뒤에는 짧고 실패하기 어려운 작업만 둡니다.**

**해법 2. 되돌릴 수 없으면 반대 작업으로 상쇄합니다.**

결제 승인 후 출고가 불가능해지면(재고 실사 차이, 센터 할당 실패) **환불합니다.**
결제를 취소하는 것이 아니라 **환불이라는 새 결제를 만들어 상쇄**합니다.

```
주문 취소 요청
  |
  +-- 재고 예약 해제 (또는 재고 복원)
  +-- 결제 환불 요청 (멱등키 = refund-{주문번호}-{환불시도번호})
  +-- 적립금 회수
  +-- 취소 알림
```

**각 보상 작업도 실패할 수 있으므로 각각 재시도와 멱등성이 필요합니다.**
환불이 실패하면 다시 시도해야 하고, 두 번 성공하면 두 번 환불됩니다.

### Saga: 보상을 순서대로 관리하는 것

보상 작업이 여러 개면 **어디까지 진행됐고 무엇을 되돌려야 하는지 기록**해야 합니다.
그 기록과 진행을 관리하는 것이 Saga 입니다.

```
order_saga
+----------+--------------------+------------------+
| order_no | step               | status           |
+----------+--------------------+------------------+
| A-0001   | STOCK_RESERVED     | DONE             |
| A-0001   | PAYMENT_APPROVED   | DONE             |
| A-0001   | ORDER_CONFIRMED    | FAILED           |
| A-0001   | COMP_REFUND        | PENDING          |
| A-0001   | COMP_STOCK_RELEASE | PENDING          |
+----------+--------------------+------------------+
```

**보상 단계를 표로 남기고 배치가 `PENDING` 을 주워 처리합니다.**
이건 03번의 아웃박스와 구조가 같습니다. **되돌릴 일을 DB 에 기록해 두고 나중에 처리하는
것**이 공통 발상입니다.

**Saga 를 처음부터 프레임워크로 만들지 마십시오.** 단계가 두세 개면 상태 컬럼과 배치로
충분합니다. **단계가 늘고 분기가 생길 때 도입하면 됩니다.**

## 정리: 이 시스템의 선택

> 여섯 가지 결정과 포기한 것을 모았습니다. 빠뜨리지 않는 것과 두 번 하지 않는 것을 각각 다른 장치로 보장합니다.

| 결정 | 선택 | 포기한 것 |
|---|---|---|
| 외부 호출 결과 | **성공, 실패, 모름 세 가지로 다룸** | 두 가지로 단순화하는 편의 |
| 중복 방지 | **멱등키(주문번호 기반)**, 미지원 시 유니크 제약 | 없음 |
| 미결 처리 | **조회 배치로 결과를 확인**, 한도 초과는 사람에게 | 즉시 확정 |
| 재시도 | **일시적 실패만, 지수 백오프와 지터** | 모든 실패를 재시도하는 단순함 |
| 되돌리기 | **순서를 바꿔 비싼 것을 뒤로**, 불가능하면 보상 트랜잭션 | 원자적 롤백 |
| 보상 관리 | **상태 표와 배치로 시작**, Saga 프레임워크는 나중에 | 정형화된 오케스트레이션 |

**핵심 문장 하나로 줄이면 이렇습니다.** 분산 환경에서는 원자성을 얻을 수 없으므로,
**빠뜨리지 않는 것과 두 번 하지 않는 것을 각각 다른 장치로 보장합니다.**
빠뜨리지 않는 것은 아웃박스와 재시도가 맡고, 두 번 하지 않는 것은 멱등키와 인박스가 맡습니다.
