# 01. 전체 설계

## 요약

**무엇을 설명하나:** 가상의 새벽배송 커머스에서 주문이 흐르는 전체 그림입니다.
규모 가정, 서비스 경계, 동기 구간의 시간 예산, 상태 모델, 멈춘 상태를 누가 마무리하는지를 정합니다.

**세 줄 요약**
1. 사용자가 기다리는 것은 주문서 검증부터 결제 결과까지이고, 이 선이 동기와 비동기의 경계입니다.
2. 같은 행에 쓰기가 몰리는 판매 가능 재고를 주문에서 떼어내고, 센터 실물 재고는 출고 영역에 둡니다.
3. 결과가 늦게 확정되는 모든 상태에는 그 상태를 마무리할 주인과 기한, 경보를 하나씩 정합니다.

## 규모 가정

> 설계의 모든 숫자(슬롯 수, 폴링 주기, 파티션 수, 청크 크기, 동시 호출 한도)는 이 표에서 계산합니다.

| 항목 | 가정 |
|---|---|
| 하루 주문 | 30만 건, 주문당 평균 상품 3개 |
| 마감 | 매일 23:00. 마감 직전 30분에 하루 주문의 40%(12만 건) |
| 주문 피크 | 평균 초당 67건, 피크는 평균의 3배인 초당 200건 |
| 특가 상품 | 판매 시작 직후 상품 하나에 초당 최대 500건 시도. 동시에 최대 5개라 합계 초당 2,500건. 재고는 상품마다 최대 300개 |
| 특가 직후 결제 | 특가 5개 × 300개 = 1,500건의 결제 승인이 판매 시작 후 약 2초 안에 몰림 |
| 물류센터 | 4곳. 주문이 한 센터에 절반까지 몰릴 수 있음 |
| 출고 일정 | 23:10 출고 배치 시작, 01:00 출고 지시 완료, 02:00 배차 |
| 결제 대행사 | 평균 300ms, 99번째 백분위 2초. 요청이 늦게 처리될 수 있는 최대 시간 60초 |
| 예약 유지 | 일반 10분, 특가 상품 3분. 결제창에서 머무는 시간과 다른 카드로 다시 결제할 여유 |

이 표에서 나오는 설계 값입니다. 계산은 각 문서의 해당 절에 있습니다.

| 설계 값 | 값 | 근거 |
|---|---|---|
| 슬롯 분산 대상 | 예상 초당 주문 100건 넘는 상품 | 한 행 조건부 갱신 5ms, 상한 초당 200건의 절반 ([02](02-재고-정합성.md)) |
| 슬롯 수 | 8 | 특가 초당 500건 ÷ 슬롯당 200건 = 3, 두 배 넘는 여유 |
| 품절 목록 갱신 | 500ms | 특가 시도 초당 2,500건 중 품절 뒤의 시도를 주문 저장 전에 거름 (아래 "특가 시도 거르기") |
| 결제 동시 호출 한도 | 600 | 평소 피크는 초당 200건 × 2.5초(느려진 대행사) = 500. 특가 직후는 초당 750건 × 0.3초 = 225 |
| 주문 DB 커넥션 풀 | 60 | 특가 첫 1초에 짧은 트랜잭션 약 7,600번 × 5ms = 동시 38, 여유 50% |
| 아웃박스 릴레이 | 200ms마다 최대 500건 | 상한 초당 2,500건, 피크 초당 200건의 10배 이상 ([03](03-이벤트-전달-보장.md)) |
| 토픽 파티션 | 12 | 컨슈머 하나 초당 100건, 피크에 2개 필요. 증설 여유 ([03](03-이벤트-전달-보장.md)) |
| 출고 배치 | 청크 500, 센터별 파티션 4 | 출고 지시 약 32만 건, 한 센터에 쏠려도 약 11분 ([05](05-풀필먼트-배치.md)) |

## 먼저 무엇을 정해야 하는가

> 사용자가 기다리는 구간이 동기와 비동기의 경계이고, 설계의 첫 결정입니다.

주문 한 건이 완료되기까지 일어나는 일입니다.

1. 주문서 검증 (배송 가능 지역, 최소 주문 금액, 쿠폰 유효성)
2. 재고 예약
3. 결제
4. 주문 확정
5. 적립금 적립
6. 주문 확인 알림 발송
7. 출고 지시 생성
8. 배차와 배송

사용자가 화면에서 기다려야 하는 것은 1번부터 4번까지입니다.
재고가 없거나 결제가 거절되면 그 자리에서 알려줘야 하기 때문입니다.
5번부터 8번은 기다릴 필요가 없습니다. 적립금은 3초 뒤에 붙어도 되고, 출고 지시는 마감 후에 만듭니다.

## 서비스 경계

> 한 트랜잭션에 묶여야 하는 것끼리 묶습니다. 판매 가능 재고는 같은 행에 몰려서 따로 뗍니다.

| 서비스 | 소유하는 데이터 | 왜 여기에 있는가 |
|---|---|---|
| **주문** | 주문, 배송지, 주문 상태, 결제 회차 번호와 승인 회차, 환불 요청 | 주문 상태 전이와 보상의 유일한 주인 |
| **재고** | 상품별 판매 가능 재고, 슬롯, 예약, 부족분 | 동시 갱신이 몰리는 유일한 지점 |
| **결제** | 결제 회차, 승인, 환불, 대행사 호출 이력 | 외부 대행사와의 경계를 흡수 |
| **풀필먼트** | 센터별 실물 재고, 출고 대상, 할당, 출고 지시 | 마감 후 대량 배치가 도는 영역 |

상품과 회원 서비스는 이 설계의 쟁점이 아니라서 다루지 않습니다. 주문서 검증에 필요한 값은 요청에 실려 온다고 둡니다.

**재고를 주문에서 떼어낸 것이 핵심 결정입니다.** 이유는 둘입니다.

첫째, 재고는 쓰기 방식이 다릅니다. 주문은 각자 다른 행을 쓰는데 재고는 여러 주문이 같은 행에 몰립니다.
둘째, 그 대기가 주문까지 번지지 않게 합니다. 같은 DB에 두면 재고 행을 기다리는 요청이 커넥션을 잡습니다.
그러면 주문 저장과 조회도 커넥션을 못 얻습니다. 떼어 두면 재고만 따로 키우거나 쪼갤 수 있습니다.

**센터 실물 재고는 풀필먼트에 둡니다.** 판매 가능 재고는 주문이 바꾸고, 실물 재고는 입고와 출고가 바꿉니다.
바꾸는 주체와 시점이 달라 한 서비스에 둘 이유가 없습니다.
이렇게 두면 출고 배치가 실물 재고를 자기 DB에서, 출고 지시와 같은 트랜잭션으로 차감할 수 있습니다.

## 주문 흐름

> 주문을 먼저 저장하고, 재고와 결제는 트랜잭션 밖에서 부릅니다. 결과가 모호하면 실패로 단정하지 않고 확인 중으로 둡니다.

### 동기 구간

```
[클라이언트] 주문서 ID(checkout_id)와 함께 주문 요청
    |
[주문]  같은 주문서 ID의 주문이 있으면 그 주문의 현재 상태를 돌려준다
    |   품절 목록에 있으면 저장하지 않고 품절 응답
    |   주문 저장 (PENDING, 시도 IDLE, 회차 0, 짧은 트랜잭션)
    |
    +--> [재고] 예약 (HELD, 만료 시각 하나)          실패하면 품절 응답, 주문 FAILED
    |    주문에 예약 만료 시각 저장
    |    결제 시도 시작 (주문 행: IDLE 을 IN_PROGRESS 로, 회차 + 1)   0행이면 "결제 진행 중" 응답
    +--> [재고] 결제 시작 표시 (PAYING, 회차)        0행이면 예약의 현재 상태로 갈래 (아래)
    +--> [결제] 승인 요청 (멱등키 = order-{주문번호}-payment-{회차})
    |
    +-- 승인 -> 주문 확정 (PAID) + 아웃박스 PAID, 같은 트랜잭션
    +-- 거절 -> 그 회차의 PAYING 을 HELD 로 되돌리고 시도를 IDLE 로. "다른 결제 수단" 응답. 주문은 PENDING
    +-- 모름 -> "결제 확인 중" 응답. 주문 PENDING, 시도 IN_PROGRESS, 예약 PAYING 유지
```

**주문 요청 자체도 멱등이어야 합니다.** 결제 멱등키는 주문번호로 만드는데, 주문번호는 서버가 요청마다 만듭니다.
앱이 응답을 못 받고 주문을 다시 보내면 새 주문번호로 결제가 한 번 더 나갑니다.
그래서 클라이언트가 주문서 화면을 열 때 받은 주문서 ID를 보내고, 주문 테이블에 유니크 제약을 겁니다.

**결제 시도는 주문당 한 번에 하나입니다.** 주문 행에 시도 상태(IDLE, IN_PROGRESS)를 둡니다.
시도를 시작할 때 IN_PROGRESS 와 회차 r + 1 로 바꿉니다.
조건은 `status = 'PENDING' AND attempt = 'IDLE' AND payment_round = r` 입니다.
사용자가 결제를 연달아 눌러도 한 요청만 시도를 시작하고, 나머지는 "결제 진행 중"으로 답합니다.
시도가 둘이면 서로의 회차를 건드려 결제된 주문이 실패로 닫힐 수 있습니다. 하나로 묶으면 그런 경합이 생길 자리가 없습니다.

시도는 결과가 확실할 때만 끝납니다. 승인은 PAID, 거절은 IDLE 입니다. 결과를 모르면 IN_PROGRESS 로 두고 결제 이벤트나 정리 배치가 끝냅니다.

**결제 시작 표시가 0행이면 예약의 현재 상태로 나눕니다.** 시도가 하나뿐이라 갈래가 단순합니다.

| 예약 상태 | 뜻 | 주문 서비스가 하는 일 |
|---|---|---|
| PAYING, 이번 회차 | 앞선 표시의 응답이 유실됨 | 그대로 결제를 진행 |
| PAYING, 앞 회차 | 앞 시도의 되돌림이 실패했음 | 결제 서비스에 앞 회차 상태를 물어 FAILED 나 EXPIRED 면 HELD 로 되돌리고 다시 표시. 그 밖이면 시도를 IDLE 로 끝내고 "결제 진행 중", 경보 |
| HELD 인데 만료 시각이 지남, 또는 RELEASED | 예약이 만료됨 | 결제를 부르지 않고 주문 FAILED, 실패 응답 |
| CONFIRMED | 이미 결제 완료 | 주문 상태를 돌려줌 |

앞 회차의 FAILED 와 EXPIRED 는 다시 바뀌지 않는 끝 상태라, 읽기만 해도 되돌려도 안전하다는 근거가 됩니다.

**결제 서비스가 "봉인됨"으로 답하면** 이번 회차는 EXPIRED 로 끝난 것입니다. 정리 배치나 만료 배치가 먼저 봉인했다는 뜻입니다.
주문 서비스는 시도를 IDLE 로 끝내고 예약을 다시 읽습니다. 만료 전이면 PAYING(이번 회차)을 HELD 로 되돌려 다시 결제를 받습니다.
만료 뒤면 주문을 FAILED 로 닫습니다. 주문을 FAILED 로 닫는 것은 예약이 만료됐을 때뿐입니다.

**시도를 끝내는 갱신에는 회차 조건을 겁니다.** IDLE 로 끝내든 PAID 로 끝내든 `payment_attempt = 'IN_PROGRESS' AND payment_round = r` 입니다.
오래 멈췄던 요청이 깨어나 끝내려 해도, 그사이 정리 배치가 끝내고 다음 회차가 시작됐다면 0행이라 아무것도 바꾸지 못합니다.

**거절되면 주문을 실패시키지 않습니다.** 카드 거절은 흔하고, 사용자는 다른 카드로 다시 결제합니다.
예약이 만료되면 재고 서비스가 예약을 풀고, 주문 서비스 정리 배치가 주문을 FAILED 로 닫습니다.

**한 주문의 예약은 만료 시각이 하나입니다.** 상품마다 유지 시간이 달라도(일반 10분, 특가 3분) 가장 짧은 값으로 맞춥니다.
예약 응답의 만료 시각을 주문에도 저장해, 주문 서비스가 재고 서비스에 묻지 않고 만료를 압니다.

**회차 번호는 주문 서비스가 정하고 결제 서비스가 검사합니다.** 결제 서비스는 기존 회차보다 큰 번호이고 가장 최근 회차가 FAILED 나 EXPIRED 일 때만 엽니다.
번호가 건너뛰어도 됩니다. 결제를 다시 눌렀지만 앞 결제가 진행 중이라 쓰이지 않은 번호가 생길 수 있기 때문입니다.

**회차는 봉인할 수 있습니다.** 아직 열리지 않은 회차를 닫아 달라고 하면, 결제 서비스는 그 회차 번호로 EXPIRED 행을 넣습니다.
`(주문번호, 회차)` 는 유니크라, 늦게 도착한 승인 요청은 그 회차를 열지 못합니다. 이미 열렸으면 봉인이 실패하고 그 회차의 상태를 돌려줍니다.
"회차 없음"을 믿어도 되는지를 시간 가정이 아니라 DB 제약이 정합니다(02번 "회차 봉인").
봉인은 멈춘 상태를 정리하는 두 배치(재고 만료 배치, 주문 정리 배치)만 요청합니다. 사용자 요청 경로는 봉인하지 않습니다.

### 특가 시도 거르기

특가 상품은 재고 수백 개가 판매 시작 1초 안에 팔리고, 그 뒤에도 초당 2,500건의 시도가 이어집니다.
주문을 먼저 저장하는 흐름에서는 실패할 시도도 PENDING 과 FAILED 를 씁니다. 초당 5,000번의 쓰기가 주문 DB에 몰립니다.
재고를 떼어 주문 DB를 지키려던 결정과 어긋납니다.

그래서 주문 서비스가 500ms 마다 재고 서비스에서 품절 상품 목록을 받아 메모리에 두고, 주문을 저장하기 전에 봅니다.
재고 서비스는 이 목록을 캐시하지 않고 요청 때마다 계산하므로, 품절이 목록에 드러나는 데 최대 500ms 가 걸립니다.
품절 뒤 500ms 안의 시도(최대 1,250건)만 주문 DB까지 오고, 그 뒤는 저장 없이 품절로 답합니다.
목록이 틀려도 손해는 한쪽뿐입니다. 품절인데 통과하면 예약에서 걸러지고, 재고가 돌아왔는데 막히면 500ms 뒤 다시 열립니다.

예약에 성공한 1,500건은 약 2초 안에 결제로 갑니다. 대행사가 평소처럼 300ms 면 동시 호출은 225건으로 한도 안입니다.
대행사가 느려져 한도를 넘으면 넘친 요청은 "결제 지연"으로 바로 거절하고 예약을 HELD 로 되돌립니다.
사용자는 예약 유지 3분 안에 다시 결제합니다. 특가 결제를 대기열로 흘리는 방법도 있지만, 대기열의 운영 부담보다 다시 결제의 불편이 작다고 판단했습니다.

### 스레드와 커넥션

요청 처리는 Java 21 가상 스레드로 합니다. 대행사를 기다리는 동안 스레드가 묶여도 플랫폼 스레드가 마르지 않습니다.
대신 묶이는 것은 결제 서비스로 가는 HTTP 커넥션과 대행사로 가는 커넥션입니다.
대행사가 2.5초로 느려지면 초당 200건 × 2.5초 = 동시 500건이 됩니다. 두 커넥션 풀을 600으로 둡니다.
주문 DB는 특가 첫 1초가 가장 바쁩니다. 몰리는 짧은 트랜잭션을 세면 이렇습니다.

| 트랜잭션 | 횟수 |
|---|---|
| PENDING 저장 (팔린 1,500건 + 품절 직후 통과한 1,250건) | 2,750 |
| 예약 실패로 FAILED | 1,250 |
| 결제 시도 시작 | 1,500 |
| PAID 확정 | 1,500 |
| 같은 1초의 평소 주문 (초당 200건 × 3번) | 600 |

합쳐 약 7,600번이고 한 번에 5ms 면 동시 38개라 커넥션 풀을 60으로 둡니다.
600을 넘는 요청은 기다리지 않고 "결제 지연"으로 바로 거절합니다. 대행사를 부르지 않았으니 결과가 확실한 실패입니다.

**규칙 1. 트랜잭션 안에서 외부를 호출하지 않습니다.**
피크 초당 200건에 대행사 300ms를 트랜잭션 안에서 기다리면 DB 커넥션 60개가 늘 묶입니다.
대행사가 3초씩 걸리면 600개가 필요해 커넥션 풀이 먼저 마릅니다.
트랜잭션 밖에서 부르면 짧은 트랜잭션 세 번(약 30ms)만 커넥션을 쓰므로 6개면 됩니다.

**규칙 2. 여러 서비스를 한 트랜잭션으로 묶지 않습니다.** 각자 커밋하고, 어긋나면 아래 "수렴 책임" 표의 주인이 맞춥니다.
2단계 커밋을 쓰지 않는 이유는 [03](03-이벤트-전달-보장.md)에 있습니다.

### 시간 예산

동기 구간의 모든 호출에 타임아웃을 정하고, 넘으면 결과를 모르는 상태로 다룹니다.
사용자가 기다리는 경로 안에서는 백오프 재시도를 하지 않습니다. 재시도는 뒤의 배치가 합니다.

| 호출 | 타임아웃 | 넘었을 때 |
|---|---|---|
| 클라이언트 → 주문 | 10초 | 같은 주문서 ID로 주문 상태를 조회 |
| 주문 → 재고 예약 | 500ms, 1회 재시도 | 예약은 (주문번호, 상품) 유니크라 재시도해도 한 벌. 그래도 실패면 주문 FAILED. 남은 예약은 만료 배치가 풂 |
| 주문 → 결제 시작 표시 | 500ms, 1회 재시도 | 재시도가 0행이면 위 표대로. 그래도 실패면 시도를 IN_PROGRESS 로 두고 "잠시 뒤 다시" 응답. 정리 배치가 끝냄 |
| 주문 → 결제 승인 | 5초 | 모름. 주문 PENDING, 예약 PAYING 유지 |
| 결제 → 대행사 | 3초 | 모름. 결제 REQUESTED |
| 주문 → 거절 되돌림 | 500ms | 실패해도 시도는 IDLE 로 끝냄. 다음 시도가 앞 회차의 PAYING 을 만나 되돌림 |

결제 서비스는 동기 경로에서 대행사를 한 번만 부르므로 5초 안에 반드시 답합니다.

### 비동기 구간

```
주문 아웃박스     --> order.events       (PAID, CANCELLED)                  키 = 주문번호
결제 아웃박스     --> payment.events     (APPROVED, FAILED, REFUNDED 등)    키 = 주문번호
풀필먼트 아웃박스 --> fulfillment.events (UNFILLABLE, EXCEPTION_CANCELLED, STOCK_CHANGED)  키 = 주문번호 또는 상품번호

order.events       --> 재고(예약 확정, 취소 복원), 풀필먼트(출고 대상 등록과 취소), 회원(적립), 알림
payment.events     --> 주문(늦게 확정된 결제 반영, 실패나 취소 주문에 온 승인의 환불, 환불 결과 반영)
fulfillment.events --> 주문(못 채운 품목과 관리자 취소 품목의 취소와 환불), 재고(입고와 실사 반영)
```

주문 서비스가 받는 쪽을 직접 부르지 않는 이유는 둘입니다.
받는 쪽은 계속 늘어나서, 직접 부르면 늘 때마다 주문 코드를 고쳐야 합니다.
그리고 한 곳이 죽어도 주문은 성공해야 합니다. 알림 서비스가 응답하지 않는다고 주문을 실패시킬 이유가 없습니다.

## 상태 모델

> 서비스마다 상태와 전이를 고정합니다. 모든 전이는 이전 상태를 조건으로 거는 조건부 갱신이라, 경합하면 하나만 이깁니다.

| 대상 | 상태 | 전이 |
|---|---|---|
| 주문 | PENDING, PAID, FAILED, CANCELLED | PENDING → PAID 또는 FAILED. 품목 취소(고객, 출고 불가, 관리자)는 품목별 취소 수량을 늘리고, 모든 품목이 취소되면 PAID → CANCELLED |
| 결제 시도 (주문 행) | IDLE, IN_PROGRESS | IDLE → IN_PROGRESS (회차 + 1). IN_PROGRESS → IDLE (거절, 봉인). 승인이면 주문이 PAID 가 되며 끝남 |
| 예약 | HELD, PAYING, CONFIRMED, RELEASED, RESTORED | HELD → PAYING (회차 기록). PAYING → HELD (같은 회차가 거절되거나 봉인됐을 때만). PAYING → CONFIRMED. HELD 또는 PAYING → RELEASED (만료). 취소 수량이 예약 수량에 이르면 RESTORED |
| 결제 회차 | REQUESTED, APPROVED, FAILED, UNKNOWN, EXPIRED | 봉인으로 생긴 EXPIRED 는 끝. REQUESTED → APPROVED, FAILED, UNKNOWN. UNKNOWN 은 사람이 확정. FAILED → APPROVED 는 정산 대사가 대행사 승인을 확인했을 때만 |
| 환불 요청 (주문) | REQUESTED, ACCEPTED, COMPLETED, FAILED, REJECTED | REQUESTED → ACCEPTED (결제 서비스 접수) → COMPLETED 또는 FAILED. REQUESTED 에서 바로 COMPLETED 도 됨 (접수 응답 유실). 접수가 거절되면 REJECTED. FAILED 와 REJECTED 는 사람이 확정 |
| 환불 (결제) | REQUESTED, COMPLETED, FAILED, UNKNOWN | REQUESTED → COMPLETED, FAILED (대행사가 거절), UNKNOWN. FAILED, UNKNOWN → COMPLETED 나 FAILED 는 사람이 확정 |

예약 HELD → PAYING 은 만료 전일 때만, 만료 배치의 HELD → RELEASED 는 만료 뒤일 때만 일어납니다.
주문이 취소될 때 바뀌는 단위는 주문이 아니라 품목입니다. 출고 예외처럼 한 주문의 일부만 처리해야 하는 경우가 있기 때문입니다.
두 갱신 모두 `status = 'HELD'` 를 조건으로 걸기 때문에 결제 시작과 만료가 겹쳐도 하나만 성공합니다.

## 수렴 책임

> 결과가 늦게 확정되는 상태마다 주인 하나, 기한 하나, 경보 하나를 둡니다. 주인이 둘이면 서로 미루고, 없으면 영원히 남습니다.

| 멈춘 상태 | 주인 | 하는 일 | 기한과 경보 |
|---|---|---|---|
| 결제 REQUESTED | 결제 서비스 조회 배치 | 멱등키로 대행사에 묻고 확정. 결과는 payment.events 로 알림 | 10분 넘으면 UNKNOWN, 경보 |
| 결제 시도 IN_PROGRESS | 주문 서비스 정리 배치 | 1분 넘은 시도의 회차를 봉인 요청. 승인이면 PAID, 봉인됐거나 FAILED 면 예약을 되돌리고 IDLE | 15분 넘으면 경보 |
| 주문 PENDING | 주문 서비스 정리 배치 | 시도가 IDLE 인 PENDING 이 예약 만료 시각을 지나면 재고 서비스에 예약 상태를 물어, 풀렸거나 없으면 FAILED | 15분 넘은 PENDING 이 있으면 경보 |
| 주문이 쓰지 않은 승인 | 주문 서비스 (결제 이벤트 소비자, 정리 배치) | 환불 요청 `refund-{주문번호}-orphan-{회차}` 를 만듦 | 1건이라도 경보. 대행사가 실패로 닫힌 회차를 늦게 승인할 때만 생김 |
| 예약 HELD, PAYING 만료 | 재고 서비스 만료 배치 | HELD 는 바로 풀고, PAYING 은 그 회차를 봉인 요청해 확정하거나 풂 | 만료 배치가 5분 넘게 돌지 않거나 만료 5분 지난 HELD 가 있으면 경보. UNKNOWN 은 풀지 않고 경보 |
| 아웃박스 PENDING | 각 서비스 릴레이 | 백오프로 재발행. 같은 키의 뒤 이벤트는 막아 둠 | 가장 오래된 PENDING 이 30초 넘으면 경보 |
| 처리하지 못한 메시지 | 처리 실패 토픽 | 원인을 고친 뒤 원래 토픽으로 다시 넣음 | 1건이라도 쌓이면 경보 |
| 마감 경계의 출고 대상 | 출고 배치 대상 확정 스텝 | 주문 서비스의 결제 완료 목록과 대조해 빠진 건을 채움 | 23:15 까지 배치가 시작하지 않으면 경보 |
| 주문 서비스의 환불 요청 | 주문 서비스 환불 배치 | REQUESTED 는 접수될 때까지 같은 키로 보냄. 1시간 넘은 ACCEPTED 는 결제 서비스에 상태를 물어 맞춤 | 접수 안 된 채 10분, ACCEPTED 로 2시간이면 경보 |
| 대행사와의 환불 확정 | 결제 서비스 환불 배치 | 접수된 환불을 같은 키로 재요청하고 조회. 결과는 payment.events 로 알림 | 1시간 넘으면 UNKNOWN, 경보 |
| 판매 가능 재고 어긋남 | 재고 대사 작업 (하루 한 번, 출고 지시 뒤) | 판매 가능 재고 − 부족분 + 잡힌 예약 + 출고 전 확정 수량 = 센터 실물 합인지 상품마다 확인 | 어긋난 상품만 10분 뒤 다시 재서 또 어긋나면 경보, 사람이 보정 API로 고침 |
| 출고 배치 실패나 지연 | 사람 | 원인을 고치고 같은 마감 시각으로 재시작 | 잡 실패 즉시, 00:50 까지 SHIPMENT_CREATED 아니면 경보 |
| 출고 예외 | 사람 (풀필먼트 관리 API 하나) | OPEN 조건으로 이월하거나 관리자 취소. 취소는 이벤트로 주문 서비스가 환불 | 1건이라도 있으면 경보 |
| 접수가 거절된 환불 요청 | 사람 (주문 관리 API) | 금액을 바로잡아 새 키로 다시 요청하거나 닫음 | 1건이라도 있으면 경보 |
| 출고 결과 검증 실패 | 사람 (관리 API) | 원인을 보고 회차를 승인하거나 해당 주문을 예외로 돌림. 승인 전에는 배차로 넘기지 않음 | 즉시 경보 |

사람이 확정하는 상태는 관리 API로 결과를 넣습니다. 관리 API도 일반 전이와 같은 조건부 갱신과 아웃박스를 거칩니다.

## 운영 지표

| 지표 | 경보 기준 | 무엇을 뜻하나 |
|---|---|---|
| 가장 오래된 아웃박스 PENDING 의 나이 | 30초 | 릴레이가 멈췄거나 브로커가 느림 |
| 컨슈머 랙(처리 지연량) | 1분 분량 | 받는 쪽이 피크를 못 따라감 |
| 처리 실패 토픽 적재 건수 | 1건 | 코드나 데이터 문제. 사람이 봐야 함 |
| 10분 넘은 REQUESTED 결제 | 1건 | 대행사 장애나 조회 배치 정지 |
| UNKNOWN 결제, UNKNOWN 이나 FAILED 환불 | 1건 | 사람이 대행사에 확인해야 함 |
| 1시간 넘은 REQUESTED 환불 (결제 서비스) | 1건 | 대행사 환불 지연 |
| 15분 넘은 PENDING 주문 | 1건 | 결제 결과가 주문에 반영되지 않음 |
| 만료 배치가 5분 넘게 돌지 않음, 만료 5분 지난 HELD | 1건 | 만료 배치 정지. 특가 재고가 묶여 판매 손실. PAYING 은 결제 결과를 기다리는 정상 상태라 넣지 않음 |
| 접수 안 된 채 10분 넘은 환불 요청, ACCEPTED 로 2시간 넘은 환불 요청 | 1건 | 주문 환불 배치 정지, 결제 서비스 장애, 이벤트 유실 |
| 15분 넘은 IN_PROGRESS 결제 시도 | 1건 | 정리 배치 정지나 대행사 장애 |
| 실패나 취소된 주문에 온 승인 | 1건 | 설계의 가정이 깨짐. 환불은 자동, 원인은 사람이 봄 |
| 풀린 예약에 온 확정 시도 | 1건 | 결제한 주문에 재고가 없음. 즉시 확인 |
| 결제 동시 호출 한도 초과로 거절 | 1분에 10건 | 대행사가 느려짐 |
| 출고 배치 진행률 | 23:15 미시작, 00:30 ALLOCATED 아님, 00:50 SHIPMENT_CREATED 아님, 잡 실패 | 01:00 완료 목표를 놓칠 위험 |
| 재고 대사 불일치 | 10분 간격 두 번 연속 | 판매 가능 재고가 실물과 어긋남 |
| 출고 예외 품목, 못 채운 품목 | 예외 1건, 못 채운 품목 0.5% | 데이터 문제나 실사 차이 |
