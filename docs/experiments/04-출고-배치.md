# 04. 출고 배치

30만 주문(품목 90만 줄)으로 출고 배치의 스텝별 시간을 잽니다. 네 센터에 고르게 나뉠 때와, 한 센터에 절반이 몰릴 때를 비교합니다.
두 경우 모두 10~13분에 검증까지 끝나 01:00 목표에 넉넉합니다. 실험 중에 할당이 재고가 넉넉한 날에도 한 센터로 쏠리는 문제를 찾아 고쳤습니다.

## 준비

- **환경:** Apple M3 8코어 노트북, Docker Desktop 위의 MySQL 8.4 컨테이너 하나. 실행 중 맥이 잠들지 않게 했습니다
- **데이터:** 주문 30만 건, 주문마다 상품 3개. 상품 5,000개. 서울 주문이 절반, 대전과 부산이 4분의 1씩입니다
- **센터:** 서울 A, 서울 B, 대전 A, 부산 A. 센터마다 상품당 재고 1,000개라 못 채우는 주문은 없습니다
- **쏠림 시나리오:** 서울 B 의 재고를 0으로 둬서 서울 주문 15만 건이 모두 서울 A 로 가게 합니다
- **설정:** 운영값 그대로. 출고 지시는 센터별 파티션 4개, 주문 500건씩 한 트랜잭션
- **실행:** `./gradlew :fulfillment-batch:experiment` (`ShipmentBatchExperiment`)

## 절차

1. 출고 대상과 품목, 센터 재고를 SQL 로 한 번에 만듭니다. 주문 서비스의 결제 완료 목록은 가짜가 1,000건씩 페이지로 줍니다
2. 마감 시각을 파라미터로 잡을 돌리고, Spring Batch 의 스텝 실행 기록에서 시작과 끝 시각을 읽습니다
3. 같은 일을 고른 분산과 서울 A 쏠림에서 한 번씩 합니다

## 예상

설계 05 는 청크 하나(주문 500건)에 2초, 즉 파티션 하나가 초당 250건을 낸다고 셌습니다.

| 스텝 | 설계 예상 |
|---|---|
| 대상 확정 | 2분 |
| 할당 | 계산 1분, 저장 3분 |
| 출고 지시 | 고르면 5분, 한 센터에 절반이 몰리면 11분 |
| 합계 | 20분 안팎 |

## 실제

| 스텝 | 고른 분산 | 서울 A 쏠림 |
|---|---|---|
| 대상 확정 | 25초 | 28초 |
| 할당 | 2분 28초 | 2분 52초 |
| 판정 발행 | 0초 (못 채운 주문 없음) | 0초 |
| 출고 지시 | 6분 57초 (네 센터 7만 5천 건씩) | 9분 28초 (서울 A 15만 건) |
| 결과 검증 | 1.3초, VERIFIED | 1.5초, VERIFIED |
| 합계 | 약 10분 | 약 13분 |

**출고 지시는 파티션끼리 DB 를 나눠 쓰는 만큼 느려집니다.** 넷이 함께 돌 때 파티션 하나는 초당 약 180건이었습니다.
설계가 센 250건보다 30% 느립니다. 대신 다른 파티션이 끝나고 혼자 남으면 초당 약 400건까지 올라갔습니다.
그래서 쏠림 회차는 설계 예상(11분)보다 빨리 끝났습니다. 서울 A 가 앞 6분 반은 다른 센터와, 뒤 3분은 혼자 돌았습니다.

## 실험이 찾은 것

**재고가 넉넉한 날에도 할당이 한 센터로 쏠렸습니다.** 첫 실행에서 서울 주문 15만 건이 모두 서울 A 로 갔고 서울 B 는 0건이었습니다.
할당 1차는 "권역 안 한 센터에서 전량 나갈 수 있는 주문"을 배정하는데, 그런 센터가 여럿일 때 고르는 규칙이 설계에 없었습니다.
구현은 센터 번호순으로 첫 센터를 골랐습니다. 이제 그 주문 품목의 재고가 가장 많이 남은 센터를 고르고, 같으면 번호순입니다.
고친 뒤 위 표처럼 네 센터가 7만 5천 건씩 나눴습니다. 같은 입력이면 결과가 늘 같다는 성질은 단위 테스트로 지켰습니다.

첫 실행은 도중에 노트북이 23분간 잠들어 서울 A 의 시간이 무효가 됐습니다. 위 숫자는 잠들지 않게 하고 다시 잰 것입니다.

## 설계에 남긴 것

- 설계 05 의 할당 1차에 센터를 고르는 규칙을 적었습니다
- 스텝별 예상 시간 옆에 측정값을 적었습니다. 출고 지시의 파티션당 처리량은 250건이 아니라 함께 돌 때 약 180건으로 셉니다
- 30만 주문이 13분 안에 끝나므로, 23:10 시작에 01:00 완료라는 창에는 재시작 몇 번을 넣을 여유가 그대로 있습니다
