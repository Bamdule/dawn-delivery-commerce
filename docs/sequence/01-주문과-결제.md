# 01. 주문과 결제

주문 요청부터 결제 결과가 주문에 반영되기까지의 흐름입니다. 설계 근거는 [01 전체 설계](../design/01-전체-설계.md)와 [04 멱등성과 실패 복구](../design/04-멱등성과-실패-복구.md)에 있습니다.

| 흐름 | 언제 |
|---|---|
| [1. 결제 승인](#1-결제-승인) | 대행사가 바로 승인할 때 |
| [2. 카드 거절과 다시 결제하기](#2-카드-거절과-다시-결제하기) | 잔액 부족 같은 거절 뒤 다른 카드로 결제할 때 |
| [3. 결과를 모를 때](#3-결과를-모를-때) | 대행사 타임아웃이나 응답 유실 |
| [4. 결제 확인 중에 다시 누를 때](#4-결제-확인-중에-다시-누를-때) | 앞 결제의 결과를 모르는데 사용자가 결제를 또 누를 때 |
| [5. 주문 요청 중복](#5-주문-요청-중복) | 앱이 응답을 못 받고 같은 주문을 다시 보낼 때 |
| [6. 주문 정리 배치와 쓰이지 않은 승인](#6-주문-정리-배치와-쓰이지-않은-승인) | 결제 결과가 주문에 반영되지 않았거나, 주문이 쓰지 않은 승인이 왔을 때 |

---

## 1. 결제 승인

사용자가 기다리는 구간입니다. 외부 호출은 모두 트랜잭션 밖에서 하고, 짧은 트랜잭션만 주문 DB 커넥션을 씁니다.

```mermaid
sequenceDiagram
    autonumber
    actor 사용자
    participant 주문
    participant 재고
    participant 결제
    participant 대행사 as 결제 대행사

    사용자->>주문: 주문 요청 (주문서 ID, 품목, 배송지)
    주문->>주문: 품절 캐시 확인 (1초마다 재고 서비스에서 받음)
    주문->>주문: 주문 저장 PENDING, 결제 회차 1 (짧은 트랜잭션)
    주문->>재고: 예약 (주문번호, 품목)
    재고->>재고: 상품번호 순으로 조건부 차감 + 예약 HELD (한 트랜잭션)
    재고-->>주문: 예약 완료
    주문->>재고: 결제 시작 표시 (회차 1)
    재고->>재고: HELD 를 PAYING 으로, 회차 1, 기한 = 지금 + 5초
    재고-->>주문: 표시 완료 (기한)
    주문->>결제: 승인 요청 (주문번호, 회차 1, 45,000원, 기한)
    결제->>결제: 회차 행 잠금, 기한과 회차 규칙 검사, 회차 1 REQUESTED
    결제->>대행사: 승인 (멱등키 order-...-payment-1, 타임아웃 3초)
    대행사-->>결제: 승인
    결제->>결제: APPROVED + 아웃박스 APPROVED (한 트랜잭션)
    결제-->>주문: 승인
    주문->>주문: PENDING 을 PAID 로, paid_round 1 + 아웃박스 PAID (한 트랜잭션)
    주문-->>사용자: 주문 완료

    Note over 주문,재고: 이후 order.events 의 PAID 로 예약 확정, 출고 대상 등록이 비동기로 일어남
```

- **8번:** 바뀐 예약 행 수가 품목 수와 다르면 결제를 부르지 않습니다
- **11번:** 기한이 지난 요청이면 회차를 열지 않습니다. 만료 배치가 "회차 없음"을 믿을 수 있게 하는 장치입니다
- **16번:** `status = 'PENDING'` 조건부 갱신이 1행일 때만 아웃박스를 씁니다

## 2. 카드 거절과 다시 결제하기

거절은 결과가 확실한 실패라 주문을 실패시키지 않고, 예약을 유지한 채 다음 회차를 받습니다.

```mermaid
sequenceDiagram
    autonumber
    actor 사용자
    participant 주문
    participant 재고
    participant 결제
    participant 대행사 as 결제 대행사

    Note over 주문,재고: 주문 저장, 예약 HELD, 결제 시작 PAYING(회차 1) 까지는 1번 흐름과 같음
    주문->>결제: 승인 요청 (회차 1)
    결제->>대행사: 승인 (멱등키 ...-payment-1)
    대행사-->>결제: 거절 (잔액 부족)
    결제->>결제: 회차 1 FAILED + 아웃박스 FAILED
    결제-->>주문: 거절
    주문->>재고: 거절 되돌림 (회차 1)
    재고->>재고: PAYING 이고 회차 1 일 때만 HELD 로
    주문-->>사용자: 다른 결제 수단 선택 (주문은 PENDING)

    사용자->>주문: 다른 카드로 다시 결제
    주문->>주문: 결제 회차 1 을 2 로 (payment_round = 1 조건)
    주문->>재고: 결제 시작 표시 (회차 2)
    재고->>재고: HELD 를 PAYING 으로, 회차 2 (만료 전일 때만)
    주문->>결제: 승인 요청 (회차 2, 기한)
    결제->>결제: 가장 최근 회차 1 이 FAILED 인지 확인 후 회차 2 생성
    결제->>대행사: 승인 (멱등키 ...-payment-2)
    대행사-->>결제: 승인
    결제-->>주문: 승인
    주문->>주문: PAID, paid_round 2 + 아웃박스 PAID
    주문-->>사용자: 주문 완료
```

- **7번:** 회차 조건이 있어서, 늦게 도착한 회차 1의 되돌림이 회차 2의 PAYING 을 HELD 로 바꾸지 않습니다
- **10번:** 다시 결제를 두 번 눌러도 회차 조건 때문에 한 요청만 다음 회차로 갑니다
- 예약 유지 시간이 지나면 12번이 RELEASED 를 만나 결제를 부르지 않고 실패로 답합니다

## 3. 결과를 모를 때

타임아웃은 실패가 아니라 모르는 상태입니다. 사용자에게는 "결제 확인 중"으로 답하고, 결제 서비스가 뒤에서 확정해 이벤트로 알립니다.

```mermaid
sequenceDiagram
    autonumber
    actor 사용자
    participant 주문
    participant 결제
    participant 조회배치 as 결제 조회 배치
    participant 대행사 as 결제 대행사
    participant 카프카 as Kafka

    주문->>결제: 승인 요청 (회차 1)
    결제->>대행사: 승인 (멱등키 ...-payment-1)
    Note right of 대행사: 승인은 했지만 3초 안에 응답하지 못함
    결제->>결제: 회차 1 REQUESTED, 마지막 전송 시각 기록
    결제-->>주문: 모름
    주문-->>사용자: 결제 확인 중 (주문 PENDING, 예약 PAYING 유지)

    loop 10초마다
        조회배치->>대행사: 멱등키로 조회
        alt 승인됨
            대행사-->>조회배치: 승인
            조회배치->>결제: APPROVED + 아웃박스 APPROVED
        else 요청 없음, 그리고 마지막 전송에서 60초 지남
            대행사-->>조회배치: 요청 없음
            조회배치->>결제: FAILED + 아웃박스 FAILED
        else 10분 지나도 모름
            조회배치->>결제: UNKNOWN, 경보 (사람이 확정)
        end
    end

    결제->>카프카: payment.events APPROVED (회차 1)
    카프카->>주문: APPROVED 소비
    주문->>주문: PENDING 을 PAID 로, paid_round 1 (1행일 때만 아웃박스 PAID)
    사용자->>주문: 주문 상태 조회
    주문-->>사용자: 주문 완료
```

- **조회는 멱등키로 합니다.** 주문번호로 조회하면 2회차 승인을 1회차 결과로 잘못 읽을 수 있습니다
- **"요청 없음"은 마지막 전송에서 60초가 지난 뒤에만 믿습니다.** 다시 보낸 요청이 처리 중일 수 있습니다

## 4. 결제 확인 중에 다시 누를 때

결제 시작 표시가 0행이면 예약의 현재 상태로 나눕니다. 0행을 "예약이 풀렸다"로만 보면, 돈은 빠졌는데 주문은 실패로 남습니다.

```mermaid
sequenceDiagram
    autonumber
    actor 사용자
    participant 주문
    participant 재고
    participant 결제

    Note over 주문,결제: 회차 1 이 REQUESTED, 예약은 PAYING(회차 1)
    사용자->>주문: 다시 결제
    주문->>주문: 결제 회차 1 을 2 로
    주문->>재고: 결제 시작 표시 (회차 2)
    재고-->>주문: 0행, 현재 상태 PAYING (회차 1)
    주문->>결제: 회차 1 의 상태
    alt REQUESTED 또는 UNKNOWN
        결제-->>주문: 확인 중
        주문-->>사용자: 결제 확인 중 (주문은 PENDING 그대로)
    else FAILED (앞의 되돌림이 실패했던 경우)
        결제-->>주문: FAILED
        주문->>재고: 거절 되돌림 (회차 1)
        주문->>재고: 결제 시작 표시 (회차 2)
        Note right of 주문: 이후 2번 흐름과 같음
    else APPROVED
        결제-->>주문: 승인
        주문->>주문: PAID, paid_round 1
        주문-->>사용자: 주문 완료
    end
```

예약이 RELEASED 일 때만 주문을 FAILED 로 닫습니다. 만료로 풀렸다면 결제 기한도 지나 새 회차가 열릴 수 없습니다.

---

## 5. 주문 요청 중복

결제 멱등키는 주문번호로 만드는데, 주문번호는 서버가 요청마다 만듭니다. 그래서 주문 요청 자체를 주문서 ID 로 묶습니다.

```mermaid
sequenceDiagram
    autonumber
    actor 앱
    participant 주문

    앱->>주문: 주문 요청 (주문서 ID c-77)
    주문->>주문: 주문 20261028-000123 저장 (주문서 ID 유니크)
    Note over 주문: 예약과 결제 진행 중
    Note over 앱: 응답 유실. 10초 타임아웃
    앱->>주문: 같은 주문 요청 (주문서 ID c-77)
    주문->>주문: 삽입 시 주문서 ID 유니크 위반
    주문->>주문: 기존 주문 20261028-000123 조회
    주문-->>앱: 기존 주문의 현재 상태 (PENDING 또는 PAID)
```

두 번째 요청은 새 주문을 만들지 않으므로 결제도 다시 나가지 않습니다.

## 6. 주문 정리 배치와 쓰이지 않은 승인

정리 배치는 결제 이벤트를 놓쳤거나, 승인 응답을 받은 직후 PAID 를 커밋하기 전에 주문 서비스가 죽은 경우를 잡습니다.
결제 이벤트 소비자는 주문이 쓰지 않은 승인을 환불합니다.

```mermaid
sequenceDiagram
    autonumber
    participant 정리배치 as 주문 정리 배치
    participant 소비자 as 결제 이벤트 소비자
    participant 주문 as 주문 DB
    participant 결제

    loop 1분마다
        정리배치->>주문: 2분 넘은 PENDING 주문
        정리배치->>결제: 주문번호의 회차별 결제 상태
        alt 승인된 회차 있음
            정리배치->>주문: PENDING 을 PAID 로 + 아웃박스 PAID (1행일 때만)
        else 가장 최근 회차 FAILED 또는 회차 없음, 주문 후 예약 유지 시간 + 2분 지남
            정리배치->>주문: PENDING 을 FAILED 로
        else REQUESTED 또는 UNKNOWN
            Note right of 정리배치: 기다림. 15분 넘으면 경보
        end
    end

    결제->>소비자: payment.events APPROVED (회차 r)
    alt 주문 PENDING
        소비자->>주문: PAID, paid_round r
    else 주문 PAID 이고 paid_round 가 r
        Note right of 소비자: 중복. 넘김
    else 주문 PAID 이고 다른 회차, 또는 FAILED, CANCELLED
        소비자->>주문: 환불 요청 refund-{주문번호}-orphan-{r} + 경보
    end
```

마지막 갈래는 설계대로면 생기지 않습니다. 대행사가 실패로 닫은 회차를 아주 늦게 승인한 경우에 대비한 안전망입니다.
